(未來規劃)======如果在EXCLE上更新資料呢============
架構：Excel 按鈕（VBA）→ 本機小埠 → 常駐 Python 進程（養著已登入的瀏覽器）→ 抓資料 → 走 ledger/planner → COM 寫回 Excel → 回訊息。

三個選擇

瀏覽器登入完自動最小化到工作列（不用無頭模式，憑證會出事）
Excel 上另加一顆「收工」按鈕關掉常駐
按下去同步等結果，跳 MsgBox 告訴你寫了什麼
規劃過程中挖出來、之後動手時不能忘的
一、一個瀏覽器同時只帶得動一個帳號的身分。 同一個 context 共用 JSESSIONID，後登入的頂掉前面的。但這只是瀏覽器這一邊的事：伺服器上 20 個帳號是 20 個各自獨立的 session，B 登入不會殺掉 A 的。2026-08-19 已經照這個做法改掉了 —— 登入時把每一組的 cookie 收起來，換人就換 cookie（見 fetch.new_store），不必重登；只有那一組在伺服器上逾時了才會真的重登一次。常駐服務沿用同一份 store 就好。

二、VBA 必須用非同步 XMLHTTP + DoEvents 迴圈，不能用同步 send。 同步會把 Excel 的訊息幫浦鎖死，而常駐進程正要用 COM 回頭寫這個 Excel → 直接卡成「Excel 正在等待另一個應用程式完成 OLE 動作」。這是整個方案最容易踩死的一個地雷。

三、寫入一定要存檔，即使是接上你開著的 Excel。 ui.py:1032-1039 已經為這件事改過一次並留了理由：不存的話紀錄檔記成「寫過了」、檔案卻是舊的，帳本跟檔案分家而畫面上沒有任何徵兆。注意 update_excel.py:250-256 還是舊行為（attached 時不存），常駐服務要跟 ui.py 走，不要跟 CLI 走。

四、常駐模式只能走例行那條路。 第一次接管（--adopt）跟 B8 修改需要你判斷「含不含今天的淨收付」，程式不能猜。所以流程是：開盤前開一次 UI 把狀態確認好，之後整個交易時段都在 Excel 按按鈕。

五、分頁名稱對不到帳號的問題。 .env 只有帳密沒有名字，帳戶名要登入後才從 sessionStorage 拿得到。所以常駐第一次要整批登入建對照表，之後才能「按哪個分頁就更新哪個交易人」。
