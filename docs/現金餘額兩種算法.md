# 現金餘額的兩種算法

現金餘額（Excel B8）算法，2026/08/19 起兩種並存，一個總開關（20 人一起），
人決定今天用哪一種：

    方法一（初始餘額累加）  現金餘額 = 今日初始現金餘額 + 今日淨收付
    方法二（銀行餘額推算）  現金餘額 = 銀行現金餘額 + 還沒交割的淨收付

兩種都是「算出 B8 該是多少」然後直接覆蓋，差別只在錢從哪裡數起；兩種都是
「對」的，只是對的日子不同（全額交割股當天方法二會扣兩次錢，見下面「為什麼
方法一不能拿掉」）。


## 資料來源一覽（2026/08/24 起）

| 資料                                | 網頁                       | CMD                                                |
| ------------------------------------ | -------------------------- | --------------------------------------------------- |
| 股數、成本                           | 未實現損益（`type=4`）     | `queryInstantAccount_new`（`range=stksum,stkdat`） |
| 淨收付(T+0)／(T+1)（含今日淨收付）   | 交割金額查詢（`type=3`）   | `query610`                                          |
| 銀行現金餘額                         | 銀行餘額查詢（`type=12`）  | `queryBankBalance`                                  |

- **交割金額查詢一支頂兩種算法**：初始餘額累加只用「今天」那一列當今日淨收
  付；銀行餘額推算把 `cdate` 比今天晚的列全部加總當「還沒交割的錢」。這支查
  詢固定回 3 筆，T+2 交割制度下最舊那一列的 `cdate` 數學上必然等於今天，會被
  規則濾掉——所以實務上加總結果永遠只有淨收付(T+0)＋淨收付(T+1)，不會出現
  T+2。兩種算法現在都固定查這支，不受方法切換影響。
- **銀行餘額查詢只有用「銀行餘額推算」那天才查**——初始餘額累加完全用不
  到，是唯一還會因算法不同而省掉的一支（20 個帳號一次讀取省 20 次往返）。


## 方法二：還沒交割的那幾天

銀行餘額只含**已經交割**的錢。台股 T+2，今天成交的要到後天才真的離開帳戶，
要補的就是這段時間差：

    現金餘額 = 銀行餘額 + Σ(交割日比今天晚的那幾天的淨收付)

畫面與 B8 公式都一天一項，不合計成一個數字：

    銀行餘額 + 淨收付(T+0) + 淨收付(T+1) = 893 - 238 + 0 = 655

`T+0` 是 `query610` 裡最新的成交日（正常情況即今天），標籤照列數往回數（不
是照日曆——隔週末連假算不出「前一個交易日」）。交割日等於今天的那一列不
補，那筆錢今天早上就扣掉了。**銀行餘額推算這一種 B8 直接寫算出來的數字，不
寫公式**（`planner._cash` 不設 `formula`，`_collect_writes` 退回用
`proposed`）；畫面上仍照算式攤開講給人看（`planner._bank_note`）。

這條路換過兩次（「當日＋昨日」→ 撈十天逐筆看 `cdate` → 現在的交割金額查詢一
次到位），沒有一次是因為前一種算錯，是逐步少掉「自己猜日期區間」的中間層；
細節見 git log（2026/08/19～08/21 commit）。

**代價是它沒有回顯帳號**：`query610` 不帶 `bhno`/`cseq`，核不了身分。可接受
是因為同一輪一定會查未實現損益（每一列都帶 `bhno`/`cseq`），session 被頂掉
時那支會先擋下來；現金那一格沒有它就整格不寫。

**前提：交割扣款早上就跑完了**。這是方法二成立的前提——如果哪天扣款時點變
了（或有人一早就跑這支程式），交割日等於今天的那一列會不會已經扣掉就不一定
了，要重新檢查這一段。


## 為什麼方法一不能拿掉

全額交割股是預收：錢在成交當下就從銀行餘額被扣走，但那一筆同時**還掛在當日
淨收付上**（網站下午才更新改正）。方法二在那段時間會扣兩次；方法一不看銀行
餘額，只看「今天開盤前多少錢」加「今天淨收付」，那一天反而是對的。兩種算法
並存不是備援，是各有各正確的日子。


## 已定案的決策（不要擅自改）

- **一個總開關，不是一人一格**：20 位交易人買賣標的都一樣，全額交割那天全
  部一起中。
- **預設一律「初始餘額累加」，不記憶上次選什麼**（`_default_method`）：兩種
  算法錯的方式不對稱——方法二錯了會把同一筆錢扣兩次、直接寫進 Excel；方法
  一最壞只是漏匯撥/股利，當下就對不起來、補得回來。「忘了換」要往安全的那
  邊倒，不能讓某一天的特例延續到之後每一天。
- **程式開起來、第一次按「讀取網頁資料」跳視窗問一次**；同次執行讀第二次不
  再問，關掉重開再問一次（`cash_method_asked`，只放記憶體不進紀錄檔）。常駐
  狀態列的算法名字本身也是切換入口（點一下先跳確認視窗再換，見
  `ui_sync._on_method_click`），兩個入口都在，換完只在這次執行內有效。
- **用銀行餘額推算的日子，「修改今日初始現金餘額」按鈕整顆藏起來**
  （`ui_sync._show_opening_row`）：那顆改的是初始餘額累加的基準，今天沒用這
  種算法時擺著只會讓人誤以為「餘額不對就按它」。
- **視窗不逐人列**：算法是全部人共用的一個開關，逐人列會看起來像可以一位一
  位挑。視窗只講「有幾位對不上、差額合計多少」，是誰、差在哪，主畫面每個人
  的現金那條後面才寫。
- **程式只算選中的那一種，不做兩種比對**：差額講不出是什麼造成的（全額交
  割？匯撥？手改過 B8？），程式分不出來；一個幫不上決定又天天出現的數字只
  會讓人不再看那個畫面。順便省查詢——用初始餘額累加的日子完全不碰銀行餘
  額，20 個帳號一次讀取省 40 次往返。
- **視窗問在讀取之前，不是讀完之後**：不必攤數字就不必等資料，也不會發生
  「選了銀行餘額推算，但這輪沒抓，要再讀一次」的情況。


## 網頁那邊怎麼拿（API 細節，2026/08/19、08/21、08/24 實測過）

原始資料在 `偵察資料\20260819_2037_*` 與 `偵察資料\20260821_140*`，跑法是
`python recon.py 1`（只讀不寫）。

### 交割金額：`CMD=query610`

交割金額查詢那一頁（`account/layoutRWD.jsp?type=3`）自己打的那一支。
`paramInfo = {branchId: '1'+branch_id, custId: cust_id}`。回應：

```json
{"data":[{"trade":"20260819","cdate":"20260821","pay_amt":"0"},
         {"trade":"20260820","cdate":"20260824","pay_amt":"0"},
         {"trade":"20260821","cdate":"20260825","pay_amt":"-238"}],
 "retcode":"000000","retmsg":"交易正常"}
```

| 要注意的  | 說明                                                                                                          |
| --------- | --------------------------------------------------------------------------------------------------------------- |
| `trade`   | 成交日；`cdate` 交割日；`pay_amt` 那一天的淨額，**負數＝要付出去**（帶正負號，不是分開的應付/應收兩欄）        |
| 固定 3 筆 | 永遠回最近 3 個交易日各一列（含今天），沒成交就是 0——「一列都沒有」代表查詢沒查成，不是「沒有錢要交割」，程式當錯誤擋住 |
| `branchId`| **一定要加 `'1'`**。不加也回 `retcode 000000`，只是每天都變成 0                                                |
| 回顯帳號  | **沒有 `bhno`/`cseq`**，核不了身分（補救見上一節）                                                              |

2026/08/24 對過一次答案（[[monday-verify-query610]]），跟事先寫的預期表完全
一致：08/20→08/24 這列 `pay_amt=0`（週一早上已扣，不用補）、08/21→08/25 這列
`pay_amt=-238`（要補）；`pay_amt` 是網站算好的帶符號淨額（應收－應付），不是
只看應付款；「今天」那一列會隨當天陸續成交即時更新。

### 銀行餘額：`CMD=queryBankBalance`

`paramInfo = {branchId: '1'+branch_id, custId: cust_id}`（跟其他查詢同款）。
回應：

```json
{"data":[{"Amount":"0000000089300","bnkacc":"71017108640","bnkno":"050",
          "qry_date":"20260819","qry_times":"203145"}],"retcode":"000000"}
```

| 要注意的 | 說明                                                              |
| -------- | -------------------------------------------------------------------- |
| `Amount` | **單位是分，要除以 100**（89300 = 畫面上的 893.00）——弄錯不會報錯，只會讓 Excel 出現一個 100 倍大、看起來很像真的數字 |
| `data`   | 是**陣列**，可能綁多個銀行帳戶。多筆時要用哪一個未知 → 擋住不寫       |
| 帳號核對 | 回應裡**沒有 `bhno`/`cseq`**，身分靠同一輪最先查的未實現損益撐著     |

帳號核對曾另外比對「`bnkacc` 有沒有含著去掉前導零的客戶號」，2026/08/24 拿
掉了：真帳號的銀行帳號本來就不含客戶號，這道弱核對是誤判，每次都擋現金格卻
沒真的抓到過抓錯人。現在完全靠「同一輪最先查的未實現損益已經核過
bhno/cseq」撐著。

備援：這頁（`layoutRWD.jsp?type=12`）自己會查好填進 `#tDate` `#tTimes`
`#tAccount` `#tBalance`（值在 `<input>` 裡）。AJAX 壞掉時可以改讀畫面，代價
是每個帳號多開一次頁面。

### 淨收付：`CMD=queryInstantAccount_new`

選哪天 CMD 都一樣，差別藏在加密的 `Param` 裡；`queryType` 對照表：

| `queryType` | 意思 | `queryType` | 意思     |
| ----------- | ---- | ------------ | -------- |
| 1           | 當日 | 5            | 上月     |
| 6           | 前一日 | 0          | 指定日期 |
| 2           | 近三日 | 4          | 本月     |

**指定日期格式是 `YYYY/MM/DD`**（送 `#startDate`）。用 `2026-08-18` 會回
`602002 查詢日期起訖錯誤`——`getTransDate()` 裡帶 `-` 的寫法填的是
`#sdate`/`#edate`，已經沒人在用，別跟著抄。

程式現在只用 `queryType:'1'`（當日）；指定區間那一支改用交割金額查詢之後只
剩 `recon.py` 在打，當「兩條路算出來一不一樣」的對照組。

**網頁的淨收付合計不含匯撥**：type=2 的 `getRowData()` 加總前會濾掉 `reason`
非空（匯撥、配股）與 `stkno` 尾碼 `O` 的列。方法一（漏掉匯撥/股利）跟方法二
（銀行餘額本來就含）受這件事的影響剛好相反，是方法二該當預設的另一個理由。
改用交割金額查詢之後，方法二連「要不要濾 `reason`」都不用管——`pay_amt` 是
網站按交割日結出來的數字，沒有明細可濾。

### 附帶：`CMD=transDateQuery`

`paramInfo = {branchId, custId}`，**branchId 不加 `'1'`**（跟其他查詢不一
樣）。方法二用 `cdate` 之後不再需要它，留著是因為它能回答「今天是不是交易
日」，將來防呆用得上。

| 檔案                     | 內容                                                                       |
| ------------------------ | ----------------------------------------------------------------------------- |
| `recon.py`                | 參數/格式/單位/`cdate` 全部實測過的偵察腳本                                  |
| `fetch.py`                | `need_bank=True` 時才多抓銀行餘額與交割金額，帶身分核對與 `settle_problem`  |
| `dev_tools/simulate.py`   | 假網頁補上銀行餘額、交割日、`query610` 那份、已交割開關                     |
| `planner.py`              | 只算 method 指定的那一種；資料沒抓到就擋住（`pending_total`）               |
| `ui.py` / `ui_sync.py`    | 總開關下拉、每天第一次讀取前跳視窗、常駐狀態列點名字切換（介面細節見 [[同步分頁訊息框改版]]） |

`ledger.py` 沒有存 `cash_method`（2026/08/21 起連 `settings` 都不寫，算法只
活在這次執行裡）：現金那一格的自動/手動判定兩種算法完全一樣（都是拿 Excel
現值跟 `last_written` 比），不必分岔；方法二不需要 baseline，但 baseline 照
樣每天設——隨時切回方法一都要它。

**還沒做的**：`fetch.login_only()` 沒有跟著抓這兩支（登入當下不查資料，維持
原樣）。方法二那幾道擋法（見下面「安全網」）都還沒在真實情境下觸發過，只在
模擬頁面上試過。


## 安全網

1. **任何一項資料查不到、或讀不懂就擋住現金那一格，絕不當成 0**。
   `bank_balance()` 讀不懂 `Amount` 時回 `None` 而不是 0——`to_num` 預設把看
   不懂的東西當成 0，而 0 在這裡看起來像一個答案（這個人沒錢），會被拿去覆
   蓋 B8（真的踩過一次：模擬頁面把負數補零成 `000-793672200`，餘額整個變成
   0）。

   | 擋在哪                  | 情況                                               |
   | ------------------------ | ---------------------------------------------------- |
   | `fetch.bank_problem`     | 銀行餘額查不到、銀行帳戶不只一筆                     |
   | `fetch.settle_problem`   | 交割金額一列都沒有、讀不到交割日、讀不到金額         |
   | `planner._cash_blocked`  | 銀行餘額或交割金額整支沒抓到（例如剛換算法那一輪）   |
   | `planner._cash_blocked`  | 未實現損益說今天有成交、交割金額裡今天卻是 0（收盤結帳後這支還準不準的保險——今天成交的錢一定還掛在交割金額上，掛不上就是資料不對） |

2. **歷程記下這一筆是用哪個算法算的**：日後對帳「那天餘額為什麼是那個數
   字」問不出來的代價很高。


## 注意事項（容易改壞的地方）

- **`branchId` 要加 `'1'` 前綴**（`query610`、`queryBankBalance`），但
  **`transDateQuery` 不加**。錯了不會報錯，只是靜靜少算或算出 0——這條最危
  險，改到這幾支查詢務必重新核對一次。
- **`queryBankBalance` 的 `Amount` 單位是分，要除以 100**，弄錯不報錯，只會
  讓 Excel 出現一個 100 倍大、看起來很像真的數字。
- **B8 無條件覆蓋，兩種算法都一樣**：不像股數/成本比對 `last_written` 才決
  定寫不寫。初始餘額累加寫的是公式，數字沒變也要覆蓋（否則格子裡可能是昨天
  的過期公式，數字對、明細卻是舊的）；銀行餘額推算寫的雖已是數字，仍沿用
  「一律覆蓋」，沒必要為它一個人加特例。
- **銀行餘額推算寫的是算出來的數字，不是公式**——`planner._cash` 不設
  `formula` 這件事本身就是切換依據，`_collect_writes` 靠這個決定要不要退回
  用 `proposed`。
- **`query610` 固定回 3 筆**：一列都沒有代表查詢沒查成，不是「沒有錢要交
  割」，程式當錯誤處理，別誤判成「今天沒事」。
- **兩種算法錯的方式不對稱**：方法二錯了會把錢扣兩次、直接寫進 Excel；方法
  一最壞只是漏匯撥/股利，當下就能發現。改預設值或錯誤處理前先想清楚哪種錯
  法比較安全。
- **交割扣款早上就跑完，是方法二成立的前提**——如果扣款時點改變，要重新檢
  查交割日等於今天那一列會不會已經扣掉。


## 這裡測不到什麼

- 模擬帳號的假網頁形狀對、行為不見得對。全額交割當天「銀行餘額已扣、當日淨
  收付還沒改正」那個時間差，只有真的遇到那天才驗得出來——第一次遇到要人自
  己核對一次，別直接相信畫面。
- 一個帳號綁多個銀行帳戶長什麼樣，沒看過。
- `reason` 非空（匯撥、配股）的列長什麼樣沒看過；`query610` 的 `pay_amt` 含
  不含它們也就跟著不知道。
- **收盤結帳（約 17~20 點）之後 `query610` 還準不準，沒有人在那個時段查
  過**——已知的是當日淨收付那一支在那個時段會查不到資料，理論上交割金額是
  排程，不該受結帳影響，但那只是推論。真的要在那個時段跑之前，先用
  `python recon.py 1` 看一次兩條路一不一樣。
- 非交易日（週六）跑 `query610` 會回什麼，還沒看過。
