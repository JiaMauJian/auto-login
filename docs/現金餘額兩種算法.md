# 現金餘額的兩種算法

2026/08/19 使用者提出。原本只有一種算法，現在要並存兩種，由人決定今天用哪一種。

    方法一（原本的）  現金餘額 = 今日初始現金餘額 + 今日淨收付
    方法二（新增的）  現金餘額 = 銀行現金餘額 + 還沒扣款的交割金額

兩種都是「算出 Excel 的 B8 該是多少」，然後直接覆蓋。差別只在錢從哪裡數起。

使用者原本講的方法二是「銀行餘額 + 當日淨收付 + 昨日淨收付」，後來改成用交割日
（`cdate`）判斷。2026/08/21 使用者又找到**交割金額查詢**這一頁
（`account/layoutRWD.jsp?type=3`），它一次就把「接下來每一天各要交割多少」列出來，
所以現在連「撈一段區間再逐筆看 `cdate`」都不必了 —— 演進的三步與各自的理由見下一節。


## 方法二要補的是「還沒交割的那幾天」

銀行餘額只含**已經交割**的錢。台股 T+2，所以今天成交的要到後天才會真的離開帳戶。
要補的就是這一段時間差：

    現金餘額 = 銀行餘額 + Σ(交割日比今天晚的那幾天的交割金額)

資料來自交割金額查詢（`CMD=query610`，見下面「網頁那邊怎麼拿」）。它一天一列，
金額已經是那一天的淨額，程式只要挑出交割日比今天晚的幾列加起來。
交割日等於今天的那一列**不補** —— 那筆錢今天早上就扣掉了。

**這條路換過兩次，兩次都不是因為前一種算錯**（免得日後有人以為換掉是因為它壞了）：

1. **「當日 + 昨日」** 在交易日跑、而且早上扣款已經跑完的前提下是對的。週一也對
   —— 週四成交的剛好在週一早上交割掉，所以週一還欠著的正是週五加週一。
   它的兩個缺口都不在數字上：「前一日」到底是「前一個交易日」還是「日曆上的昨天」
   沒有人證實過（2026/08/19 那次回空的，兩種解釋都說得通）；在非交易日跑會漏一天
   （週六跑的話週四與週五都還沒交割，而「前一日」只抓得到週五）。
2. **「撈十個日曆天的成交，逐筆看 `cdate`」** 把上面兩個缺口補掉了：交割日是每一筆
   自己帶著的，不必經過「前一日是哪一天」這個要靠伺服器解釋的中間層。它算得對
   —— 2026/08/21 跟現在這條路對過答案，兩邊都是 `-238`。
3. **交割金額查詢**（現在用的）少掉的是「自己算日期區間」與「逐筆挑」這兩件事：
   網站直接照交割日把錢分好了。一個帳號一次往返（原本是撈區間那一支），
   回應也從一大包成交明細變成三列。

**代價是它沒有回顯帳號。** 其他查詢每一列都帶 `bhno`/`cseq`，可以硬核對「這份資料
是不是這個人的」，`query610` 沒有。這件事之所以還能接受，是因為同一輪一定會抓
**當日淨收付**，那一支每一列都有 `bhno`/`cseq`：session 被別人頂掉時它會先被擋下來，
而現金那一格沒有它就整格不寫（見 `planner._cash_blocked` 第一道）。
換句話說，身分核對沒有消失，只是不在這一支上。

**前提：交割扣款早上就跑完了。** 使用者確認扣款遠早於九點、而他九點後才交易，
所以按下讀取的任何時刻，銀行餘額都已經是「今天該扣的都扣完」的狀態。
這件事是方法二成立的前提 —— 如果哪天扣款時點變了（或有人一早就跑這支程式），
交割日等於今天的那一列會不會已經扣掉就不一定了，那時要重新檢查這一段。


## 為什麼方法一不能拿掉

全額交割股是預收：錢在成交當下就從銀行餘額被扣走，但那一筆同時**還掛在當日淨收付上**
（網站下午才更新改正）。方法二在那段時間會扣兩次。

方法一不看銀行餘額，只看「今天開盤前有多少錢」加「今天淨收付」，所以那一天反而是對的。
這就是使用者要求兩種並存的原因 —— 不是備援，是各有各正確的日子。


## 已定案的決策（使用者親自選的，不要擅自改）

- **一個總開關，不是一人一個。** 20 位交易人買賣的標的都一樣，全額交割那天是全部一起中，
  沒有「只有某一位要切」的情況。設定記在紀錄檔的 settings。
- **這次程式開起來、第一次按「讀取網頁資料」跳視窗問一次今天要用哪一種。**
  同一次執行裡讀第二次以後不再問；關掉程式重開，下次讀取會再問一次
  （見 `cash_method_asked`，只放記憶體不進紀錄檔）。問過、名字顯示出來之後，
  工具列上那個名字本身也是一個開關：點一下先跳確認視窗、再換成另一種
  （2026/08/20 加的，見下方「2026/08/20 加的地方」）——不必等重開程式或還原
  Excel 備份，兩個入口都在、答案都寫進紀錄檔的 `cash_method` 跨天沿用。
- **用銀行餘額推算的日子，「修改今日初始現金餘額」那顆按鈕整顆藏起來**
  （2026/08/20 使用者要求）。它改的是初始餘額累加那一種的基準，今天既然不用那種
  算法，擺在那裡只會讓人以為「餘額不對就按它」。原本的做法是灰掉 —— 灰掉擋得住
  按下去，擋不住「這顆是不是壞了」這個誤會。數字本身不藏（基準每天照樣設，
  明天切回去就要用它），旁邊那句「現在用銀行餘額推算，這個數字不會寫進 B8」
  也留著：按鈕不見了，更要看得到為什麼。
- **視窗不逐人列**（2026/08/19 使用者看過第一版後要求）：算法是全部人共用的一個開關，
  把每個人一列列出來會看起來像可以一位一位挑，而那正是這個設計不允許的事。
  視窗上只講「有幾位對不上、差額合計多少」；是誰、差在哪裡，主畫面每個人的
  現金那一條後面都寫著。
- **程式只算選中的那一種，不做兩種比對**（2026/08/19 使用者問「為什麼要特別檢查
  每個人的算法」之後拿掉整套）。原本兩種都算、在每個人的現金那一條後面寫著另一種
  算出來多少，當成「你的帳跟銀行對不對得起來」的對帳訊號。拿掉的理由：

  差額講不出是什麼造成的 —— 全額交割？匯撥或股利？有人手改過 B8？程式分不出來。
  而「今天要用哪一種」的判斷依據是「今天有沒有買全額交割股」，那只有人知道，
  不在畫面上。一個幫不上決定、又天天出現的數字，只會讓人不再看那個畫面。

  省下來的還有查詢：用「初始餘額累加」的日子完全不必碰銀行餘額，
  20 個帳號每次讀取少 40 次往返。

- **視窗問在讀取之前**，不是讀完之後。因為不必攤出任何數字，就不必等資料；
  而算法決定這一輪要不要多抓那兩支，先問才不會發生「選了銀行餘額推算，
  但這一輪沒抓，要再讀一次」。視窗長這樣：

        今天所有人的現金餘額要用哪一種算法？20 位一起，不分開挑。

          ( ) 銀行餘額推算
          (o) 初始餘額累加

        （下面小字：兩種各是什麼、全額交割那天要選哪一個、
          這個視窗每天只跳一次、上面的下拉隨時改得動）

  中途換算法要再按一次「讀取網頁資料」，換成銀行餘額推算時尤其明顯 ——
  那一輪沒抓銀行餘額，現金那一格會直接擋住並寫明原因，不會拿舊資料算一個數字出來。

## 網頁那邊怎麼拿（2026/08/19 與 08/21 偵察全部實測過）

原始資料在 `偵察資料\20260819_2037_*` 與 `偵察資料\20260821_140*`，
跑法是 `python recon.py 1`（只讀不寫）。

### 交割金額：`CMD=query610`

就是交割金額查詢那一頁（`account/layoutRWD.jsp?type=3`）自己打的那一支。
`paramInfo = {branchId: '1'+branch_id, custId: cust_id}`。回應：

```json
{"data":[{"trade":"20260819","cdate":"20260821","pay_amt":"0"},
         {"trade":"20260820","cdate":"20260824","pay_amt":"0"},
         {"trade":"20260821","cdate":"20260825","pay_amt":"-238"}],
 "retcode":"000000","retmsg":"交易正常"}
```

| 要注意的       | 說明                                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `trade`        | 成交日；`cdate` 交割日；`pay_amt` 那一天的淨額，**負數＝要付出去**（畫面上分成應付款／應收款兩欄，這裡是一個帶正負號的數字） |
| 沒有成交也有列 | 最近幾個交易日一律各給一列，沒成交就是 0 —— 所以「一列都沒有」代表查詢沒查成，不是「沒有錢要交割」，程式當成錯誤擋住         |
| `branchId`     | **一定要加 `'1'`**。不加也回 `retcode 000000`，只是每一天都變成 0                                                            |
| 回顯帳號       | **沒有 `bhno`/`cseq`**，核不了身分（理由與補救見上一節）                                                                     |

`branchId` 那條跟銀行餘額的 `Amount` 同一種危險：錯了不報錯，只是靜靜少算錢。

2026/08/21 14:08 對過答案：這一支算出 `-238`，撈十天逐筆看 `cdate` 也是 `-238`，
當日淨收付合計同樣是 `-238`，銀行餘額 893 → 兩條路都得到 655。

### 銀行餘額：`CMD=queryBankBalance`

`paramInfo = {branchId: '1'+branch_id, custId: cust_id}`（跟其他查詢同款）。回應：

```json
{"data":[{"Amount":"0000000089300","bnkacc":"71017108640","bnkno":"050",
          "qry_date":"20260819","qry_times":"203145"}],"retcode":"000000"}
```

| 要注意的 | 說明                                                               |
| -------- | ------------------------------------------------------------------ |
| `Amount` | **單位是分，要除以 100**（89300 = 畫面上的 893.00）                |
| `data`   | 是**陣列**，可能綁多個銀行帳戶。多筆時要用哪一個未知 → 擋住不寫    |
| 帳號核對 | 回應裡**沒有 `bhno`/`cseq`**，只能靠 `bnkacc` 含著客戶號（弱核對） |

`Amount` 那條是整條路上最危險的細節：弄錯不會報錯，只會讓 Excel 出現一個 100 倍大、
看起來很像真的數字。程式裡要跟畫面上的值對一次答案。

帳號核對只能比對去掉前導零的客戶號（`71017108640` 含 `108640`），是弱核對，
要用第二組真帳號確認規則才敢寫死。銀行餘額是單一數字，抄錯人不會有任何徵兆。

備援：這一頁（`layoutRWD.jsp?type=12`）自己會查好填進四個固定 id ——
`#tDate` `#tTimes` `#tAccount` `#tBalance`（值在裡面的 `<input>`，要讀 value）。
AJAX 壞掉時可以改讀畫面，代價是每個帳號多開一次頁面。

### 淨收付：`CMD=queryInstantAccount_new`

選哪一天 **CMD 都一樣**，差別藏在加密的 `Param` 裡（固定 256 bytes、每次都不同，
比對兩串密文問不出東西）。看 type=2 頁面的 JS 才有答案：

```js
if($('#time').val()=='0'){        // 指定日期
    qrytype = '0';
    sdate=$('#startDate').val();  edate=$('#endDate').val();
}else{
    qrytype = $("#time").val();   // 其餘全部照抄下拉的 value
}
```

| `queryType` | 意思   | `queryType` | 意思     |
| ----------- | ------ | ----------- | -------- |
| 1           | 當日   | 5           | 上月     |
| 6           | 前一日 | 0           | 指定日期 |
| 2           | 近三日 | 4           | 本月     |

**指定日期的格式是 `YYYY/MM/DD`**（送出的是 `#startDate`，daterangepicker 的輸入框）。
用 `2026-08-18` 會回 `602002 查詢日期起訖錯誤` —— `getTransDate()` 裡那個帶 `-` 的寫法
填的是 `#sdate`/`#edate`，已經沒人在用了，別跟著抄。

**實測證據**：指定 `2026/08/17` 查回 `-107`、`tdate=20260817`、`cdate=20260819`，
跟那天的成交一致 —— 指哪打哪，這條路可以信。

程式現在只用 `queryType:'1'`（當日）那一支；指定區間那一支改用交割金額查詢之後
只剩 `recon.py` 在打，當成「兩條路算出來一不一樣」的對照組。上面這段留著，
是因為那個對照組要靠它，而且它是目前唯一能查到過去某一天成交明細的路。

### 附帶：`CMD=transDateQuery`

`paramInfo = {branchId, custId}`，**branchId 不加 '1'**（跟其他查詢不一樣）。回應：

```json
{"isTransDate":"1","lastTransDate":"20260818","nextTransDate":"20260820",
 "secTransDate":"20260821","comOpenTime":"0832","comEndTime":"1335", ...}
```

方法二用 `cdate` 之後就不需要它了（不必問「昨天是哪一天」）。留著這段是因為
它能回答「今天是不是交易日」與「今天成交的交割日是哪一天」，將來要做防呆用得上。

### 網頁的淨收付合計不含匯撥

type=2 的 `getRowData()` 在加總之前會先濾掉 `reason` 不是空字串的列（匯撥、配股）
與 `stkno` 尾碼 `O` 的列。這件事對兩種算法的影響剛好相反：

- 方法一（初始 + 淨收付）**漏掉匯撥與股利** —— 從交割帳戶匯錢進出，餘額不會跟著動。
- 方法二（銀行餘額 + 未交割）**自動吸收**，因為銀行餘額本來就已經含了。

這是方法二該當預設的另一個理由。程式現在的 `settlement_total()` 只濾 `qty=='0'`、
沒濾 `reason`，跟畫面的算法不一致（見 todo 4.1，要先看到真的匯撥列長什麼樣再改）。

改用交割金額查詢之後，方法二連「要不要濾 `reason`」這個問題都沒有了：`pay_amt`
是網站自己按交割日結出來的一個數字，沒有明細可以濾。它到底含不含匯撥與配股，
要等真的遇到那種列才知道 —— 但無論含不含，那都是「這一天實際會從銀行帳戶進出多少」，
本來就是方法二要的東西。


## 程式怎麼改

方法一與方法二的本質不同，這決定了程式的形狀：

| 方法   | 本質 | 需要基準嗎             | 跟哪一格同類     |
| ------ | ---- | ---------------------- | ---------------- |
| 方法一 | 累加 | 要（今日初始現金餘額） | 只有現金是這樣   |
| 方法二 | 快照 | 不要，網頁直接給絕對值 | 跟股數、成本同類 |

**方法一的機制一格都不動。** 每天第一次讀取網頁資料照樣設好基準
（`planner.initialize`，現在掛在 `_on_fetched` 裡，登入按鈕不碰這件事），
所以任何時候切回去都是對的，也不會有補算舊帳的問題。方法二只是在 `planner._cash()`
多開一條路，其餘（自動／手動判定、寫入、歷程）兩條路共用。

| 階段 | 檔案                    | 狀態           | 內容                                                                                            |
| ---- | ----------------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| 0    | `recon.py`              | 完成           | 參數、格式、單位、`cdate` 全部實測過；2026/08/21 加上 `query610`，並把舊路留著當對照組          |
| 1    | `fetch.py`              | 完成           | `need_bank=True` 時才多抓銀行餘額與交割金額，加身分核對與 `settle_problem`                      |
| 1    | `dev_tools/simulate.py` | 完成           | 假網頁補上銀行餘額、交割日與「已交割」開關；2026/08/21 補上 `query610` 那一份                   |
| 2    | `planner.py`            | 完成           | 只算 method 指定的那一種；資料沒抓到就擋住（`pending_total`）                                   |
| 3    | `ui.py`                 | 完成           | 總開關下拉、每天第一次讀取「之前」跳的視窗，加上點名字切換（2026/08/20 加法，見下）             |
| 4    | `update_excel.py`       | 完成（已移除） | `--cash=bank` / `--cash=opening`，曾跟介面共用同一個設定；2026/08/20 CLI 拿掉後功能全部併入 GUI |

**2026/08/20 加的地方**：原本規劃的「每天第一次讀取前跳視窗問、問完之後畫面上
沒有任何入口可以改」沒有變；多加了一個入口 —— 問過、名字顯示出來之後，工具列的
「現金算法」名字本身也能點一下切換（`ui_background._toggle_cash_method`），先跳
確認視窗（防手滑，預設「取消」）再換，換完立刻重算、寫進紀錄檔的 `cash_method`
跨天沿用。理由：測試時每次都要靠還原 Excel 備份才能換答案太重。

點名字切換測得差不多之後，使用者要求這顆開關本身也能整個關掉，正式使用時避免
手滑誤觸 —— 加了 `.env` 的 `CASH_METHOD_TOGGLE`（`ui_common.cash_method_toggle_enabled`）。
留空或設 1 是原本行為；設 0 時名字還在畫面上，只是不綁點擊、游標也不變手指，
看起來是純顯示（`ui_layout.py` 建版面時就決定，改了要重開介面）。每天第一次
讀取前跳視窗問一次的原本流程完全不受影響，這顆開關只管工具列那個名字。

`ledger.py` 沒有動：算法記在 `settings` 的 `cash_method`，
現金那一格的自動／手動判定兩種算法完全一樣（都是拿 Excel 現值跟 `last_written` 比），
所以不必分岔。方法二不需要 baseline，但 baseline 照樣每天設 —— 隨時切回方法一都要它。

**還沒做的**：`fetch.login_only()` 沒有跟著抓這兩支（登入當下不查資料，維持原樣）。
方法二那幾道擋法（見下面「安全網」的表）都還沒在真實情境下觸發過，只在模擬頁面上試過。


## 安全網

1. **任何一項資料查不到、或讀不懂就擋住現金那一格**，絕不當成 0。
   `bank_balance()` 讀不懂 `Amount` 時回 None 而不是 0 —— `to_num` 預設把看不懂的
   東西當成 0，而 0 在這裡看起來像一個答案（這個人沒錢），會被拿去覆蓋 B8。
   真的踩過一次：模擬頁面把負數補零成 `000-793672200`，整個人的餘額就變成 0 了。沿用現有的 `blocked` 機制
   （就是「淨收付是 0 但今天有成交」那道）。方法二要擋的情況多了這幾種：

   | 擋在哪                  | 情況                                               |
   | ----------------------- | -------------------------------------------------- |
   | `fetch.bank_problem`    | 銀行餘額查不到、銀行帳戶不只一筆、帳號對不上       |
   | `fetch.settle_problem`  | 交割金額一列都沒有、讀不到交割日、讀不到金額       |
   | `planner._cash_blocked` | 銀行餘額或交割金額整支沒抓到（例如剛換算法那一輪） |
   | `planner._cash_blocked` | 未實現損益說今天有成交、交割金額裡今天卻是 0       |

   最後那道是「收盤結帳之後這支還準不準」的保險：今天成交的錢要 T+2 才扣，
   所以一定還掛在交割金額上，掛不上就是資料不對。少算的正好是今天那一整筆，
   而畫面上不會有任何徵兆。
2. **歷程記下這一筆是用哪個算法算的。** 日後對帳時，「那天餘額為什麼是那個數字」
   問不出來的代價很高。


## 這裡測不到什麼

- 模擬帳號的假網頁是自己畫的，形狀對、行為不見得對。全額交割當天「銀行餘額已扣、
  當日淨收付還沒改正」那個時間差，只有真的遇到那一天才驗得出來 —— 第一次遇到時
  要人自己核對一次，別直接相信畫面。
- 一個帳號綁多個銀行帳戶長什麼樣，沒看過。
- `reason` 非空（匯撥、配股）的列長什麼樣，沒看過；`query610` 的 `pay_amt` 含不含它們，
  也就跟著不知道。
- 週一與連假後對不對，要等到那一天才驗得到（平常日看不出差別）。`query610` 那幾天
  會列出哪幾個交易日、非交易日（週六）跑會回什麼，都還沒看過。
- **收盤結帳（約 17~20 點）之後 `query610` 還準不準，沒有人在那個時段查過。**
  這是這次換路留下來最大的一個未知數 —— 已知的是當日淨收付那一支在那個時段會查不到
  資料。理論上交割金額是「還欠著多少」的排程，不該受結帳影響，但那只是推論。
  真的要在那個時段跑之前，先用 `python recon.py 1` 看一次兩條路一不一樣。
