# 分頁認人與並行登入偵察

2026/08/26 用 `recon_session.py` 這支偵察工具，回答兩個各自獨立、但常常被混在一起討論
的問題：

    問題一：不靠換 cookie，分頁能不能各自查回自己的資料？
           （能的話，fetch.py 抓資料架構有機會拿掉「換人要換 cookie」這一步）
    問題二：20 組帳號能不能真的同時（並行）登入，而不是依序排隊？

**目前結論**：問題一方向正面、值得繼續評估；問題二已經實測過、證據不支持繼續做（見下方
「已定案的決策」）。


## 背景

`fetch.py` 的抓資料邏輯假設「整個瀏覽器只有一組 cookie，換帳號登入會把前一個頂掉」，這件
事在真實環境踩過一次 bug（2026/08/21，見 `fetch.collect` 的 docstring）：20 組帳號全部
登入完才回頭抓，前面那幾組拿到的其實是最後一組的資料。

但使用者反應：手動在同一個瀏覽器開 20 個分頁、20 個不同帳號，事後回頭任意點哪個分頁，
資料都還是對的——不管先後順序。這跟「共用一組 cookie」的假設矛盾，值得查清楚：會不會
網站其實有某種機制讓每個分頁能認出自己是誰，只是現在抓資料的方式沒吃到那個機制。


## 三種測法（抓資料，問題一）

`recon_session.py` 依序登入好幾組真帳號（每組一個新分頁，過程中刻意不做任何 cookie
互換），全部登入完、瀏覽器目前帶著的 cookie 只剩「最後登入那組」的之後，回頭測每一個
分頁：

| 測法 | 做法 | 回答的問題 |
| --- | --- | --- |
| 測法一 | 分頁自己重新整理（模擬「回頭點分頁裡的連結」） | 網站自己內部查詢回來的資料屬於誰 |
| 測法二 | 照 `fetch.py` 現在的做法，直接對分頁背景呼叫查詢 API，**一組一組依序做** | 現在的抓資料方式事後依序查會不會查錯人 |
| 測法三 | 用瀏覽器的 `Promise.all` **真的同時**對每一組帳號各發一次背景查詢 API | 好幾組同時查會不會彼此撞在一起——這才是評估「抓資料改平行處理」真正該看的證據 |

測法二就算每次都對，也只證明「事後依序查不會錯」，沒證明「好幾組同時查也不會錯」；測法三
才是「拿掉換 cookie、改平行處理」划不划算的直接答案。


## 登入表單卡不卡（問題二的第一步）

`login.do_login` 裡寫死一個假設：瀏覽器帶著別組的 cookie 時，登入頁不會畫出表單（網站
以為已登入），要先清掉 cookie 才行。這個假設從沒被實際驗證過，`recon_session.py` 的
`_login_all()` 順便安全地記錄每組登入時有沒有真的觸發這條備援路（只留是非值，`do_login`
內部印的身分證字號/明文驗證碼一律用完即丟，不進報告）。


## 並行登入測試（問題二的第二步）

只驗證「表單看不看得到」還不夠——就算表單不卡，登入**送出**那一刻大家還是搶同一份
cookie，這件事需要真的讓好幾組登入重疊時間送出才測得出來。

Playwright 的同步 API 不能跨執行緒安全共用，沒辦法測「好幾組 `do_login` 真的同時在跑」；
`_test_login_concurrency()` 改用 `playwright.async_api` 的 `asyncio.gather`，讓好幾組
`do_login` 真的並行推進，全部做完之後回頭核對每個分頁最後停在誰的身分上，跟前面已經
驗證過的「第幾組真正是誰」對照表比對，判斷會不會撞車。


## 實測結果

用 3 組真帳號（帳號代碼 111E-0041695、111E-0057964、111E-0058358）跑了兩次：

| 時間 | 測法一 | 測法二 | 測法三 | 登入表單卡住？ | 並行登入 |
| --- | --- | --- | --- | --- | --- |
| 2026/08/26 13:49 | 3/3 對 | 3/3 對 | 3/3 對 | 3 組都沒觸發 | （當時還沒加這段） |
| 2026/08/26 14:41 | 3/3 對 | 3/3 對 | 3/3 對 | 3 組都沒觸發 | **1/3 成功、2/3 卡死送不出去** |

原始報告：`偵察資料\20260826_1349_session偵察_邱博笙.txt`、
`偵察資料\20260826_1441_session偵察_邱博笙.txt`。

### 並行登入的失敗模式

3 組真的同時送出登入時，沒有出現「認錯人／撞成別人身分」這種最壞情況（沒有人的分頁最後
停在別人的帳號上），但出現了另一種同樣會擋路的問題：**大多數會直接卡在原頁，送不出
去**。猜測是送出登入那個請求需要跟當下那份共用 cookie 對得起來，好幾組同時送、彼此互相
蓋過，除了「贏那一瞬間」的那組，其他都被網站默默擋住。


## 同一身分多重 session 測試（2026/08/27 新增，跟前面問題一二都不同）

前面測法一二三跟並行登入測試問的都是「不同身分」之間會不會互相干擾；這裡換一個角度：
**同一個身分**依序登入好幾次（.env 的 TBB_ID_1~4 全部設成同一個真帳號），看伺服器允不
允許同一個人的好幾個 session 同時活著，順便驗證「換 cookie」這個機制本身的邊界在哪裡。

三支小工具、三個問題：

| 工具 | 做法 | 結果 |
| --- | --- | --- |
| `recon_same_identity.py` | 同一 context 內依序登入 4 次，收下每次的 cookie，再逐一換回來確認還活不活著 | **4 組全部還活著**，同一身分沒有單一 session 限制 |
| `recon_concurrent_login_time.py` | 把收下來的 4 組 cookie 原封不動搬到全新、獨立的瀏覽器 context（不是原本那個），`asyncio.gather` 真的同時導去歡迎頁 | **4 組全部被導回 `index/home.jsp`**，網站不接受跨瀏覽器重放的 cookie |
| `recon_same_context_login_time.py` | 對照組：留在同一個 context 內依序換 cookie（已知會成功的做法），各自去看歡迎頁「前次登入資訊」 | 4 組讀到的登入時間**全部一樣**——這欄位是帳號層級共用的顯示訊息，不是每個 session 各自獨立記住的值，不能拿來當「session 各自獨立」的證據 |

結論：

- **同一身分可以同時撐好幾個活著的 session**，`fetch.py` 現有的換 cookie 機制對同一人
  一樣有效，不是只對不同人才成立。
- **「真的並行」（跨瀏覽器/跨連線重放 cookie）在這個網站上行不通**：session 驗證不只看
  cookie 值本身，還綁了瀏覽器連線本身的某種特徵（IP、TLS 連線特徵之類，沒有進一步深究）。
  換句話說，前面「抓資料改平行處理可以繼續評估」這句話的「平行」只能是**同一個 context
  內換 cookie 依序處理**（跟現在 `fetch.py` 的架構一樣），不能是好幾個瀏覽器/連線真的同時
  發請求——那條路已經被這次測試堵死，不用再評估。
- 「前次登入資訊」這類網站介面上的顯示訊息不可靠，不能拿來判斷 session 是否各自獨立；
  真正可靠的判斷依據是查詢資料裡回顯的 `bhno`/`cseq`（測法一二三用的就是這個）。


## 已定案的決策（不要擅自改回去測）

- **並行登入（問題二）不繼續做。** 不是資安/認錯人的風險，是可靠度問題：3 組真的同時
  送出，2/3 直接卡死，放大到 20 組代表大部分會登入失敗、還要想辦法補登，比現在依序登入
  （已知穩定，登入約 5.6 秒、讀取約 2.1 秒一組，成本可接受）更麻煩更慢。開多個獨立瀏覽器
  profile 做真並行也一併不用再評估——同一 profile 裡都測出不可靠了，這條路沒有繼續推進
  的必要。
- **「一次把 20 組依序登入完，不必每組手動點」這個需求本來就已經存在**：
  `fetch.login_only()` / GUI 的「登入」按鈕就是做這件事，不需要新開發、也不是「並行」。
- **抓資料改平行處理（問題一）方向持續正面，可以繼續評估，但只能是「同一 context 內換
  cookie 依序處理」這個形式**（見上面「同一身分多重 session 測試」）。兩次測法三都是同一批
  3 組帳號重跑，不是新樣本——真的要動手改 `fetch.py` 架構前，建議先用不同/更多帳號再驗一次。
