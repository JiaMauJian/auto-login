# 持股同步介面規劃

Excel 版面維持原樣，程式自己記帳，用一個 Tkinter 視窗把過程攤開來看。

檔案配置、模組職責、改動前必看的規則見 CLAUDE.md；現金餘額怎麼算見
[[現金餘額兩種算法]]。這份文件只講介面本身的設計與理由。

---

## 一、為什麼要有介面

程式只要記得自己寫過什麼，任何跟記憶不符的數字就一定是人改的——這樣才能
放心讓 Excel 版面完全不動、程式只覆蓋固定幾格。記憶放在 Excel 旁邊的紀錄檔
（`*-同步紀錄.json`、`*-同步歷程.jsonl`），不佔用 Excel 裡任何一格。

---

## 二、更新分頁：左邊挑人、右邊看一個人

多個交易人、每人十幾格，攤平成一張表會很難用：交易人的名字捲出畫面、要處理
誰得整份表捲一遍、表格比視窗寬導致最右邊的說明被切掉。實際的工作方式是
**依序輪詢**——一次只看一個人，看完換下一個，版面就照這個方式切：

```
┌────────────────────────────────────────────────────────────────────────────────────────────┐
│ [ 開啟EXCEL ]  ...\持股管理.xls                                      [ 登入 ] [ 全部登出 ] │
├────────────────────────────────────────────────────────────────────────────────────────────┤
│   更新  │  下單  │  掛單  │  歷程  │  憑證                                                 │
├────────────────────────────────────────────────────────────────────────────────────────────┤
│ 範圍 [ 全部 ▾ ]                                                                            │
│ [ 更新全部帳戶 ]  查詢台企銀，更新 Excel 的持股與現金餘額                                  │
├────────────────────────┬───────────────────────────────────────────────────────────────────┤
│ 交易人   2/20 位要處理 │ 現金算法：初始餘額累加　今日初始現金餘額：553,161                 │
│                        │ 現金餘額：524,854　✓ 與網頁一致（10:32:07）　[ 修改 ]             │
│ 姓名          狀態     │                                                                   │
│ 交易人A          ✓     │ ┌ 交易人G（模擬）　訊息 ────────────────────────────────────────┐ │
│ 交易人B          ⚠     │ │ 10:32:07 [今日初始餘額] 553,161                               │ │
│ 交易人E（模擬） ⚠      │ │ 10:32:07 [餘額更新] 初始餘額累加 = 553,161 - 28,307 = 524,854 │ │
│ 交易人G（模擬） ⚠      │ │ 10:32:07 [股票更新] 2059 川湖　股數 1,000　成本 1,307         │ │
│ 交易人L          ✓     │ │ 10:41:55 [警告] 網頁庫存已無此檔，Excel 那一列沒有動          │ │
│                        │ │ 10:41:55 [異常] 第 3 組登入逾時                               │ │
│ 點一下換人             │ │                                                               │ │
│ Ctrl+↑ / Ctrl+↓        │ │                                                               │ │
│                        │ └───────────────────────────────────────────────────────────────┘ │
├────────────────────────┴───────────────────────────────────────────────────────────────────┤
│ 寫入 3 格完成                                   [ ■ 停止全部操作 ]                         │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

最上面那一條在**分頁列外面**，三個分頁共用：`開啟EXCEL`／`登入`／`全部登出`
管的是「這段工作階段的資源」——Excel 接上了沒、瀏覽器登入了沒——那是整支程式
的前置，不是更新分頁自己的操作（同步要 Excel，下單兩者都要，掛單只要登入，它
一格 Excel 都不碰）。跟底部那條「停止全部操作」同一個道理：人要用它的時候可能
正停在任何一個分頁上。留在更新分頁的是「範圍」與「更新」，那兩個真的只跟更新
有關（見 `ui_layout._build_session_bar` 與 `_build_toolbar`）。

「登入」與「全部登出」是一對，亮暗規矩也一樣：都只看 `self.busy`（那是 cookie
鎖，不是 Excel 鎖），沒開 Excel 照樣按得下去。

「開啟EXCEL」旁邊那行字只有兩句：沒接上就是「EXCEL未開啟」，接上了就是那份檔的
路徑。路徑出現本身就代表開著，不必再補一句說明；沒開著的時候路徑也不是使用者要
看的東西，他要知道的只有「現在有沒有接上」（見 `ui_background._path_text`）。

圖上右上角折成兩行的那一段，實際是**同一列**（現金算法 → 今日初始現金餘額 →
現金餘額 → ✓ 與網頁一致 → 修改），視窗夠寬時排成一行；這裡折開只是為了容得下。
「今日初始現金餘額」與「修改」只有今天用初始餘額累加時才出現，銀行餘額推算的
日子這個基準用不到（見 `ui_sync._show_opening_row`）。

**幾個刻意的決定**

- **沒有「寫入」「上一位／下一位」按鈕**。讀完直接接著寫，不必再多按一顆；
  換人則點左邊名單比按按鈕快，兩者都是同一件事的第二個入口。留下的是
  Ctrl+↑ / Ctrl+↓：手放在右邊訊息框時焦點不在名單裡，還是要能換人。
- 換人照**名單上真正顯示的順序**走（`_shown()` 直接問 Treeview），不照
  `proposals` 的順序算——問畫面才不會跟眼睛看到的分家（更新分頁現在沒有
  篩選，名單就是 `proposals` 的全部；照畫面走是為了將來加回篩選時不必回頭改）。
  `_step_person` 也不等 `<<TreeviewSelect>>`：那個事件要排進事件佇列才送，
  「鍵按了、右邊要立刻換」不該押在佇列什麼時候輪到它上面。
- 高度**不**跟著帳號數長，名單本來就有捲軸。要一次看完就自己拉高視窗，或在
  `.env` 設 `UI_HEIGHT`。外觀有三個設定放在 `.env`（改完要重開介面）：

  | 設定           | 沒設時                   | 有設時             |
  | -------------- | ------------------------ | ------------------ |
  | `UI_FONT_SIZE` | 12                       | 夾在 8～24         |
  | `UI_WIDTH`     | `wide(960)`，跟著字級走  | 當像素用，下限 640 |
  | `UI_HEIGHT`    | `wide(720)`，跟著字級走  | 當像素用，下限 400 |

  長寬填的數字就是像素，不再乘上字級——使用者量的是螢幕上的視窗，不是某個
  基準字級下的寬度。三個設定填了看不懂的東西一律當作沒設，不值得為了一個
  打錯的數字讓介面開不起來。

- 「範圍 全部 ▾」決定的是**讀取哪幾組帳號**（登入一律全部，不看它），跟左邊名單（讀完之後
  看誰）是兩件事，見第四節。

## 三、歷程分頁

```
交易人  簡嘉懋 ▾    項目  現金餘額 ▾    期間  今天 ▾

08/17 11:30  程式  簡嘉懋 B8   893 → 786    今日淨收付 −107（3 筆成交）
08/17 11:30  程式  簡嘉懋 E5   500 → 600    未實現損益 成交股數
08/17 14:02  人工  簡嘉懋 B8   786 → 900    ← 08/18 09:15 執行時偵測到，已轉手動
08/18 09:16  校正  簡嘉懋 B8   基準改為 900（08/18 起算，今日淨收付尚未計入）

篩出 3 筆／共 943 筆，最新的在最上面。
```

人工那一筆的時間標的是**偵測到的時間**，不是實際改的時間——程式沒在看，
只能事後從差異推回來，介面上明講這件事，不假裝知道。

多帳號跑幾天就是近千筆，一路捲下去等於找不到，所以照「某個人的某一格，今天
怎麼了」拆成交易人、項目、期間三層，都不選時維持全部列出：

- 項目清單跟著交易人走——選了人就只列那個人有的格子。清單順序是現金在
  最前面，其餘照股票分組（同一檔的股數排在成本前面），因為人是先想到股票
  才想到看哪一格。
- 期間只給「今天」與「近 7 天」——再細要多一個日曆元件跟一整套錯誤處理，
  換來的是沒人真的會用的功能。「今天」是每次重畫時現算的，不是開程式那一刻
  的日期，因為程式常開著過夜，跨過午夜還停在昨天會讓剛跑完的那批整批不見。
  時間欄壞掉的紀錄只有「全部」看得到，避免憑空生出一筆今天的異動。

切到歷程分頁時，交易人的篩選會自動跟著更新分頁走——切過去通常就是想看
剛才那位的歷程，不必再選一次人。

## 四、一次只更新一位交易人

一顆「更新」永遠做全部的話，帳號一多跑一輪要好幾分鐘；但盤中真正
在看的通常只有一位——剛下完單的那一位。

**範圍就是「按下去會動到誰」**：更新分頁的下拉選單跟左邊名單是同一個選擇的
兩個入口（點名單上一位，範圍跟著換；範圍換一位，名單與右邊也跟著換），按鈕上的
字就是這一節的重點——按下去會動到誰，直接寫在按鈕上：

它只管「更新」。「登入」2026/08/30 起一律登入全部，也搬到分頁列外面那條常駐列
去了——使用者確認過不會單獨只登入一組，而且要補登入某一組時，「更新（他）帳戶」
本來就會順便把他登進去（見 `fetch.collect`），沒有任何入口因此消失。

| 範圍                | 按鈕字樣            | 按下去做什麼                       |
| ------------------- | ------------------- | ---------------------------------- |
| 全部（預設）        | 更新全部帳戶        | 每一組都重新查、都寫               |
| 第 3 組（名字已知） | 更新（王小明）帳戶  | 只查他、只寫他那一頁               |
| 第 3 組（名字未知） | 更新（第 3 組）帳戶 | 一樣只做那一組，只是還說不出他是誰 |

名字要登入後才從網站 sessionStorage 拿得到，所以對照表是邊做邊長出來的
（模擬帳號例外，名字本來就寫在 `.env` 裡）。左邊名單是網頁資料長出來的，
沒讀過一輪之前是空的，所以一天的動線通常是：開盤前讀一次全部，之後整個
交易時段都在「點一位 → 更新（他）帳戶」。

**只更新一位要守住三件事**

1. **讀到的是補上去，不是整份換掉**——`records`／`sheet_data` 全部改成合併，
   否則清掉別人等於整份名單只剩一個人。
2. **寫入、落帳、現金基準只能碰這一輪讀到的那幾位**——`round_scope` 這條硬
   規則，`_collect_writes`、`_commit_round`、`_initialize`、`_on_written` 四處
   都照它。名單上別人
   也可能有「要寫」的格子，那是用上一輪的舊資料算出來的，順手寫出去就是拿
   舊資料改 Excel。現金「修改」按下去也一樣，範圍縮到眼前這一位。
3. **失敗原因掛在「第幾組」上，不是每讀一次就整串重來**——只更新一位時，
   別人上一輪沒完成的事不會因此解決，那些 ⚠ 要留到那一組自己再讀一次成功
   為止。

**換人不重登：把 cookie 換回去。** 整個瀏覽器只有一組 `JSESSIONID`，同時只
帶得動一個人的身分，但伺服器那邊 20 個帳號是各自獨立的 session，B 登入不會
殺掉 A 的。所以換人不是重新登入，是換一組 cookie：

1. 按「登入」時每一組登入完就把當下整份 cookie 收進 `store["jars"]`
2. 「更新（某人）」先把他那份 cookie 換回瀏覽器，回帳戶頁確認一下就直接查，
   不必跑登入流程、不必驗證碼
3. 確認不過（那組在伺服器上逾時了）才真的重登一次

換 cookie 換不回去的唯一原因是 session 逾時，那時候走的是原本就有的重登，
最壞結果等於沒有這個機制，不會更糟。

確認身分那一道不能省：分頁自己的 `sessionStorage` 不會因為 cookie 被換掉就
失效，只看它會誤判成「還活著」而拿到別人的資料。所以 `_revisit` 三道一起
看：還在帳戶頁、`sessionStorage` 有值、身分跟登入時記下的帳號代號相同；
`collect()` 裡「每一列的 `bhno`／`cseq` 要跟登入身分相符」照樣留著當最後一道。

**一組登入完就立刻抓完他的資料**，不是全部登入完才回頭一組一組抓——後者
查到的會是最後那一組的資料，因為前面幾組的分頁看起來都還活著，但 cookie
只有一組，伺服器只認 cookie。`collect()` 因此是「登入 → 抓完 → 換下一組」。
`ensure_logged_in()` 留給「登入」按鈕用（只登入、不抓資料），docstring 裡
寫明要抓資料不能用它；借空白分頁也只借「第一個而且還沒有人認領」的
（`spare_page()`），否則第二組會把第一組正在用的分頁導去登入頁。

## 五、現金：今日初始現金餘額，每天重新起算

方法一（初始餘額累加）下的算式：

```
現金餘額（B8） = 今日初始現金餘額 + 今日淨收付
                 ↑ 今天第一次登入      ↑ 網頁抄來的
                   時 Excel 上的 B8       不會錯
```

右邊那項不會錯，所以餘額不對的時候錯的一定是左邊那項。既然如此，它就該
一直看得到、一直改得動——現金那一條底下固定寫著這一行，旁邊一顆「修改」，
不必等程式判斷「現在該不該問」。

**一天只設一次基準。** 每次讀取，只要基準日還不是今天，就把 Excel 上的 B8
收成今天的起點；已經是今天就跳過，不會把今天的淨收付重複加進基準。當天要
重新起算只能靠「修改」這顆按鈕明講，不會漏跑就補不回來——不回頭算舊帳，
今天的 B8 就是今天的起點，跟昨天無關。

| 情況                         | 顯示                | 「修改」 |
| ---------------------------- | ------------------- | -------- |
| 還沒選到人（還沒讀網頁資料） | `—`                 | 灰       |
| 紀錄檔還沒有基準             | `(還沒設定)`        | 灰       |
| 正常                         | `1,234,567`         | 亮       |
| 剛按過修改、還沒落帳         | `1,234,567 → 5,000` | 亮       |
| 淨收付信不過（`blocked`）    | 照常顯示            | 灰＋理由 |

沒有網頁資料就不給改：新的 B8 是「開盤前 ＋ 今日淨收付」，沒有淨收付算不
出來。按下去就直接寫進 Excel 並落帳（算出來剛好等於原值也一樣要落帳，否則
下一次讀取會拿沒被修正的基準再算一次，今天的淨收付被加第二次）——跟其他
格子一樣一律覆蓋，沒有開關可以切成「只顯示建議值、Excel 由人自己改」那條路
（見 CLAUDE.md「改動前必看」）。

**容易出錯的情境：紀錄檔遺失後同一天重開**（誤刪、Excel 改檔名或搬資料夾、
換一台電腦）。這時 `baseline_date` 是 `None`，看起來像今天第一次登入，於是
已經含了今日淨收付的 B8 被當成起點，待會兒再加一次一遍。接住它的是畫面
本身而不是彈窗提醒：那個數字寫在現金餘額底下，跟「今日淨收付」上下並排，
起點被算成含了今天的成交會明顯偏高——看到不對就按「修改」。真正會走到這顆
按鈕的路只有一條：**人自己在盤中改過 B8**，他改進去的是「現在正確的餘額」，
已經含了今天的成交，照抄成開盤前就等於把淨收付算進起點裡重複加一次。三個
位置各講一段，愈靠近出錯的當下講得愈細：

| 位置                 | 說什麼                                                         |
| -------------------- | ---------------------------------------------------------------- |
| 「修改」旁邊那行灰字 | 這個數字＝今天第一次登入時的EXCEL現金餘額B8                    |
| 提醒框最後一行       | 今天別改檔名、別自己改 B8；真改了就用「修改」補開盤前的金額    |
| 對話框（按下去之後） | 開盤前的定義、`B8 − 今日淨收付` 算好擺著附「帶入」、填錯的後果 |

對話框裡那一行「B8 已經含了今天的成交的話，開盤前是 X」是最實際的一項：
需要按這顆按鈕的人手上有的正好是 B8，缺的正好是那個減法，算好擺著再給一顆
「帶入」，比請他自己心算一次更可靠。提醒框那一句排在最後一行，因為那個框
只有五行高又沒有捲軸，常駐的字排在前面會把當天真正的警告推出視線。

方法二（銀行餘額推算）不用這一套：用銀行餘額推算的日子，「修改」整顆按鈕
藏起來，見 [[現金餘額兩種算法]]。

## 六、讀取時設定今日現金基準

第一次用、或任何一格沒被程式管過，都要有個起點。做法是：**開 Excel → 按
登入 → 按讀取 → 這一輪讀到 Excel 現值的當下（`_on_fetched`，這一輪還沒被
寫入動過），現金餘額直接被收成今天的起點**，不會另外跳精靈問「這個數字
含不含今天的淨收付」——時間點選在 Excel 現值剛讀回來、真正把淨收付往上
加之前，答案自然就是「不含」：

```
讀取（當天第一次）  Excel 上的數字 = 今天買賣之前的狀態  →  直接當基準，沒有猜的空間
同一輪，緊接著      今天成交了什麼（網頁抓到的淨收付）  →  往基準上加
寫入                基準 + 今天的淨收付                  →  寫回 B8
```

| 動作                       | 誰觸發         | 現金基準怎麼定                |
| -------------------------- | -------------- | ------------------------------ |
| 讀取（當天第一次，那一組） | 按「更新」     | = Excel 的 B8，今天的流水記 0 |
| 讀取（當天已經設過基準）   | 按「更新」     | 不變，跳過                    |
| 改今日初始現金餘額         | 人自己按「修改」 | = 人填的數字 − 今天的淨收付   |

登入本身不碰現金基準，只用來取得那一組的名字（見第四節）。持股（股數／
成本）也不用問，每次讀取都直接以網頁值覆蓋，不分第一次或第 N 次，沒有
「先接管」這一步（見 CLAUDE.md「改動前必看」）。

## 七、既有的安全機制

- 每一列都驗 `bhno`／`cseq`，擋掉多帳號時 session 被頂掉抓到別人資料。
- 網頁沒有的股票**不自動清空**，只提醒。
- 「未實現損益顯示今天有成交，但淨收付是 0」（收盤結帳後查不到）要擋，但
  只擋現金那一列，持股照樣可以寫，不必整份中止。
- Excel 已經開著就接上那個實例，直接寫、直接存檔，不留 Ctrl+S 那一步——
  紀錄檔在寫入成功後就記成寫過了，人沒按 Ctrl+S 會讓帳本跟檔案分家，畫面上
  不會有徵兆，這點要記住。

## 八、模擬多帳號（測試用）

手上帳號數量有限，但實際要跑的是多組。真的那一組照原本流程登入，其餘在
**同一個瀏覽器**各開一個分頁，放一頁程式自己畫的假網頁（`window.__SIM__`），
`fetch.py` 對假帳號改成呼叫它而不是打 `MainController`，回傳形狀跟真 API
一樣，所以 planner／ledger／excel_io／ui 都不知道有假帳號這件事。

| 檔案                     | 職責                                                |
| ------------------------ | ---------------------------------------------------- |
| `dev_tools/simulate.py`  | 假帳號清單、隨機資料、假網頁 HTML、開分頁與讀回資料 |
| `dev_tools/sim_excel.py` | 在 Excel 補上／移除模擬分頁（交易人A～S）           |
| `.env`                   | `SIMULATE_ACCOUNTS=N`，沒設就等於整套模擬不存在      |

開起來的順序：

1. `python dev_tools/sim_excel.py --write`（複製 N 個分頁，範本就是真分頁）
2. `.env` 設 `SIMULATE_ACCOUNTS=N`
3. `python ui.py`——登入、讀取，跟平常一樣操作（現金基準在讀取時自動設定，見第六節）

隨機值的種子是（帳號名 + 日期），同一天重讀網頁資料數字不變，剛好可以驗證
「同一天重跑不會重複扣現金」。要換數字就按假網頁上的「重新隨機」；股數、
成交均價、市價、當日成交都是輸入格，改完立刻生效，可以自己擺出特定情境
（某檔股數改成 0 = 網頁庫存沒這檔）。

**測不到的**：只有 1 個分頁真的在跟網站講話，所以「多帳號共用 JSESSIONID
會互踢」這個真正的風險模擬不出來，那只有真的多組帳號才驗得出來。

**收乾淨**：`python dev_tools/sim_excel.py --remove --write` 會刪掉模擬分頁、
從紀錄檔移除對應分頁、把歷程檔裡的模擬紀錄濾掉。模擬分頁是加在正在用的那份
Excel 裡，紀錄檔又是跟著檔名走的，所以清理這件事一定要程式做，手工清不乾淨。

## 九、下單分頁：五類功能怎麼擺

規劃文件（`docs/自動下單與半自動下單規劃.pptx.txt`）把功能分成五類。**分類是「人怎麼
想」，不等於「畫面怎麼切」**——這五類不對應五個分頁：

| 規劃文件的分類 | 骨架                                             | 放哪裡                                       |
| ---            | ---                                              | ---                                          |
| 一、買賣股票   | 選帳戶 → 選股票 → 設定 → 執行預覽 → 依序送出 | 下單分頁，作業之一                           |
| 二、出清股票   | 同上                                             | 下單分頁，作業之一（＝2026/08 已實作的那個） |
| 三、全持股交易 | 同上，只是不必選股票                             | 下單分頁，作業之一                           |
| 四、取消掛單   | 看現在在外面的委託 → 整批取消                   | 掛單分頁（第十節）                           |
| 五、列出掛單   | 就是四的上半部                                   | 掛單分頁（第十節）                           |
| 五、強制中斷   | 隨時要按得到                                     | 底部狀態列，跨分頁常駐（第十節）             |

一、二、三 的差別只有兩件事：**第二列要填什麼**、**張數與價格從哪來**。其餘（執行
執行帳戶那一格、執行預覽那張表、依序執行、多輪、自動送出）逐字相同——拆成三個分頁等於把這
一整套複製三份，而且「現在在跑什麼」變成三個地方要看。所以往上長一層「作業」，不是
往旁邊長三個分頁。

四、五 形狀完全不同：沒有股票要選、沒有預覽要看，是對「已經送出去的委託」動作，
所以才拆出去。

`M18` 是「加買股數」的表頭，`M19:M28` 才是 10 檔的值。列的算法是巨集裡的
`stock_limit + 9`～`stock_limit * 2 + 8`，`stock_limit` 改了每一個位置都會跟著移
——所以程式這邊**只留一個 `excel_io.STOCK_LIMIT`**，`HOLDING_ROWS`、`PLAN_ROWS`、
今年報酬率那一列全部由它推（2026/09/02 改，原本各寫死一次）。要換格式就只改那一個
數字，不要回頭把哪一個範圍寫死。

**錨點檢查：開檔就驗 A22**（2026/09/02 使用者要求「開啟EXCEL的時候可以先檢查錨點，
今年報酬率如果不在 A22 那開錯別的格式」）。`excel_io.anchor_ok` 讀一格判斷一個分頁
是不是這一版；`layout_problem` 在**一個看得見的分頁都對不上**時回一句說明，
`ui_background.check_excel_layout` 在 Excel 接上的那一刻背景驗一次，對不上就跳錯誤
視窗、把 `excel_open` 扳回 False，整支程式的 Excel 功能停在那裡（旗標
`excel_layout_problem` 也要在 `_poll_excel` 那邊看，不然三秒後它會照「檔案開著」把
狀態扳回來）。

為什麼是擋住不是警告：5 檔那一版的今年報酬率在 A17，它的持股只到 D8、下單試算在
M14:N18——**每一個程式會讀寫的位置都不一樣**。一格對得上其餘就都對得上，對不上就
整份不能用。同一天早上曾經為了相容 B17／B22／B32 三種格式改成掃 A 欄找標籤，定案
之後那條路拿掉了：相容多種格式本身就是危險的來源，讀得到報酬率只會讓一份每個位置
都對不上的表看起來像可以用。

也因為有這道檢查，「哪些分頁算數」的判斷跟著換成錨點（`list_account_sheets`）：
看得見 ＋ A22 對得上就是一位交易人。順便把「一頁全空的新交易人」收進來了——他一格
股票都還沒填，舊那套「報酬率讀得到 或 D 欄有股號」會把他整個漏掉。

「指定股票」的候選清單來自**第一個分頁的 D4~D13**（`excel_io.read_stock_list`），不是
勾選帳戶手上有什麼：要選的是「這一輪要動哪幾檔」，拿其中一位的清單當候選會讓別人
多出來的那幾檔選不到。勾選帳戶讀到的股票再併進去當補充。

四支可呼叫的巨集，全都在 `Module1`：

| 巨集         | 做什麼                                                      | 平常誰按                                                         |
| ------------ | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| `更新股價`   | 對 D4:D13 每一檔打一次 Yahoo 報價 API，寫進 I4:I13，A1 填日期 | Excel 上的「更新」鈕；程式的「自動更新股價」與盤中的「讀取試算」 |
| `自動計算`   | 依 M4:M13 目標比重反覆試算，結果寫進 M19:N28                 | 人（2026/09/02 起程式不按，見 9.3）                              |
| `初始化下單` | M19:M28 ← O4:O13、N19:N28 ← I4:I13                           | 人（2026/08/31 起程式不再用，見 9.7 第 4 步）                    |
| `清空下單`   | 清掉 M19:N28                                                 | 人（程式從來沒用過這支）                                         |

第二列是**那個作業自己的設定**，圖上畫的是出清股票那一版；買賣股票只有 `單位`，

**`[執行 更新→自動計算]` 已經拿掉（2026/09/02 使用者要求）。** 它原本站在「指定股票」

人自己按就好**——程式這一顆只是同一件事的第二個入口。一輪的操作因此變成：選帳戶 →
（自己在 Excel 上按更新／自動計算）→ 讀取試算 → 挑股票。

**這兩支巨集程式要跑的場合是「多輪執行時自己跑」（勾了才跑），不是人按一顆按鈕**
（2026/09/02 使用者補充）——手動那條路 Excel 上本來就有兩顆鈕，程式再放一顆只是同一件
事的第二個入口；程式該做的是人不在旁邊的那一種：一輪跑完自動重算再排下一輪。

現況跟那句話還有兩段差距，記在這裡免得下次被當成已經做好了：多輪迴圈只跑「更新股價」
（`ui_order_exec._order_price_refresh_worker` 的 `run_macro`），沒跑「自動計算」；而且
「多輪直到出清」「自動更新股價」限**價格是追價算出來的那兩種**（出清・整張盤中、
出清・零股，見 `ui_order._order_uses_excel_price`），買賣股票與出清・盤前都沒有多輪。
所以 `自動計算` 現在是零個自動呼叫者。

（2026/09/03 補：多輪之間現在會多做一件事——完整同步，見 9.9；2026/09/04 起第 1 輪
之前也跑一次。那一步跑的是更新分頁那條路，不是巨集，所以上面「沒跑自動計算」這句話
還是成立的。）

連帶收掉的：`ui_order.run_auto_calc`／`_order_auto_calc_worker`／`_on_order_auto_calc`、
`ui_background` 那兩處佇列接線。`excel_io.run_auto_calc_macro()` **留著沒刪**——全持股
交易那一版的 `[跑自動計算]`（9.5）與上面那個多輪自動跑的方向都還要用它。

執行帳戶、指定股票、執行預覽、依序執行按鈕列、多輪那一列、狀態文字**三個作業共用
同一份 widget，不複製**。會變的只有第一列的「作業」選了誰、第二列整列換掉、指定股票
那一格的內容。

**帳戶那一格前後換過五種形狀，第五種是現況**（每一種都是使用者指定）：checkbox 多選
→ 第一列的單選下拉 → 左欄的 radiobutton 清單 → 單選 Treeview（09/01）→ **左欄的
兩欄 Treeview（帳戶／今年報酬率），列首自己畫 ☐／☑、可以勾好幾位，上面兩顆
「全選」「全不選」**（09/02，見 9.3 第 5 點）。用 Treeview 是為了**跟更新分頁的交易人
名單用同一個元件**——兩份看起來像同一種東西的名單，用兩種不同元件會讓人以為互動
方式不一樣。

Treeview 在這個專案本來是「不得已才用」（設計原則第十三節：畫不出格線、欄寬不會照
內容自動調），這裡的不得已就是一致性。09/01 那版還額外付了「`<<TreeviewSelect>>`
分不出使用者換人與程式重畫清單」的成本，09/02 改成勾選之後那筆成本消失了：勾選狀態
自己存一份（`order_checked`），☐／☑ 只是文字，`selectmode="none"` 讓「被選取」這個
狀態整個不存在。

**這一格整個是 Excel 那一頭的答案，開檔就有、不必等登入**（2026/09/01 使用者要求）：
一份持股管理表的分頁本來就是一位交易人一頁，名字與 B22 一起讀回來（`excel_io.
list_account_sheets`）。登入只跟「送得出委託」有關——真的按下「開始買賣」時才需要
那個人的 cookie，那時對不到帳號會擋下來。

哪些分頁算數：看得見的、而且**錨點對得上**（A22 ＝「今年報酬率」，見 9.1）。純說明頁
沒有那一格就不會混進來。不用分頁名稱猜（名字就是人名，猜不出規則），也不預設「所有
分頁都是交易人」。09/02 之前是「報酬率讀得到 或 D 欄有股號」那種兩選一的特徵判斷，
換成錨點之後順便把「一頁全空的新交易人」也收進來了——他一格股票都還沒填，舊那套
會把他整個漏掉，人在畫面上找不到他。

這一格最上面是「讀取ＯＯ持股」，下面是兩顆「全選」「全不選」（09/02，見 9.3 第 5
點）。原本擺在這裡的「讀取持股與報酬率」09/01 搬到右邊「指定股票」那一列改名
「讀取持股」——報酬率開檔就自己進來了，名字裡那一半不再是它的工作。09/02 下午
使用者又把它拆成兩顆：只讀**第一個分頁**候選清單、跟勾了誰無關的那一半改名
「讀取ＯＯ持股」（ＯＯ＝實際讀到的分頁名）搬回這裡，因為它跟「執行帳戶」清單一樣
是開檔就有的答案；真正要讀勾起來那幾位的持股、股價、試算，留在右邊「指定股票」
那一列，改名「讀取試算」（見下一段的表格與 9.3）。

狀態文字接在**第二列**後面（買賣股票就是「零股」右邊，2026/09/01 使用者指定）。
它不在那三個互換的 Frame 裡，而是跟它們一樣掛在外層的 `job_bar` 上、佔右邊那一格：
三個作業共用同一份狀態，塞進去就要複製三份，切一次作業還得把話重抄一次。

位置同一天換過三次：第一列的尾巴 → 自己一整列 → 第二列。自己一列是為了讓路給當時
排在第一列的帳戶選單與讀取按鈕，那兩個都搬進左欄之後就不必了；併回第二列還省下一
整列高度，那高度本來是從執行預覽身上扣的。

**三個面板怎麼擺是量出來的**（2026/08/31 定案，09/01 帳戶回到左欄後照舊）：

| 面板     | 最大需求                     | 給它什麼                             |
| ---      | ---                          | ---                                  |
| 執行帳戶 | 20 組 × 一列 ≈ 480 像素     | 獨佔左欄，寬度鎖 260                 |
| 指定股票 | 最多 10 檔（`stock_limit`）  | 右欄上緣，**最多三檔高**，超過用捲軸 |
| 執行預覽 | 勾幾位 × 幾檔（跳過的也列）  | 右欄剩下的全部                       |

執行預覽在 09/02 又變回會爆的那一個：一輪可以勾好幾位，20 位 × 10 檔就是 200 列
（跳過的也照列）。這是它拿走右欄所有剩餘高度、而「指定股票」被壓在三檔高的理由。

- **帳戶剛好吃滿一整欄，所以獨佔左欄。** 20 組一列疊一列約 480 像素，再多也不會
  （帳號數有上限）。寬度鎖 260，比 08/31 那版 checkbox 的 200 寬——多了順位號碼、
  多了「今年報酬率」那一欄，上面還多了那顆讀取按鈕。實測（11 級字）：整格 286 像素、
  兩欄 168＋88、按鈕 146，剛好塞得下。

- **指定股票的高度跟著實際檔數長，最多三檔**（使用者指定），空著的時候只留一檔高。
  它跟預覽上下疊，佔的每一像素都是從預覽身上扣的，而預覽是唯一會爆的那個
  （跳過的列也照列，見 `orders.plan_stock_orders`）。
- **一檔一列、一行排完**（2026/08/31 改，原本分兩行）。分兩行是為了 300 像素寬的
  左欄設計的——一行塞不下「名稱＋比重＋價格＋移除」。搬到右欄有一千多像素寬之後
  那個前提不成立了，而且分兩行等於把橫向那一大片空白換成縱向的浪費：一檔 70 像素
  降到 37，三檔的指定股票整格從 300 降到 177，省下的 120 全部流給預覽。每一列自己
  是一個 Frame（pack 疊起來，移除中間一列不會留空位），列內部用 grid 且每列共用同
  一組欄 minsize，所以「移除」「比重」「價格」上下對齊成一張小表。
- 中間那根分隔可以拖：會長的是預覽，指定股票有上限，彈性留給預覽。
- **「順序」欄現在是清單上的號碼**（＝報酬率由低到高的第幾位），不是「這一輪第幾個
  執行」——一輪只有一位，那個意思下的號碼永遠是 1，一整欄的 1 只是噪音。報酬率讀不到
  的那位寫「－」。
- **執行預覽的欄位順序**是「會送出什麼」在左（順序／帳戶／買賣／股票／張數／價格）、
  「為什麼是這樣」在右（持股／出清進度／備註）。持股是算張數的依據、不是會送出去的
  東西，所以跟備註同一區，不夾在股票與張數中間（2026/08/31 使用者指定）。改順序時
  `ui_layout` 的 `columns` 與 `ui_order._render_order_preview` 的 values tuple 要
  一起改——Treeview 照位置對欄位，只改一邊不會報錯，只是每一欄顯示別欄的值。
  「出清進度」2026/09/05 加在持股後面，只有出清股票這個作業看得到（`displaycolumns`
  切掉／放回），見 9.10。

**這個排法吃視窗高度。** 指定股票滿三檔約 177 像素，預覽底下的動作列、多輪那一列與
狀態文字又是固定的約 150 像素，都從同一個高度裡扣。2026/08/31 實測（11 級字，指定
股票已經是一行一檔的版本；三檔以上高度就不再變了，所以只有一欄數字）：

| 視窗高 | 執行預覽看得到 |
| ---    | ---            |
| 800    | 5 列           |
| 900    | 9 列           |
| 960    | 11 列          |

所以預設視窗高從 `wide(720)` 加到 `wide(860)`（`ui_layout._build`）。`.env` 的
`UI_HEIGHT` 蓋得過這個預設——**設了就是設了**，那台機器上的預覽有幾列由那個數字決定
（這台開發機是 960）。

### 9.3 「作業」那一列與它下面那一列

第一列（作業）固定三選一，第二列是**那個作業自己的設定**：

| 作業            | 第二列                                              | 指定股票那一格                             | 張數／價格哪來                       |
| ---             | ---                                                 | ---                                        | ---                                  |
| 買賣股票        | 單位 整張／零股                                     | 「讀取試算」＋股票下拉＋「新增」；下面是清單，顯示這一檔在勾選帳戶裡的試算彙總（唯讀） | Excel 下單試算 M19:N28               |
| 出清股票・整張  | 單位　＋ 時機 盤前／盤中　＋ 追價檔數（預設 2）     | 股票清單 ＋ 比重（可填）（＋盤前才有價格） | 比重×持股；價格＝人填或追價         |
| 出清股票・零股  | 單位　＋ 時機（**鎖在盤中**）　＋ 追價檔數（預設 3）| 股票清單，比重那一格寫「全部零股」（唯讀） | 持股的零股那一段；價格＝追價         |
| 全持股交易      | 整張追價 [2] 檔　零股追價 [3] 檔　＋ `[跑自動計算]` | 整格唯讀，寫「全部持股，不必指定」         | 自動計算的 M×N 當個股資金預算／需求 |

出清那兩個單位差的不只是量怎麼算，是**整條執行路徑**（見 9.8），所以切單位跟切
作業一樣要把股票清單清空重選（9.3 第 1 點那條規矩的同一個理由：兩邊的列形狀不
一樣，整張有「比重」輸入框、零股沒有）。追價檔數也跟著換成那個單位的預設值——
規劃文件各自寫在自己那一節（整張 2 檔、零股 3 檔），停在另一個單位的預設值上會
讓人以為那就是文件講的數字。

**巨集按鈕不跳確認框**（2026/08/31 使用者要求）。它只動 Excel 的格子，而且一輪要按好
幾次，每次都要按掉一個只是重述按鈕名字的視窗太吵；「按下去了、正在跑什麼」改由**底部
常駐狀態列**講（`更新→自動計算 執行中……（李大華）`，跑完換成跑了幾個分頁）。這條
只適用這裡——10.3 那三顆取消掛單的按鈕**還是要跳確認**，那動的是真實委託，不是 Excel
格子。唯一那顆巨集按鈕 2026/09/02 拿掉了（見 9.2），這條規矩留著給全持股交易的
`[跑自動計算]`：它接上的時候照這樣做，不要又加一個確認框。

那句話的刪節號是中文的六點「……」，**只有這一句**：程式其他地方的等待訊息（`讀取中…`、
`登入／填單中…`、`處理中…`…）維持單點「…」，2026/08/31 問過使用者，答覆是先不動。
不要為了統一去掃它們。（那句話跟著按鈕一起下線了，規矩同上，留給下一個用得到的人。）

五條實作規則：

1. **切作業＝清空股票清單重選。** 跟現在切盤前／盤中、切買賣同一條規矩（見
   `ui_order._on_order_mode_changed`）。「比重」在出清是人填的設定、在買賣股票根本
   不存在，沿用舊列會讓人以為兩邊是同一個數字。
2. **第二列換版面用 `grid_remove()`，不要用 `pack_forget()`。** `grid_remove` 記得住
   格子位置，再 `grid()` 回來會回到原位——`ui_layout.py` 裡「不如留著 disabled」那
   幾段取捨（`order_ticks_entry`、`order_quotes_button`）就是被 `pack_forget` 會跑到
   列尾這件事逼出來的，換成 grid 就沒這個問題。整列預先建三個 Frame，切作業時
   `grid_remove` 舊的、`grid` 新的。
3. **「賣／買」那組單選鈕整個拿掉。** 出清永遠是賣；買賣股票的方向由 M19:M28 的正負
   逐檔決定；全持股交易也是算出來的。三個作業沒有一個需要人選方向——方向只該出現
   在執行預覽的「買賣」欄跟紅綠底色（`buy`／`sell` tag 已經有了）。目前 `買` 是
   disabled 掛在那，順勢收掉。`orders.SIDE_BUY`／`SIDE_SELL` 保留，只是改成算出來的。
4. **「盤前／盤中」降一級**，變成出清作業自己的設定，不再是整個分頁的頂層開關——它
   對買賣股票、全持股交易都沒有意義。
5. **執行帳戶可以勾好幾位，一次跑完**（2026/09/02 使用者決定，**推翻 09/01 那版
   「一次一位」**）。清單還是左欄那張表（帳戶／今年報酬率），只是每一列前面多一個
   ☐／☑，上面多兩顆「全選」「全不選」。使用者的原話是「買賣股票加上選帳戶這個過程
   會太慢，變成和手動下單一樣，直接選股票就好……程式去執行全部帳戶的下單試算的
   內容」，操作因此變成 **勾帳戶 → 選股票 → 執行**。

   為什麼 09/01 那版站不住：那天的理由是「使用者的操作本來就是一次一位」，但那是
   **出清股票**的節奏（比重、價格是人一位一位斟酌的）。買賣股票的張數與價格全部
   來自各帳戶自己那一頁的下單試算，人一個數字都不必填，逐位重複「選人 → 讀取 →
   加股票 → 送出」等於把程式當成手動下單的遙控器。

   勾選狀態是 `ui_order.order_checked`（一份分頁名的集合），畫面上的 ☐／☑ 只是
   #0 欄文字的第一個字元，不是 Treeview 的 selection（`selectmode="none"`）——
   09/01 那版要擋 `<<TreeviewSelect>>` 的那兩道 guard 因此整個不需要了（程式自己
   重畫清單不會誤觸勾選）。剩下的一道還在：鎖住的時候（Excel 正在被動、或這一輪
   委託還沒跑完）點下去直接不理，因為 Treeview 的 disabled 擋不住自己綁的
   `<Button-1>`。

   下面這四點是 09/01 寫的，**除了第一點以外現在還算數**：

   - **規格那句「報酬率低的先執行」又回到執行順序上**（09/01～09/02 之間它只是
     「建議的處理順序」）。清單每一列前面的號碼就是 `orders.order_accounts` 排出來的
     順位，`ui_order._order_execution_accounts` 照那個順序把勾起來的人排成這一輪的
     queue，號碼小的先送。B22 讀不到的排最後、號碼寫「－」，但**照樣勾得到**——他們
     之間的先後就照活頁簿裡分頁本來的順序，不假裝算得出一個順位。
   - **改勾選＝清空持股、試算、報價，但股票清單留著**（`_clear_order_round`）：
     每一項跟「是誰」綁在一起的資料都作廢，因為勾進來的新人一格都還沒讀；股票清單
     是「這一輪要動哪幾檔」，跟勾了誰無關。留著舊試算不清的話，新勾的那位會照著
     別人的數字算出一列「看起來可以送」的委託——不會報錯，只會拿 A 的數字算 B 的
     張數。（換 Excel 檔那條路連股票清單一起清，`keep_stocks=False`。）
   - **「讀取試算」只讀勾起來的那幾位**（2026/09/01 之前叫「讀取持股與報酬率」，
     09/01～09/02 上午是「只讀選中那一位」，09/02 下午原本統稱「讀取持股」的按鈕
     又拆成兩顆：純讀第一個分頁候選清單、跟勾了誰無關的那一半獨立成「讀取ＯＯ持股」
     搬去左欄「執行帳戶」；這裡留下的、真正要讀勾選帳戶資料的一半改名「讀取試算」
     ——使用者原話「讀取持股不用勾選執行帳號，因為都用EXCEL第一個分頁取得持股」）。
     這就是 C2「盤中讀取太慢」的解法：以前一次讀 20 個分頁，盤中每頁還各跑一次
     「更新股價」巨集（一頁 10 檔＝10 次 Yahoo HTTP，20 頁就是那 100 次），而沒勾的
     那幾頁這一輪一格都用不到。要跑全部就自己按「全選」——那是人的決定，不是程式
     偷偷替他決定（`_order_sheets()` 也刻意**不**把「沒勾」解釋成「全部」）。
   - **勾了但還沒讀的那幾位，執行預覽要講得出來**：他們的每一列寫「還沒讀取試算，
     略過」（`orders.REASON_NOT_LOADED`，靠 `plan_trade_orders` 的 `loaded_sheets`
     分辨），提示列再整批講一次。不分開講的話，那幾列會跟「下單試算是空的」長得
     一模一樣，人會跑去 Excel 按自動計算，而其實只要按「讀取試算」。
   - **某一位沒有選中的那一檔就略過**（`orders.REASON_NO_STOCK`，2026/09/02 使用者
     指定）：一次跑全部帳戶本來就會遇到有人沒這一檔，那是常態不是錯誤。跟「有這一檔
     但試算是 0」分兩句寫，人才看得出「是我選錯股票」還是「這一輪不必動它」。
   - **清單本身（有誰、報酬率、排序）來自 Excel 分頁，開檔就有**：
     `ui_order.refresh_order_accounts` 一位只讀兩格（A22 錨點、B22 報酬率），
     不跑巨集、不讀 D/E/F/I/M，
     在兩個時刻自動跑——Excel 接上的那一刻、切到下單分頁。每次都真的重讀一遍，不記
     「掃過了沒」：一位兩次 COM 往返，20 位也只是幾十毫秒，換來的是「人在 Excel
     裡加了一頁、改了報酬率，切個分頁回來就對了」。讀不到不跳視窗（人沒按任何按鈕，
     是背景自己去的），那位排最後、報酬率欄寫「讀不到」就是了。

   確認框第一句是**帳戶：甲、乙、丙**——列的是「queue 裡真的有東西」的那幾位，不是
   勾了誰（勾了但沒這一檔、或試算是空的，整位都會被略過，寫進來只會讓人以為那一位
   也要下單）。超過 6 位只報數字：那個框是要人看完再按的，一行 20 個名字沒有人會
   真的讀，逐位確認的地方本來就是執行預覽那張表。

執行按鈕的字照第四節那條原則跟著作業走，**按下去會動到什麼寫在按鈕上**：
`開始買賣（整張）`／`開始出清（整張・盤中）`／`開始全持股交易`。

### 9.4 整張／零股是同一個數字拆兩段

M19:M28 是**股數**不是張數（巨集全程以股為單位運算，最後還有「加 1 股／減 1 股」的
零錢處理）。所以規劃文件把買賣股票拆成整張、零股兩節，不是兩份資料，是同一個數字
拆兩段：

```
M14 = 2,350 股  ->  整張 2 張（2,000 股） + 零股 350 股
M15 =  -800 股  ->  整張 0 張             + 零股 賣 800 股
```

整張＝`int(abs(n) / 1000)` 帶回原本的正負號（**往零的方向取整，不是四捨五入、也不是
Python `//` 對負數往下取整**）；零股＝`abs(n) - 整張 * 1000` 帶回正負號。「單位」那個
選擇決定這一輪送哪一段，另一段不送。

執行預覽那一欄（2026/09/01 定案）：**欄名跟著單位換（`張數`／`股數`），格子裡只放
一個純數字**——沒有單位，也沒有拆法。沒送出去的另一半一律在「備註」欄講，兩個方向
各一句：選整張是「另有零股 847 股，這一輪不送」，選零股是「另有整張 2 張，這一輪
不送」。

這一欄走過三個版本：原本是 `2 張（餘 350 股）`；08/31 把餘數移進備註（使用者覺得
括號裡那段是雜訊）；09/01 再把單位移到欄名（`847 股` -> `847`）。出清那兩個作業本來
就是純數字，這下三個作業同一個形狀。欄位鍵一直是 `lots`，換的只是欄名，換的地方在
`ui_order._recompute_order_preview`（畫面上任何設定變動的唯一入口，走哪條路都不會漏）。

**2026/08/31：零股那半段的送單路徑接好了，只差一個值。** 算的那一半本來就做完了
（`orders.split_lots`／`plan_trade_orders(unit=...)`），這次補的是「送出去」那一段：

| 檔案               | 這次補的東西                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `order_fill.py`    | `TAB1_LOT`／`TAB1_ODD` 兩個交易盤別常數；`open_order_form(odd=)` 選完讀回來核對有沒有真的切過去；`fill_order(odd=)` 送出前用 `_check_qty` 量數量的單位 |
| `orders.py`        | 每一列多帶一個 `unit`；`UNITS_READY` 從一個共用的 tuple 改成「一個作業一組」的 dict，加 `unit_ready(job, unit)`                                        |
| `ui_order_exec.py` | `_order_fill_job` 照那一列自己帶的 `unit` 決定 `odd`，跟 `side`／`bs_flag` 同一條路（吃凍結好的 queue，不回頭問畫面）                                  |
| `ui_layout.py`     | 單選鈕問的是「這個作業的這個單位」，不是一個三個作業共用的清單                                                                                         |
| `ui_order.py`      | 切作業時把在新作業還沒接上的單位扳回整張；切單位會重算執行預覽（原本只換按鈕上的字）                                                                   |

**2026/09/01 09:18 盤中把最後那個值查回來了**（`recon_order_form.py`，報告在
`偵察資料60901_0918_下單表單選項.txt`），零股從這天起選得到、也送得出去。
交易盤別（`.tab1`）一共四個選項：

| `.tab1` | 選項     | 程式用在哪                             |
| ------- | -------- | -------------------------------------- |
| `'1'`   | 整股     | 買賣股票・整張、出清股票（`TAB1_LOT`） |
| `'2'`   | 盤後     | 沒用（13:30 之後那場整股定價交易）     |
| `'5'`   | 盤中零股 | 買賣股票・零股（`TAB1_ODD`）           |
| `'3'`   | 盤後零股 | 沒用（13:40~14:30 那場零股集合競價）   |

零股取 `'5'`（盤中零股）不是 `'3'`（盤後零股）：`'5'` 對到整股的 `'1'`，是同一段連續
交易時間裡的另一半，規劃文件的兩個零股流程（買賣股票照試算送、出清零股「全部掛賣單、
20 秒後取消」）講的都是這一段。`'3'` 那一場對到的是 `'2'`（盤後），整張那半邊也沒在
用——真要做盤後那一場的話，是多一個「時機」設定，不是把 `TAB1_ODD` 改掉。

同一份報告一次確認了另外兩個原本只是假設的東西，兩個都對，所以沒有東西要改：

- 零股的數量欄旁邊寫的是「股」（整股寫「張」）——`_check_qty` 零股只收 1~999 成立。
- 零股的委託別只剩 `'R'`（ROD）、交易別只剩 `'0'`（現股）；IOC／FOK 是整股才有的。
  買賣股票整批固定 ROD，本來就不受影響；但「出清・零股」那套「全部掛賣單、20 秒後
  全部取消」現在有了正式理由——零股根本沒有 IOC 可用，只能掛了再撤。`fill_order`
  因此多一道擋門：零股帶著非 `R` 的委託別直接擋下來，不然 `select_option` 只會丟
  一句「找不到這個選項」，看不出真正的原因。

還沒人看過的只剩一件：那份報告是 09:18 **盤中**倒的，四個盤別當時都切得過去，
**盤前（09:00 以前）零股切不切得過去沒試過**。`open_order_form` 選完會把值讀回來
核對，真的沒切過去就擋下來不送——不會用整股的單位把零股的量送出去。

### 9.5 全持股交易要兩步，不能一顆按鈕直通

`自動計算` 會**暫時改寫 E/F/B8 再還原**（見 9.6 第 3 點），而且它算出來的 M19:N28
是「這一輪打算做什麼」的完整計畫。所以：

```
[跑自動計算]  ->  讀回 M19:N28  ->  畫進執行預覽  ->  人看過  ->  [開始全持股交易]
```

不是一顆按鈕直通下單。這正好就是執行預覽本來的角色（「看得到會發生什麼事」），不必
新發明東西。

送單策略照規劃文件：整張用 IOC、剩餘資金下零股、20 秒後取消全部零股單；收斂條件是
成本比重與目標比重差 < 0.1%（＝巨集裡那個 `0.001`）或自動計算結果空白。

### 9.6 三個坑

**1. 巨集只認 ActiveSheet——一頁一次，不能整批一次。**

`更新股價`、`自動計算` 都寫在標準模組裡，用的是無限定的 `Range("D" & i)`，VBA 解析成
`ActiveSheet`。2026/08/29 之前 `run_update_price_macro` 是整批只呼叫一次，20 個帳戶
只有使用者上次剛好停在的那一頁拿到新價格，其餘讀回來是舊的 I4:I13——**不報錯、不少
一欄、看起來完全正常**，而盤中追價的基準價就建立在這上面。

已修：`excel_io.run_update_price_macro(excel, sheet)` 收分頁參數、自己 `Activate()`，
呼叫端包 `excel_io.keep_active_sheet(book)` 把使用者原本停的那一頁還回去。同一天用
複製檔（兩個分頁、I4:I13 清空）實測過：整批一次 → 只有 ActiveSheet 拿到 5 個價格、另
一頁全空；一頁一次 → 兩頁都拿到。**之後接 `自動計算` 照同一個做法，別再寫成整批一
次。**

**2. 兩支巨集都會跳 MsgBox，而 `Application.Run` 會被卡住。**

九個 MsgBox，一個在 `更新股價`、八個在 `自動計算` 的「檢查輸入錯誤」那一段：

| #   | 巨集       | 觸發條件                                             | 訊息                       | 單一分頁最多跳幾次               |
| --- | ---        | ---                                                  | ---                        | ---                              |
| 1   | `更新股價` | regex 在 Yahoo 的回應裡找不到 `"price":{"raw":"…"}` | `<代號> 股價更新失敗`      | 5（迴圈內，每檔一次，沒有 Exit） |
| 2   | `自動計算` | `CountA(D4:D13) = 0`，完全沒填股票                    | 尚未輸入任何股票！         | 1（迴圈外）                      |
| 3   | `自動計算` | 有股號、但 `I` 欄是空的                              | 股價尚未輸入完全！         | 5（迴圈內，每列一次，沒有 Exit） |
| 4   | `自動計算` | 沒股號、但 `E` 欄有值                                | 有股數無股號！             | 5                                |
| 5   | `自動計算` | 沒股號、但 `F` 欄有值                                | 有成本無股號！             | 5                                |
| 6   | `自動計算` | 沒股號、但 `I` 欄有值                                | 有股價無股號！             | 5                                |
| 7   | `自動計算` | 沒股號、但 `M > 0`                                   | 有預計比重無股號！         | 5                                |
| 8   | `自動計算` | `Round(Sum(M4:M13), 3) > 1`                           | 預計持股比重總和大於100%！ | 1（迴圈外）                      |
| 9   | `自動計算` | 任一 `M < 0`                                         | 預計持股比重不能為負數！   | 1（有 `Exit For`）               |

三件關於數量的事：

- **#3 跟 #4~#7 是同一個 `If/Else` 的兩邊**，同一列只會走一邊；但 #4~#7 是四個各自
  獨立的 `If`，同一列可以連跳四次（空股號那一列的 E／F／I／M 都有殘值時）。
- **沒有任何一個會 `Exit Sub`。** 它們只把 `check_error` 設成 `True`，迴圈照樣跑完
  ——是「一次跳完全部」不是「跳第一個就停」。單一分頁最壞情況 `1 + 5×4 + 1 + 1 = 23`
  個對話框要一個一個按掉。
- **#1 會直接引爆 #3。** 更新股價抓不到價 → `I` 欄留空 → 自動計算立刻踩「股價尚未
  輸入完全！」。這兩支巨集連著跑的時候，一次網路抖動就是兩輪跳窗。

`Application.DisplayAlerts = False` **管不到 VBA 自己叫的 MsgBox**（那個開關只管
Excel 內建的警告，例如覆蓋檔案、刪除工作表），Python 這邊沒有任何辦法擋掉或自動按
掉。而 `自動計算` 的 `Application.ScreenUpdating = False` 是在檢查之前就設好的，
萬一是程式自己開的那個 `Visible = False` 實例（`excel_io._open_once` 的第二個分支），
對話框會出現在一個看不見的 Excel 上，等於「畫面沒有任何東西、程式永遠不會回來」。

介面上能做的只有兩件：狀態列要講到「正在跑第幾個分頁」（卡住時看得出卡在哪），以及
巨集這一步要有可放棄的路。

**做法已定案（2026/08/30）：不改巨集，改成 Python 事前檢查。** 討論過「加一個靜音旗標、
把九個 `MsgBox` 換成 `Say`、訊息收進模組變數讓程式讀回來」這條路，結論是不走：`.xls`
不在版控裡、要複製到別台電腦、隨時可能被換成新的一份，巨集改過就得每一份各改一次，
忘了就退回會掛住的狀態。而且靜音旗標是「讓它跑完再把訊息撈回來」，`自動計算` 還是進去
過一次，第 3 點那個「暫時改寫 E/F/B8」的風險一點都沒少；事前檢查則是根本不 `Run`，
那三處一格都沒被碰過。

九條的分工：

| 條件       | 誰擋                               | 為什麼                                         |
| ---------- | ---------------------------------- | ---------------------------------------------- |
| #2、#4～#9 | Python 讀格子（`自動計算` 之前）   | 純粹是格子狀態，跟巨集等一下算出來的一樣       |
| #3         | 同上，但要在 `更新股價` 之後才複查 | I 欄是 `更新股價` 填的                         |
| #1         | Python 先打一次同一支 Yahoo API    | 不是格子狀態，是那次 HTTP 的結果，只能降低機率 |

要做對的四件事：

1. **`自動計算` 那八條別在 Python 重寫判斷式，叫 Excel 自己算**（`WorksheetFunction.CountA`、
   `Application.Evaluate("ROUND(SUM(...),3)")`）。`CountA` 算不算公式吐出來的空字串、
   `Round` 的進位規則、`Sum` 的浮點誤差——只要跟 VBA 差一點點，就會變成「Python 說沒
   問題、巨集照樣跳窗」，那正是這一整段要消滅的失敗。
2. **檢查要跟 `Activate()` 綁在同一個迴圈裡，一頁一次。** 這是第 1 點那個坑換一件衣服：
   檢查 A 分頁、卻 Activate 到 B 分頁去跑，一樣不會報錯。
3. **#1 的預檢要跑同一條 regex，不是看「有沒有回應」。** 巨集的失敗判定是 regex 在回應
   裡找不到 `"price":{"raw":"…"}`——Yahoo 哪天把欄位改名，HTTP 照樣 200、body 照樣一大包
   JSON，巨集卻會整批失敗、I 欄全空、接著引爆 #3。組 `option_num` 的那一行照抄就好
   （只吃股號，不分上市上櫃）。
4. **#1 一次問完，而且只在真的要跑巨集之前問。** 網址是 `symbols=`（複數），把這一步
   會用到的代號去重之後一個 request 問完，不是一檔一次、也不是一頁一次；也不是每次
   「讀取試算」都問——只有真的要拿 Excel 股價（盤中的 `更新股價`）或
   自動計算結果的那一步之前問一次。

**預檢擋不到的那一種**：整輪跑到第 63 個 request 才被 Yahoo 限流。預檢是第 1 個 request，
不可能預知。所以看門狗還是要留——`Application.Run` 超過 N 秒沒回來，狀態列就講「第 N
個分頁的巨集可能跳了對話框，去 Excel 看一下」，把無聲掛住變成一句看得懂的指示。預檢
擋掉的是「這一輪注定全滅」（API 換形狀、代號打錯、沒網路、Yahoo 掛了），剩給看門狗的
只有偶發抖動。

**前置作業：先把 `更新股價`、`自動計算` 的原始碼匯出成文字進版控（`excel_vba/`）。**
現在它只存在 `.xls` 這個二進位檔裡，而上面兩支預檢本質上是「巨集邏輯的鏡射」——原件
沒進版控，哪天巨集被改了（`stock_limit` 從 5 變成 8、多一個檢查條件），沒有任何辦法
比對出鏡射已經失準，而失準的下場就是回到掛住。

**這一整段還沒實作，也刻意先不做。** `更新股價` 已經跑了一陣子，還沒有人實際遇過掛在
對話框上；真的遇到再回來照這裡做，不必為了還沒發生的事先付這筆工。

**2026/09/02：真的遇到了（出清股票・盤中，2002 中鋼跳「股價更新失敗」），先做上面
那句看門狗，其餘（Python 事前檢查、VBA 匯出進版控）維持刻意不做。** 加了
`excel_io._run_macro_watched`：`run_update_price_macro`／`run_auto_calc_macro` 多一個
可選的 `on_stuck` 參數，背後是一顆 `threading.Timer`，超過 `MACRO_STUCK_AFTER`（10 秒）
`Application.Run` 還沒回來就呼叫一次；五個呼叫端（`ui_order._order_plans_worker`（原
`_order_read_worker`，2026/09/02 下午拆成「讀取ＯＯ持股」／「讀取試算」兩顆按鈕時
改名）／
`_order_stock_price_worker`／`_order_auto_calc_worker`、`ui_order_exec.
_order_price_refresh_worker`）都接上了，透過 `ui_background._macro_stuck_notifier` 把
訊息丟進 `self.queue`（背景執行緒不能碰 widget，跟其他背景結果同一條路），常駐狀態列
顯示「『更新股價』可能卡在《某分頁》跳出的對話框，去 Excel 看一下」。這顆計時器只是
提醒，不會、也沒辦法主動打斷或按掉那個對話框——真的卡住還是要人去 Excel 手動點確定。

**3. `自動計算` 會暫時改寫 E/F/B8，而且不收斂就永遠不停。**

它記下 `orginal_cash = Range("B8").Formula`，過程中反覆改寫 E4:E13／F4:F13／B8，最後才
還原。中途出錯 → 三處留在中間狀態，而且 `Application.ScreenUpdating = False` 還原不
回來（那個 `over:` 標籤沒有任何 `GoTo` 指向它，是死碼）。`Do ... Loop Until final_check`
和後面三個 `Do While` 都沒有迭代上限。

這跟更新分頁「E/F/B8 一律覆蓋」是**正面衝突**——兩邊會同時動同一組格子。所以：

> **自動計算執行期間，更新分頁的讀取／寫入要鎖住，反之亦然。** 這是一條新的互斥
> 規則，跟 `round_scope` 同一個層級，已寫進 CLAUDE.md 的「改動前必看」。

### 9.8 出清・零股：掛了再撤，而且多輪之間要真的同步

**2026/09/03 實作，未實測真帳號。** 規格是規劃文件「出清股票－零股」那一節
（`docs/自動下單與半自動下單規劃.pptx.txt` 52-63 行）。

設定只有四項，**沒有比重**——零股本來就是整張切剩下的零頭（9.4），出清它就是整段
賣掉，沒有「賣幾成」可以斟酌。所以量固定是 `split_lots(持股)[1]` 的絕對值
（1~999 股），畫面上那一格寫「全部零股」而不是留一個永遠不會被讀的輸入框。

流程三步，中間那兩步跟有沒有勾多輪無關：

```
0. 只有勾多輪才有：完整同步 -> 重讀 Excel（2026/09/04 起，見 9.9）
1. 全部零股掛賣單（ROD，一筆一筆依序送，跟其他作業共用同一台引擎）
2. 等 6 秒 -> 把還掛著的撤掉（一個帳戶一則指令；規劃文件原文是 20 秒，2026/09/04
   使用者改成 6 秒，見 `ui_order_exec.ODD_CANCEL_WAIT_MS`）
3. 只有勾多輪才有：完整同步 -> 重讀 Excel -> 還有零股就回到第 1 步
```

**為什麼是「掛了再撤」而不是像整張那樣用 IOC**：零股那一場根本沒有 IOC／FOK 可選
（2026/09/01 盤中偵察確認，見 9.4 最後一段），只能用 ROD 掛出去。ROD 不會自己取消，
所以第 2 步是程式的責任，不是交易所的。這也是為什麼「停止」在等待那幾秒時要特別
講一句「零股賣單還掛在市場上，自動撤單已經取消，請自己去掛單分頁撤」——停止在這
一段的意思跟在別的地方不一樣。

**撤哪幾筆是查回來的，不是程式記得的**（2026/09/03 使用者選定範圍）：半自動模式下
按確認的是人，`order_fill.confirm_order` 只回一句訊息、拿不到委託書號，程式手上根本
沒有那份清單。所以改成查一次 `queryOrder` 再過濾，條件三個都要——

| 條件 | 不加的話 |
| --- | --- |
| `apcode == '5'`（盤中零股） | 會撤到整股的單。同一檔股票很可能同時掛著整張的委託 |
| 股票在這一輪指定的那幾檔裡 | 會撤到這一輪沒指定的其他零股單 |
| `side == 'S'` 且 `open` | 買單、已成交的單跟出清無關 |

查回來一筆都沒有**不是失敗**，是「這一輪掛出去的全部成交了」——出清零股最想看到的
結果。狀態列要分得出這兩件事（「查到 0 筆還掛著」vs「撤了 0 筆但有 5 筆撤不掉」）。
撤單本身借掛單分頁那一套（`ui_pending._cancel_orders_split`，委託單走
`order_cancel.py`、預約單走 `order_cancel_reservation.py`），不另外寫一份。

### 9.9 每一輪開始前都要真的同步，否則會重複賣

**這是 2026/09/03 才修好的一個既有缺口，整張與零股共用同一個修法**；2026/09/04
再把同一個修法補到第 1 輪之前（見本節最後一段）。

規劃文件對出清整張・盤中（47 行）與出清零股（63 行）寫的是同一句話：多輪之間要
「更新持股管理檔的現金（初始餘額累加）、股數、成本」。但在這之前，多輪只做了
`_order_price_refresh_worker` 那次**重讀 Excel**，而 `excel_io.write_cells` 全專案
只有 `ui_background._write_worker`（更新分頁的寫入）一個呼叫端——也就是說：

```
第 1 輪  照 Excel E 欄 8,000 股算出賣 2 張  ->  IOC 成交  ->  真實持股剩 6,000
         但 Excel E 欄還是 8,000（沒有任何一條路會改它）
第 2 輪  重讀 Excel  ->  還是 8,000  ->  又賣 2 張
         ...一路重複到 ORDER_MULTI_ROUND_CAP = 10 為止
```

**不是「跑滿 10 輪才停」而已，是重複賣同一批部位。** 所以現在多輪之間會先跑一次
完整同步（`ui_order_exec._start_round_sync`），跑完才重讀 Excel 判斷收斂。

走的是更新分頁那一整條路（`("fetch", …)` → `_on_fetched` → 寫 Excel → `_on_written`
→ `_commit_round`），等同程式自己按一次「更新（這幾位）帳戶」，**不是另外寫一份
簡化版**：`round_scope` 只准碰這一輪讀到的那幾位、寫入成功才落帳——這些規則都在
那條路上，複製一份出來遲早會少掉其中一條。

**現金算法固定用初始餘額累加，不跟更新分頁那顆全域開關走、也不跳視窗問**
（2026/09/03 使用者訂正，推翻同一天稍早的版本——見下面「三件連帶要做對的事」第一
點）。規劃文件原文「現金（初始餘額累加）」講的就是這個算法本身，不是「跳視窗讓人
選」。`cash_method` 這個 Var 是更新分頁跟這裡共用的，所以 `_start_round_sync` 用
「暫時切成初始餘額累加、`_order_sync_finished` 一開頭就切回來」而不是永久改掉——
不然出清跑完，更新分頁會被靜靜換成初始餘額累加，跟使用者那天在更新分頁選的算法對
不上；也因此出清這幾位當下用哪一種，跟更新分頁那顆總開關、跟今天問過沒有都無關。

#### 為什麼不能省掉「寫回 Excel」這一段

2026/09/04 試過改成「輪與輪之間直接看網頁持股，不繞 Excel」，當天就改回來
（commit `8b9aa54` 與它的 revert）。那個念頭本身是合理的：**出清**這兩個作業的量是
從持股直接算的，而持股就是網頁那份未實現損益，寫進 Excel 再讀回來確實只是把同一份
數字轉手一次。少掉那一段還能少掉 COM 寫入、存檔、落帳、現金基準、暫時切換現金算法。

**但那只對出清成立。** 全持股交易／買賣股票的量不是從持股算的：

| 作業                 | 這一輪要送多少，答案在哪裡             |
| -------------------- | -------------------------------------- |
| 出清・整張／零股     | 持股 × 比重（持股＝網頁的未實現損益）  |
| 買賣股票／全持股交易 | 各帳戶自己那一頁的**下單試算 M19:N28** |

M19:N28 是 `自動計算` 巨集拿 **E/F/B8** 算出來的（見 9.1、9.5）。E/F/B8 沒有寫回去，
下一輪讀到的試算就還是上一輪的計畫——跟「重讀 Excel 讀回下單前的股數」是同一種錯，
只是換一組格子。

所以這一段的作用**不是搬數字，是讓 Excel 的公式有機會重算**，那是網頁給不了的東西。
目前接上多輪的只有出清（買賣股票切過去就強制關掉多輪，見
`ui_order._on_order_job_changed`），所以這條路現在還沒有人非它不可——但它是全持股交易
接上多輪的前提，2026/09/04 使用者確認要留著。

#### 第 1 輪之前也要同步（2026/09/04 使用者定案）

上面那個修法只補到「輪與輪之間」，第 1 輪送出去的量還是拿按下「開始下單」那一刻的
Excel E 欄算的——而沒有人保證那份 Excel 是最新的：

| Excel 為什麼會是舊的                    | 第 1 輪會拿到什麼                        |
| --------------------------------------- | ---------------------------------------- |
| 今天還沒按過「更新」                    | 隔夜交割、昨天的成交都還沒反映           |
| 人自己用手機／網頁下過單                | 程式完全不知道                           |
| 上一批跑滿 `ORDER_MULTI_ROUND_CAP` 停下 | 最後那一輪賣掉的沒寫回去（停在同步之前） |
| 上一批中途按了「停止」                  | 同上                                     |

最後兩條最危險：那個輪數上限的警告框正好叫人「再按一次開始下單」，而 Excel 比實際
多出來的部分，第 1 輪就會照著再賣一次——跟這一節開頭那張圖是同一個錯，只是換一個
輪次。所以勾了多輪的話，按下「開始下單」之後不是直接送第 1 筆，而是：

```
round = 0 -> _start_round_sync（查網頁 -> 寫回 E/F/B8 -> 落帳）
          -> _prepare_next_round（順便跑「更新股價」巨集，看有沒有勾）
          -> _on_order_price_refresh 用剛讀回來的持股重組隊列 -> round = 1
```

跟第 2 輪以後**完全同一條路**，沒有另外寫一份。「自動更新股價」原本自己有一條岔路
（勾了才 `round=0`），現在併進來了——規劃文件那句「每一輪開始前都先觸發更新股價，
包含第一輪」由同步之後那一段照樣做到。沒勾多輪的單輪維持原狀，按下去就送。

兩件連帶的事：

- **`_round_zero_missing` 在 round 0 要回空的。** 它的意思是「這幾檔網頁上不見了＝
  程式剛剛賣光了，歸零寫回 Excel」；但第 1 輪之前程式一筆都還沒送，「網頁上不見了」
  只可能是人自己賣掉或本來就沒有，那正是 `planner.plan` 那段講明不該自作主張清成 0
  的情況。同一個旗標在兩個時間點意思相反。
- **同步完發現一筆都不用送要跳訊息框**，不能只寫狀態列：確認框剛講完「即將依序處理
  N 筆委託」，結果一筆都沒送，只寫狀態列很容易被當成當掉了。而那幾乎一定就是這一段
  同步要抓的東西——網頁上早就沒有那些部位了。

三件連帶要做對的事：

- **Excel、紀錄檔要先檢查好。** 同步要 Excel 開著、要紀錄檔是好的，這兩件在按下
  「開始」之前就檢查完（`_order_round_sync_ready`）——等第一輪跑完才發現 Excel
  沒開好的話，委託已經送出去了。現金算法本身不用問（見上段），所以這裡不會跳視窗。
- **busy 要自己補回來。** `_on_fetched`／`_on_written` 兩個終點都會 `_set_busy(False)`，
  那顆是整支程式共用的 cookie 鎖。鬆掉的話「登入」「更新」「全部登出」在下一輪開始前
  變成可以按的，而它們都會換掉手上這組 cookie——接下來那一輪的委託就會掛到別人帳上。
- **同步失敗就整批停下來。** 查不到網頁資料、寫入失敗、一位都沒對照起來，都代表 Excel
  上的持股還是舊的，下一輪不能跑——那正是這一整段要消滅的那個錯。

### 9.10 執行預覽的「出清進度」欄

2026/09/05 加的一欄，只有**出清股票**這個作業有（買賣股票／全持股交易的量不是從
「清掉一段持股」算出來的，沒有分母可言）。位置在持股與備註之間，格式是
`███▒░ 62%`：`█` 已經確認出清、`▒` 這一輪已經送出但還不知道成交沒、`░` 還沒動、
沒有這一段可以清顯示 `－`。不做整批總進度條（那個已經決定不做），也不碰收斂訊息
（「跑了 N 輪，已經全部出清」那幾句一個字都沒改）與底部那條 indeterminate 進度條
（那是「有事在跑」，不是進度）。

**分母不是全部持股，是「這個作業要清掉的那一段」**（`orders.clearable_qty`）：

| 作業           | 分母                                    | 終點 |
| -------------- | ---------------------------------------- | ---- |
| 出清・整張     | `split_lots(起始持股)[0] × 1000`         | 0    |
| 出清・零股     | `split_lots(起始持股)[1]`                | 0    |

整張那一版把零股算進分母的話，跑到收斂會停在 97%，看起來像沒做完——但那正是
9.9 講的「整張的部分已經出清，剩下不到 1 張的零股換算不出下一張委託」，沒有下一輪
了，所以分母刻意不含零股，收斂時是 `█████ 100%`。比重不影響分母：多輪每輪都對
剩餘再取一次比重（8→4→2→1），終點一樣是清光。

**分子＝分母 − 現在同一段的量**，資料來源是 `self.order_holdings`（多輪重讀 Excel
後會更新它，見 9.9）。百分比**只算已經確認出清的部分，絕對不含「已送出」那一段**：
真帳號拿不到成交量（IOC 可能整筆零成交、零股可能沒撮到就被撤掉，見 9.8；半自動時
人還可能在瀏覽器按「取消」），把送出的量當成果就是謊報，下一輪重讀持股會自己修正。

`▒`（sent）＝這一輪 queue 裡 `index < order_exec_pos` 那幾筆的量：
`_on_order_dialog_closed` 要等委託確認視窗真的關了才會把 `order_exec_pos` 往前推，
所以正在等視窗的那一筆不算已送出——它可能人還沒按確認，甚至還沒真的送出去。

格子數用 floor 除法算，`done < base_qty` 時代數上保證湊不到 `PROGRESS_CELLS` 整格
（`orders.progress_text`）：差一股就顯示 100% 比少顯示一個百分點更容易被忽略，所以
沒清完就不給滿格；真的清完（`now_qty` 在這一段歸零）才是滿格 `100%`。`sent_qty > 0`
就至少給一格 `▒`（還有空格的話）：它的作用是讓人看到有東西在路上，格數不必跟比例
精確對應。

**分母什麼時候拍照**（`ui_order_exec._snapshot_order_base_qty`）：

| 情況       | 拍照點                                                           |
| ---------- | ----------------------------------------------------------------- |
| 沒勾多輪   | `start_order_execution` 凍結 `queue_rows` 的那一刻                |
| 勾了多輪   | `_on_order_price_refresh` 裡 `order_exec_round == 0` 那一次，更新完 `order_holdings` 之後、算 preview 之前 |

多輪不能在按下「開始下單」那一刻拍——那份 Excel 不保證是最新的（見 9.9），拿它當
分母會一開始就顯示一個其實是「人自己賣掉」的百分比。新的一批 start 時整份覆蓋掉
舊的；按「停止」不清，留著讓人看最後結果。

實作分成三塊：

- `orders.py`：`clearable_qty(held_qty, unit)` 算分母／分子用的那一段股數；
  `progress_text(base_qty, now_qty, sent_qty)` 組出顯示字串；三支出清用的
  `plan_stock_orders`／`plan_intraday_orders`／`plan_clear_odd_orders` 每一列多帶
  `"clearing": True`（`plan_trade_orders` 沒有這個鍵，這是刻意的——它掃不到，正是
  要的結果，因為那個作業不顯示這一欄）。
- `ui_order.py`：`_render_order_preview` 算每一列的進度字串（基準優先用
  `order_exec_base_qty`，沒有的話退回用這一列當下的 `clearable_qty` 當基準——還沒
  開始執行時是「條全空 0%」，不是「－」），並記一份 `(sheet, code) -> iid` 給後面
  單格更新用；`displaycolumns` 看 `preview` 裡有沒有 `"clearing"` 的列決定要不要
  顯示這一欄（preview 是空的就退回問 `order_job`）。
- `ui_order_exec.py`：`_snapshot_order_base_qty` 拍分母、`_order_sent_qty` 算某一列
  已送出的量、`_refresh_order_progress_cells` 只更新單格（不重畫整張表），掛在
  `_update_order_exec_ui` **最前面**——那支下面有好幾個 early return（等撤單、等
  同步、queue 空了），放後面的話「▒」在那幾段就不會更新，`order_exec_pos` 歸零
  之後也不會跟著消掉。

**不做的事**：不在 Treeview 每列塞真的 `Progressbar`（Treeview 放不了 widget，改用
image element 會撞上設計原則第十二、十三節量出來的重畫成本）；不把「送出」當
「成交」推進度；不試著讓 `held` 欄跟進度百分比對得起來（`held` 是持股全量，含這個
作業不動的那一段，備註欄的「另有整張 N 張，這一輪不送」已經在解釋這件事）；不估
「還剩幾輪／還要多久」（成交與否不可預測，`ORDER_MULTI_ROUND_CAP` 是安全閥不是
預期值）。

## 十、掛單分頁與強制中斷

### 10.1 掛單分頁

```
┌ 掛單 ─────────────────────────────────────────────────────────────────────────┐
│ 範圍 全部 ▾   [查詢掛單]                            最後查詢 11:32:05        │
├───────────────────────────────────────────────────────────────────────────────┤
│ 帳戶  委託日期  有效交易日  委託書號  股票代號  交易別  買賣別  委託價格      │
│       原委託數量  已取消數量  已成交數量  委託別  委託狀態  有效數量          │
│ 交易人A  2026/08/31 09:00:43  2026/08/31  J0124  2059  整股 現股  賣出        │
│       1,305  2  0  0  ROD當日有效  委託成功  2                                │
│ …（14 欄在畫面上是同一列，這裡排不下才折成兩行）                              │
├───────────────────────────────────────────────────────────────────────────────┤
│ [取消全部買單]  [取消全部賣單]  [取消全部掛單]                                │
└───────────────────────────────────────────────────────────────────────────────┘
```

「列出掛單」跟「取消掛單」在同一頁不是湊在一起——取消之前本來就要先看到會取消掉
什麼。而且它同時是**自動送出委託單的唯一驗證面**：勾了自動送出之後，人現在沒有任何
地方能確認送出去了什麼，這頁補上這個缺口。

資料源是 `order_recon.py` 已經確認過判讀方式的 `queryOrder`（`paramInfo` 與結果判讀
見 [[下單API細節與order_recon.py]]）。「範圍」跟更新分頁的範圍選單同一個概念，但這
裡預設「全部」——看掛單本來就是要一次看完所有帳戶。

欄位跟網站「委託查詢」那張表一欄一欄對齊，連欄位名都照抄（2026/08/31 使用者要求）：
這一頁存在的意義就是拿來跟網頁互相核對，欄位名不一樣、少一欄多一欄，核對的人就得先
在腦子裡做一次對照表。多出來的只有最前面那一欄「帳戶」——網站一次只看得到登入的那
一個人，這裡是所有帳戶攤在同一張表上。十四欄全部出自同一份 `queryOrder` 回應，沒有
為了湊欄位另外再查一支 API：

| 畫面欄位   | 來源                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 委託日期   | `orddate` ＋ `ordtime`，毫秒不印                                       |
| 有效交易日 | `workdate`                                                             |
| 委託書號   | `ordno`                                                                |
| 股票代號   | `stockno`（網站還會印股名，那份資料不在這支回應裡）                    |
| 交易別     | `apcode` ＋ `trade` **兩碼合起來**查（`order_recon.TRADE_NAMES`）      |
| 買賣別     | `buysell`                                                              |
| 委託價格   | `odprice`；非限價的改印 `priceflag` 的種類（市價單的 odprice 是 0）    |
| 原委託數量 | `orgqty`                                                               |
| 已取消數量 | `celqty`                                                               |
| 已成交數量 | `matqty`                                                               |
| 委託別     | `bs_flag`（ROD／IOC／FOK）                                             |
| 委託狀態   | `describe_outcome()`，判讀方式抄自網站自己的 `fakeJSON()`              |
| 有效數量   | 自己算：原委託 − 已成交 − 已取消（`celable` 不是數量，別拿它當數量用） |

欄寬不是寫死的數字，是每次填完表之後照「表頭（粗體）＋這一批資料實際的字」量出來的
（`ui_pending._resize_pending_columns`）。寫死的話，字級／字型／DPI 只要有一項跟當初猜
的時候不一樣就會切字——2026/08/31 就切到過：「委託日期」只剩 `2026/08/31 09:00:4.`、
「委託狀態」被壓成「委託狀…」。量出來的寬度要連 `minwidth` 一起設：欄寬總和比表格寬
的時候，Tk 會去壓 stretch 的那一欄，一路壓到 `minwidth`（預設只有 20 像素）為止，只設
`width` 擋不住，被壓的正好就是「委託狀態」那一欄。

平常一天（都是 ROD、沒有失敗訊息）14 欄合計約 1,420 像素，`UI_WIDTH=1450` 剛好放得下、
不會出現捲軸；有 IOC／FOK 那種長失敗訊息的日子會撐到約 1,650，那時候才用表格下面那條
水平捲軸——把失敗原因整句看完，比不用捲重要。

三顆取消按鈕都要先跳確認（會動到真實委託），確認框裡列出「這一次會取消幾筆、哪幾
檔」，不是只問「確定嗎」。

### 10.2 強制中斷放底部狀態列

`ui_layout.py` 裡那條 `bottom` Frame（狀態文字＋進度條）是**跨分頁常駐**的，
「停止全部操作」就該在那裡，不在下單分頁的預覽框裡——人按它的時候很可能正在掛單
分頁看委託，而現在的「停止」在別的分頁上按不到。

有東西在跑才亮、沒跑就灰，不搶注意力。現有的 `ui_order_exec.stop_order_execution` 直接接
上去即可，等於把既有那顆按鈕升級成全域的；下單分頁裡那顆「停止」可以留著當第二個
入口（跟「範圍選單／左邊名單是同一個選擇的兩個入口」同一種做法）。

### 10.3 取消全部掛單

規格來源：2026/08/31 使用者提供的「委託查詢」頁 HTML 片段與「刪單確認」視窗截圖，加上
`偵察資料\委託確認視窗\orderConfirmRWD.html` 的原始碼——那支檔案同時是下單、改價、改量、
刪單四種確認視窗，不是四份。

2026/08/31 10:06 用 `order_cancel_recon.py` 對一張真的掛在外面的單（J0845，2007 燁興，買進
1 張 ROD）實地跑過一遍：勾選、開刪單確認視窗、把每一列倒出來，**沒有按確認**，那張單毫髮無傷。
下面第三、七、十點寫的都是那一次看到的東西，不是推測。**同一天盤中接著把三顆按鈕接上、
用真帳號把那張 J0845 刪掉了**，所以連「按下確認之後會怎樣」也驗過了（第十點最後一段）。

**一、三顆按鈕的差別只有「勾哪幾列」**

動的一律是**畫面上這張表現在看得到的那幾列**，不是按下去才重新查一次：

| 按鈕         | 送哪幾列                |
| ------------ | ----------------------- |
| 取消全部買單 | `open` 且 `side == "B"` |
| 取消全部賣單 | `open` 且 `side == "S"` |
| 取消全部掛單 | `open`，不分買賣        |

`open` 是 `order_query.normalize` 已經算好的旗標（委託本身沒失敗，而且原委託 − 已成交 −
已取消 > 0），畫面上淡化的那幾列本來就取消不掉。

**接上取消之前，`open` 要改成看 `celable`**：網站自己判斷「這一列刪不刪得掉」用的是
`celable == '1'`——是 `1` 才畫得出那一列的勾選框，不是 `1` 就整格空白（`renderTable` 裡的
`celBox`）。我們現在那個算式跟它的結論目前一致，但那是自己推的，`celable` 是網站給的答案。

**按下去之前不自動重查一次**：人是看著這張表按的，重查會讓「按下去那一刻看到的」跟「真的
送出去的」變成兩份東西。範圍改過、或這張表是上次登入前查的，那就自己先按一次「查詢掛單」
——按鈕在還沒查過、或表上一筆 `open` 都沒有的時候本來就是灰的。

**二、為什麼一定要走頁面，不能自己打那支 API**

刪單的 CMD 是 `modifyOrder`，卡在跟 `newOrder` 完全一樣的地方：送出前那一步是
`getCert(row, plainText)`，TWCA 憑證簽章在瀏覽器裡做（見記憶「下單 API 細節與
order_recon.py」）。而且 `submitObj` 有一半欄位（`sales`、`cust_data`、`signcode`、
`plainText`、`orderMode`）是頁面自己從那一列委託湊出來的，Python 這邊根本沒有來源。

所以取消掛單跟下單同一種做法：**操作真實頁面**。它的定位是 `order_fill.py` 那一種，不是
`recon.py`／`fetch.py`／`order_query.py`「自己打 AJAX」那一種。

**三、網站那一頭實際上做了什麼**

照 `orderConfirmRWD.html` 與「委託查詢」頁自己的 JS 讀出來的，加上 08/31 那次實跑的驗證：

| 步驟           | 網站那一頭                                                                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 頁面           | `order/layoutRWD.jsp?type=2`，就是 `order_recon.ORDER_PAGE`，查掛單本來就會導過去                                                                                            |
| 哪幾列畫得出來 | `renderTable` 只畫 `ordstatus == '2' && market != 'R'`——**預約單、興櫃不在這一頁**                                                                                           |
| 逐列勾選       | `#qOrderTable` 裡一列一個 `<input type=checkbox name=chkCel value="<i>">`，`celable == '1'` 才畫得出來                                                                       |
| 那個 value     | 是 `queryOrder` 回應陣列的**索引**，不是委託書號；頁面靠 `#qOrderTable #bar<value>` 這個 tbody 讀回那一列                                                                    |
| 全選           | `#numall`（`name=chkAll`）→ `$('input:checkbox').not(this).prop('checked', this.checked)`，**整份文件**一起設                                                                |
| 開確認視窗     | `#openConfirm`「終止委託單」→ 收 `$('input[name=chkCel]:checked')`（**也是整份文件**）湊成 `orderArray`，`mod='3'`，`layer.open` 開 `orderConfirmRWD.html`，標題「刪單確認」 |
| 沒有可刪的單時 | `#openConfirm` 這顆按鈕會被 `remove()` 掉，不是變灰——程式要當成「按鈕可能根本不存在」                                                                                        |
| 視窗內容       | 一列一筆，欄位跟截圖一樣：比 10.1 那張表多「盤別」「欲取消數量」「委託結果」，少「帳戶」「委託狀態」「有效數量」                                                             |
| 送出           | `#submit`：`submitArray` 有幾筆就打幾次 `MainController`，一筆一次                                                                                                           |
| 送出的內容     | `CMD=modifyOrder`、`ws_id` ＝委託書號、`od_qty` 固定 `'0'`（原始碼註解「刪單刪減數量為 0」）、`orderMode` 固定 `'2'`                                                         |
| 結果           | 逐筆寫進 `#result0`、`#result1`…，成功是「刪單成功」四個字，失敗直接印券商回的 `retmsg`                                                                                      |
| 收尾           | 送到**最後一筆**才呼叫 `parent.renderTable()` 重畫網頁那張表；`#submit` 自己隱藏、`#cancel` 的字變成「關閉」                                                                 |

刪單不必自己算數量（`od_qty` 固定 0 ＝「剩多少刪多少」），所以 `left` 那個數字只用來決定
「這筆還值不值得送」跟畫面顯示，不會被送出去。

**四、跟下單那條路差在哪**

| 事項       | 下單（`order_fill`）                           | 刪單                                               |
| ---------- | ---------------------------------------------- | -------------------------------------------------- |
| 一次幾筆   | 一筆一個確認視窗                               | 一個帳戶的一整批共用一個視窗                       |
| 結果讀哪裡 | `#result0`                                     | `#result0` ～ `#result{n-1}`，一列一個             |
| 誰按確認   | 看「自動送出委託單」開關                       | 程式自己按（第五點）                               |
| 視窗誰關   | `confirm_order` 按 `#cancel`（字已變「關閉」） | 同左，但**一定要在換下一個帳戶的 cookie 之前關掉** |

**`order_fill.confirm_order` 不能直接拿來用**：它只讀 `#result0`。一批刪 8 筆、第 1 筆成功
第 5 筆失敗，沿用那支會回報「全部成功」——這是這一整段最容易寫錯、而且錯了不會報錯的地方。

**五、確認框問一次，之後程式自己按**

下單那顆「自動送出委託單」預設關著，因為送出去會建立新部位、會花錢。刪單方向相反——它是把
已經送出去的東西收回來，不會產生新部位、不會多花一毛錢；而 20 個帳戶各等人回瀏覽器按一次
確認，等於這三顆按鈕沒有用。所以：

1. 按下按鈕先跳一次 `ask_confirm`，列出**會取消幾筆、哪幾檔、哪幾個帳戶**（10.1 已經寫過
   這條），不是只問「確定嗎」。
2. 人按了確定之後整批跑完，中途不再問。
3. 底部「停止全部操作」照樣要能中斷，做法見第六點。

**六、一個帳戶一則指令，不是一則指令跑完整批**

一個帳戶要做的事：

```
ensure_logged_in（換 cookie，不重登） -> goto type=2 -> 等頁面 ready
  -> 勾這個帳戶要取消的那幾列 -> #openConfirm -> 等「刪單確認」出現
  -> 核對（第七點） -> #submit -> 逐列讀 #result -> 關視窗 -> 回話
```

**勾選只勾 `#qOrderTable input[name=chkCel]`，一律不要按全選。** 全選會把整份文件的 checkbox
都設一遍（第三點），連凍結表頭那份影子表格也算進去，而三顆按鈕裡有兩顆本來就要逐列勾。
保險起見，按「終止委託單」之前把不在 `#qOrderTable` 底下的 `chkCel` 全部取消勾一次。

指令切成一個帳戶一則（跟下單的 `("order", …)` 同一個形狀，**不是** `pending` 那種一則指令
跑完全部帳戶）：這樣「停止全部操作」在帳戶與帳戶之間就是免費的——不派下一則就是停了，不必
為了中斷另外發明一個跨執行緒的旗標。

**視窗一定要在這一則指令裡收乾淨**（送出後按「關閉」，或核對失敗按「取消」）。理由跟下單
那條「兩筆之間一定要等視窗關掉」一模一樣：整個瀏覽器只有一組 cookie，視窗還開著就換下一個
帳戶的 cookie，那個視窗後來送出去的會是「現在瀏覽器帶著的身分」——真的會刪到別人的委託。
差別只在下單是等人去關、刪單是程式自己關，所以不必像下單那樣留一個 page 給閒置輪詢盯著。

**七、按確認之前先核對筆數與委託書編號**

勾選是在 DOM 上做的，送出去的卻是頁面自己蒐集的 `parent.orderArray`，中間隔了一層。所以按
`#submit` 之前，把視窗裡每一列的 `#ordno<i>` 讀回來跟程式自己要送的那幾筆比對：**筆數對不
上、或有哪一筆委託書號不在名單裡，就按「取消」收工並回報，不要按確認。**

這道核對不是憑空加的，而且 08/31 那次實跑已經**證實它會發生**：畫面上只有一張掛單（J0845），
按全選之後 4 個 checkbox 被勾起來、刪單確認視窗上出現**兩列一模一樣的 J0845**，`orderArray`
真的是 2 筆——按下確認就會對同一張單送兩次刪單。

成因也查清楚了，是網站自己的兩段程式湊出來的，跟我們怎麼操作無關：

1. 這一頁跑 `$(".table-freezes").freezeTable(...)`，那個外掛會 clone 一份表格出來做凍結表頭
   （DOM 裡因此有兩份 `chkCel`，其中一份沒有 id、文字是空的）；
2. 全選跟 `#openConfirm` 用的都是**整份文件**的選擇器（`$('input:checkbox')`、
   `$('input[name=chkCel]:checked')`），影子那一份照樣被算進去。

所以第六點才要指定 `#qOrderTable` 底下的 checkbox。但核對還是要做——擋的是「網站改版又多
clone 一份」這種我們看不到的變化，而且它是免費的。

**八、送出之後的驗收：重查，不是看對話框**

刪單成功與否的最終答案在「委託查詢」，不在視窗上那四個字。所以整批跑完**自動重查一次掛單**，
用查回來的 `open` 筆數當驗收，狀態列講兩個數字：送出去幾筆、重查之後還剩幾筆掛在外面。這一頁
本來就是自動送出的驗證面（10.1），刪單是同一個道理。

**九、失敗語意：按下去之後不自動重試**

`#submit` 一按下去，那一批的刪單多半已經送到券商了。跟 `order_fill.OrderMaybeSubmitted` 同一
條規矩：**送出之後的任何失敗（等不到結果、視窗關不掉、瀏覽器斷線）都不自動重來一遍**，一律
回報給人，然後重查掛單。

跟下單不同的是後果的重量：同一筆委託重送一次是真的多一筆單；同一筆刪單重送一次，多半只會拿到
券商一句「委託單不存在」。但「多半」不是「一定」，而且重查一次就有答案，不值得為它開一條自動
重試的路。

**十、偵察結果（2026/08/31 10:06，`order_cancel_recon.py`）**

| 原本要看的                                  | 看到的答案                                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 逐列 checkbox 的 selector，怎麼對回委託書號 | `#qOrderTable input[name=chkCel]`，`value` 是回應陣列的索引；要對回委託書號讀 `#qOrderTable #bar<value>` 那一列的第 4 欄 |
| 全選會不會勾出重複的列                      | **會**，而且視窗上真的變兩列——成因見第七點                                                                               |
| layer 標題列是不是「刪單確認」              | 是（`parent.mod` 也確認是 `'3'`）                                                                                        |
| 預約單在不在這一頁                          | **不在**。`renderTable` 只畫 `ordstatus == '2'`，而且送出去的 `orderMode` 是寫死的 `'2'`——這一頁只刪得掉盤中單           |

`order_cancel_recon.py` 留著：它是唯讀的（勾選、開視窗、倒出來就停手，**不按確認**），網站改版
之後要重新確認上面這幾條，再跑一次就好。要有一張真的掛在外面的單才跑得動。

**「按下確認之後會怎樣」也驗過了**：2026/08/31 盤中，掛單分頁按「取消全部買單」，一筆
（J0845，2007 燁興，買進 1 張 ROD），確認框列出那一筆、送出、`#result0` 回「刪單成功」，
自動重查回來那一列變成刪單成功、有效數量 0。第七點那道核對也順帶證明有效：視窗上要是又
變成兩列，這一次會停在核對、一筆都不送——它沒有停，代表逐列勾選那段真的避開了影子表格。

還沒遇過的是**一批多筆**（一個帳戶同時刪好幾張、或多個帳戶接力）。逐列讀 `#result<i>`
那段是照 `orderConfirmRWD.html` 寫的、也用假 page 物件測過六條路徑，但真的多筆還沒跑過。

| ----------------------- | ------------------------------------------------------------------------------------- |
| `order_cancel.py`（新） | 頁面操作：勾選、開視窗、核對、按確認、逐列讀結果、關視窗。定位跟 `order_fill.py` 一樣 |

**十二、預約單也要能取消（2026/09/02 補）**

盤後測試「取消全部掛單」失敗，查出來是盤後送出的 ROD 委託轉成了預約單
（`ordstatus=='1'`），`order_query.normalize()` 判斷可取消的 `open` 沒有排除它，
卻又讀不到它的 `ordno`（那個欄位在 `queryOrder` 回應裡對預約單是空字串），湊出一批
空委託書號被過濾光，才丟出「沒有指定要刪哪一筆」。

原本討論到「乾脆分兩顆按鈕」，但使用者指出原始規劃（本文件開頭「四、取消掛單」跟
`docs/自動下單與半自動下單規劃.pptx.txt` 81-85 行）寫的就是「取消全部買/賣/掛單」
三顆，**沒有分委託單跟預約單**——這三顆本來就該兩種都能取消，只是預約單那條路
（`order/layoutRWD.jsp?type=4`）從來沒人看過，第十點的偵察只做過 `type=2`。

2026/09/02 對真帳號、真的一筆預約單（P0638918）偵察兩輪（用過的偵察腳本已經
拿掉，見 `order_cancel_reservation.py`），看到的東西：

| 原本要看的                         | 看到的答案                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 逐列的刪除機制長什麼樣              | 每一列自己一顆 `.delRow`「刪除」鈕，不是勾選＋一顆批次按鈕；點下去只是把 `orderObj` 塞進 `orderArray`、`mod='3'`，開 `layer.open`，**沒有送出任何 AJAX** |
| 開出來的確認視窗是哪一份            | `orderConfirmRWD.html`——**跟 `order_cancel.py`／`order_fill.py` 用的是同一份**，`#submit`／`#cancel`／`#result0` 選擇器直接沿用 |
| 識別欄位是什麼                      | `preordno`（預約書號），不是 `ordno`；對照 `偵察資料\20260828_1055_..._委託查詢.json` 確認兩個欄位在回應裡一直都在，只是依 `ordstatus` 條件性地一個有值一個是空字串 |
| 送出去的 CMD 跟欄位                 | 一樣是 `modifyOrder`；`orderConfirmRWD.html` 的 `mod=='3'` 分支會把 `chgqty` 覆寫成 `'0'`，`orderMode` 直接讀 `orderObj.ordstatus`（`.delRow` 固定填 `'1'`）——委託單跟預約單是同一支 CMD 底下的分岔，不是兩套邏輯 |
| 有沒有批次刪除                      | 這頁也有勾選＋`#openConfirm`「終止委託單」，但開的是**另一份** `orderConfirm.html`（沒有 RWD），完全沒偵察過，跟 `.delRow` 不是同一個 iframe——**刻意不碰**，一律走已驗證的 `.delRow`，一筆一次 |

落地：`order_query.normalize()` 依 `ordstatus` 選 `preordno`／`ordno`（並多回傳
`ordstatus` 供路由判斷）；新增 `order_cancel_reservation.py`（跟 `order_cancel.py`
對稱的公開介面），`ui_pending.py` 的 `cancel_pending()` 把同一帳戶的候選列拆成
委託單／預約單兩份委託書號，`_pending_cancel_job` 登入一次、兩邊都跑、結果合併。
