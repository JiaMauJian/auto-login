# 持股同步介面規劃

Excel 版面維持原樣，程式自己記帳，加一個 Tkinter 視窗把過程攤開來看。

---

## 一、為什麼要有介面

現在的 `update_excel.py` 是「一次性覆蓋」：跑一次、印一堆字、寫進去。
它沒有記憶，所以只能靠在 Excel 裡多開三格（B9 前日餘額、B10 今日淨收付、
B11 最後更新日）來記住上次做到哪。這有兩個問題：

- Excel 版面被改了，那三格也可能被誤改，改了程式就停下來罵人。
- 人工改過的數字，程式無法分辨是「你刻意改的」還是「算錯了」，只能一律中止。

介面要解決的是後者：**讓程式記得自己寫過什麼，這樣任何跟記憶不符的數字，
就一定是人改的。** 記憶放在程式旁邊的紀錄檔，Excel 就可以完全保持原本的樣子。

## 二、資料放哪裡

| 檔案                                 | 內容                                            | 誰維護   |
|--------------------------------------|-------------------------------------------------|----------|
| `持股管理-台美股-5家.xls`            | B8 現金餘額、E4:E8 股數、F4:F8 成本，其餘全公式 | 人＋程式 |
| `持股管理-台美股-5家-同步紀錄.json`  | 現金帳本、每格自動/手動狀態、上次程式寫入的值   | 程式     |
| `持股管理-台美股-5家-同步歷程.jsonl` | 一行一筆異動，只增不改                          | 程式     |

兩個新檔案放在 Excel 旁邊（同一個資料夾），這樣備份、搬機器會一起走。
檔名跟著 Excel 的檔名走而不是固定名稱：萬一同資料夾裡出現第二份持股表，
兩者的現金基準混在一起是災難級的錯誤，而且不會有任何徵兆。
**紀錄檔掉了不會壞事**：程式只會判定「所有格子都不認得」，全部當成手動、
一格都不敢寫，然後請你重新設定基準。壞掉的方向是安全的那一邊。

## 三、自動 / 手動怎麼判定

每一格**各自**有狀態，不是整個分頁一起切。判定規則只有一條：

```
Excel 現在的值 == 紀錄檔的 last_written   →  自動（程式還管著，可以覆蓋）
Excel 現在的值 != 紀錄檔的 last_written   →  手動（有人改過，程式不准碰）
紀錄檔裡沒有這一格                        →  未接管（登入時自動以 Excel 現值接管）
```

比對時機是**每次執行、抓完網頁資料後讀一次 Excel**。不常駐監看，
免得跟你正在編輯的 Excel 搶連線、讀到打到一半的數字。

### 手動 → 自動：兩種格子答案不同

這是你問的重點。「切回自動會不會怪怪的」，答案分兩半：

**股數、成本 —— 隨時可以切回，不怪。**
這兩個是**快照**，網頁上的庫存就是唯一真相，Excel 只是抄過來。
你手改只是暫時蓋掉，交還給程式就是「以網頁為準重抄一次」，沒有副作用。

**現金餘額 —— 不能直接切回，要重新校正。**
現金是**累加**出來的。網頁只告訴你「今天淨收付 −107」，
從來不告訴你「你現在有多少錢」。所以程式算出的餘額永遠是
`某個基準 + 之後每天的淨收付`。你手動把 786 改成 900 時，程式無法知道
那 114 是什麼，更不知道那 900 裡面**含不含今天的 −107**——
猜錯就是多扣或少扣一次。

所以介面把它做成一個明確的動作，而不是一個開關：

```
┌─ 現金餘額重新校正 ────────────────────────────┐
│ 目前 Excel 的 B8 是  900                      │
│ 程式記得自己寫的是   786                      │
│                                               │
│ 以 900 為新的基準，從今天開始重新累加。        │
│ 這個 900 有沒有已經算進今天的淨收付 −107？     │
│   ( ) 已經算進去了                            │
│   ( ) 還沒算，請幫我扣                        │
│                                               │
│              [ 取消 ]  [ 確定校正 ]           │
└───────────────────────────────────────────────┘
```

按下確定，程式把 `baseline_date` 設成今天、`baseline_value` 設成 900，
並依你的回答決定 `applied["2026-08-17"]` 要不要留著。之後就恢復自動。

**設計原則**：自動轉手動由程式自己偵測、悄悄發生（保護你的手改）；
手動轉自動一定要人按按鈕，而且現金這一格還要多回答一個問題。

## 四、現金帳本：順便解掉「漏跑一天就永遠不準」

> 這一節的逐日累加後來拿掉了，改成每天重新起算 —— 見第十五節。以下是當初的想法。

舊的 B9/B10 模型是「前日餘額 + 今日淨收付」，一旦有一天沒跑，
那天的錢就永遠不會進帳，之後全錯。新的紀錄檔改成按日累積：

```
應有餘額 = baseline_value + sum(applied 裡所有日期的淨收付)

applied = {
  "2026-08-17": -107,
  "2026-08-18":  240,
  "2026-08-19":    0
}
```

同一天重跑就是覆蓋 `applied[今天]`，跑幾次結果都一樣。
更重要的是**漏跑變成看得見、補得回來**：介面比對 `applied` 的日期
跟基準日至今的交易日，缺哪天就列出來，你可以去網頁的對帳單查那天的數字、
在介面上補登，餘額立刻算對。這是舊模型做不到的。

（交易日清單可以用既有的 `CMD=transDateQuery` 拿，不必自己算國定假日。）

**寫不寫 Excel，只由「程式自動更新」這一個開關決定**

勾起來：按「讀取網頁資料」讀完就自己備份、寫進 Excel、更新紀錄檔，
中間不再問一次 —— 意願在按下按鈕之前就已經表達過了。
取消勾選：程式一格都不碰，同步分頁只是對照表，數字由人自己在 Excel 改。
（原本右下角還留著一顆「寫入」當逃生口，後來拿掉了 —— 真的想讓程式寫，
把開關勾起來再讀一次就是了，不必有第二條路。）

原本每一格前面都有勾選框、外加全選／全不選。20 個帳號、上百格的規模下
沒有人會一格一格看，同一件事有兩層開關只是多一次誤判的機會，所以全部拿掉。
個別格子的保護沒有消失：人工改過的格子在同一次執行中仍然是「手動」，
下次登入才會以 Excel 上的新數字重新收成起點（見第十一節）。

開關記在紀錄檔的 `settings.auto_write`，下次打開沿用。
一個決定「程式會不會動你的檔案」的開關，不該每次啟動就自己跳回自動。

**歷程分頁**

```
交易人  簡嘉懋 ▾    項目  現金餘額 ▾    期間  今天 ▾

08/17 11:30  程式  簡嘉懋 B8   893 → 786    今日淨收付 −107（3 筆成交）
08/17 11:30  程式  簡嘉懋 E5   500 → 600    未實現損益 成交股數
08/17 14:02  人工  簡嘉懋 B8   786 → 900    ← 08/18 09:15 執行時偵測到，已轉手動
08/18 09:16  校正  簡嘉懋 B8   基準改為 900（08/18 起算，今日淨收付尚未計入）

篩出 3 筆／共 943 筆，最新的在最上面。
```

人工那一筆的時間標的是**偵測到的時間**，不是你實際改的時間——程式沒在看，
只能事後從差異推回來，介面上會明講這件事，不要假裝知道。

上面三個選單是必要的：20 個帳號跑幾天就是近千筆，一路捲下去等於找不到。
人要問的問題永遠長成「某個人的某一格，今天怎麼了」，所以就照那句話拆成
交易人、項目、期間三層，都不選時維持原本的全部列出。

項目清單跟著交易人走 —— 選了人就只列那個人有的格子，沒選人才列全部。
把 20 個帳號上百格攤平在同一個下拉選單裡，跟沒有篩選是一樣的。
清單的順序是現金在最前面，其餘照股票分組（同一檔的股數排在成本前面）：
照字串排會讓同一檔股票的兩格隔開幾十列，但人是先想到股票才想到看哪一格。

期間只給「今天」與「近 7 天」兩個級距。歷程回答的是「剛才那次執行做了什麼」
與「這幾天有沒有人動過」，再細的區間要多一個日曆元件跟一整套錯誤處理，
換來的是沒有人真的會用的功能。「今天」是每次重畫時現算的，不是開程式那一刻的
日期 —— 這支程式常開著過夜，跨過午夜還停在昨天的話，剛跑完的那批會整批不見。
時間欄壞掉的紀錄只有「全部」看得到：把它當成今天等於憑空生出一筆今天的異動，
而歷程是拿來對帳的東西。

## 六、程式怎麼拆

現在都擠在 `update_excel.py`。要接介面就得把「抓資料 / 算 / 寫」拆開，
因為 Tkinter 得在自己的執行緒跑，Playwright 和 Excel COM 不能卡住畫面。

| 檔案              | 職責                                                      |
|-------------------|-----------------------------------------------------------|
| `login.py`        | 不動。登入、開瀏覽器                                      |
| `recon.py`        | 不動。AJAX 重放                                           |
| `fetch.py`        | 從 `update_excel.py` 抽出 `collect()`，只負責回傳網頁資料 |
| `ledger.py`       | 紀錄檔讀寫、自動/手動判定、現金帳本計算、歷程追加         |
| `excel_io.py`     | COM 開檔、讀 B8/E/F、寫入、備份。只認得這三處             |
| `planner.py`      | 網頁資料 × Excel 現值 × 紀錄檔 → 一張「變更提案」清單     |
| `ui.py`           | Tkinter 視窗，唯一有畫面的檔                              |
| `update_excel.py` | 保留無介面模式，改成呼叫上面那些模組                      |

`planner.py` 產出的每一列長這樣，介面直接照著畫，不用再自己算：

```python
{
  "cells": ["E5", "F5"], "label": "聯發科(2454)",
  "current": (500, 900), "web": (600, 880), "proposed": (600, 880),
  "state": "auto",            # auto / manual / untracked / web_missing / excel_missing
  "checked": True,
  "note": ""
}
```

執行緒切法：按下「讀取網頁資料」→ 背景執行緒跑 Playwright 和 COM 讀取 →
結果丟回主執行緒畫表格。寫入也一樣。畫面全程可以按取消。

## 七、既有的安全機制要留著

- 寫入前備份，保留最近 10 份。
- Excel 已經開著就接上那個實例，直接寫、直接存檔。不留 Ctrl+S 那一步 ——
  紀錄檔在寫入成功後就記成寫過了，人沒按 Ctrl+S 就會讓帳本跟檔案分家，
  畫面上還不會有徵兆。要反悔用寫入前那份備份。
- 每一列都驗 `bhno`/`cseq`，擋掉多帳號時 session 被頂掉抓到別人資料。
- 網頁沒有的股票**不自動清空**，只提醒。
- 「未實現損益顯示今天有成交，但淨收付是 0」（收盤結帳後查不到）仍然要擋，
  但改成只擋現金那一列，持股照樣可以寫——不必整份中止。

## 八、做的順序

| 階段 | 內容                                                            | 能驗收什麼                   | 狀態 |
|------|-----------------------------------------------------------------|------------------------------|------|
| 一   | 拆模組、`ledger.py` 上線，拿掉 B9/B10/B11，CLI 先跑通新帳本模型 | 命令列試算結果跟現在一致     | 完成 |
| 二   | Tkinter 主畫面：讀取、表格、寫入                                | 不用看命令列就能完成一次同步 | 完成 |
| 三   | 歷程分頁、現金帳本分頁、補登、重新校正                          | 手改一格再跑，看得到它變手動 | 完成 |
| 四   | 併進 `tbb-login.exe`，或另做一支 `持股同步.exe`                 | 目標機器雙擊就能用           | 完成 |

介面在 `ui.py`，執行方式是雙擊 `持股同步.bat` 或 `python ui.py`。
登入、抓網頁、開 Excel 全在背景執行緒（COM 前要先 `CoInitialize`），
背景只回傳純資料、由主執行緒畫，不在背景碰任何 widget。

打包成單一 exe，三個進入點靠參數切換（`login.py` 的 `route()`）：

    tbb-login.exe            自動登入（不變）
    tbb-login.exe --sync     持股同步介面
    tbb-login.exe --update   持股同步命令列版

`dist\持股同步.bat` 由 `build.ps1` 動態產生。實測到兩個「只有在目標機器上
才會現形」的坑，都已修掉：`tkinter` 原本被 `--exclude-module` 排除，
留著的話打包成功、一執行 `--sync` 才會炸；`.bat` 內容一度混了中文註解，
cmd.exe 靠系統 OEM 編碼解析 .bat（不保證是 UTF-8），實測會把註解片段
誤判成指令去執行，改成純 ASCII 並用完整路徑呼叫 exe
（有些機器設定 `NoDefaultCurrentDirectoryInExePath` 後，
cmd.exe 不會在目前目錄搜尋不帶路徑的指令名稱）。

階段一實際拆出來的檔案：`util.py`（數字與寬度對齊的小工具）、
`excel_io.py`（只認得 B8/D/E/F 的 COM 讀寫）、`ledger.py`（紀錄檔與現金流水）、
`planner.py`（純計算，產出變更提案）、`fetch.py`（登入抓資料）。
`update_excel.py` 只剩命令列介面。介面版之後直接接 `planner` 的提案清單就好。

拿掉 B11 最後更新日還順手消掉一個陷阱：程式不再需要把日期寫進 Excel，
原本 pywin32 把 datetime 當本地時間換算成 COM 日期、少一天導致重複扣款的問題
就不存在了（日期現在只存在紀錄檔的 ISO 字串裡）。

### 第一次啟動要做的事

現在 Excel 的 B8 = 893，而且**你已經手動扣過今天的 −107 了**。
紀錄檔還不存在，所以第一次開介面會跳設定精靈，問三件事：

1. Excel 檔在哪、哪個分頁對哪組帳號（分頁名 = 帳戶名，可自動猜）
2. 現金基準：以目前的 893 為準，基準日填今天
3. 這個 893 含不含今天的 −107？→ 你答「含」，程式就把 `applied["2026-08-17"] = -107`
   記起來，之後今天再跑不會重複扣

持股那邊不用問，第一次執行就以網頁值全部接管。

## 九、還沒決定的事

- **多帳號**：紀錄檔已經用分頁名當 key，20 個分頁不用改結構。
  但介面上是一次跑一組、還是一鍵跑完全部？後者要處理 session 被頂掉的問題
  （每登入一組就立刻抓完），畫面上要有進度。等真的有多組再說。
- **交易日清單**：`transDateQuery` 回傳範圍多長還沒實測，
  漏跑偵測的可靠度看它。先做成「基準日至今每個工作日」的粗略版本也可以用。
- **補登的來源**：現在只能人工輸入。對帳單查詢頁（`type=2`）能不能回查
  某一天的淨收付還沒偵察，可以的話就能自動補。

## 十、模擬多帳號（測試用）

手上只有一組真帳號，但要跑的是 20 組。介面、Excel 20 個分頁、紀錄檔與現金帳本
在這個規模下順不順，不該等到拿到 20 組帳密才知道，所以補了一套模擬：

真的那一組照原本流程登入，另外 19 個在**同一個瀏覽器**各開一個分頁，
放一頁程式自己畫的假網頁（`page.set_content`，不連任何網站）。假網頁把資料放在
`window.__SIM__`，`fetch.py` 對假帳號改成呼叫它而不是打 `MainController`，
回傳的形狀跟真 API 一模一樣，所以 planner / ledger / excel_io / ui 都不知道有假帳號這件事。

| 檔案                     | 職責                                                |
|--------------------------|-----------------------------------------------------|
| `dev_tools/simulate.py`  | 假帳號清單、隨機資料、假網頁 HTML、開分頁與讀回資料 |
| `dev_tools/sim_excel.py` | 在 Excel 補上／移除模擬分頁（交易人A～S）           |
| `.env`                   | `SIMULATE_ACCOUNTS=19`，沒設就等於整套模擬不存在    |

開起來的順序：

1. `python dev_tools/sim_excel.py --write` —— 複製 19 個分頁（範本就是真分頁，公式全部保留）
2. `.env` 設 `SIMULATE_ACCOUNTS=19`
3. `python update_excel.py --adopt --today=pending --write` —— 一次接管 20 個分頁
   （介面上一格一格按是 200 格，不現實）
4. `python ui.py` —— 登入、讀取（自動更新開著就會直接寫），跟平常一樣操作

隨機值的種子是（帳號名 + 日期），所以同一天重讀網頁資料數字不變 ——
剛好可以驗證「同一天重跑不會重複扣現金」。要換數字就按假網頁上的「重新隨機」。
股數、成交均價、市價、當日成交在頁面上都是輸入格，改完立刻生效，
可以自己擺出特定情境（某檔股數改成 0 = 網頁庫存沒這檔）。

**測不到的**：20 個分頁裡只有 1 個真的在跟網站講話，所以「多帳號共用 JSESSIONID
會互踢」這個真正的風險模擬不出來，那只有真的 20 組帳號才驗得出來。
`fetch.py` 那道「每一列的 bhno/cseq 要等於這個分頁登入的身分」的檢查照樣會跑
（假資料的 bhno 也照真 API 的規則帶開頭那個 1），所以檢查本身有被測到。

**收乾淨**：`python dev_tools/sim_excel.py --remove --write` 會刪掉模擬分頁、
從 `同步紀錄.json` 移除對應分頁、把 `同步歷程.jsonl` 裡的模擬紀錄濾掉
（動手前 Excel 與歷程都會先備份）。模擬分頁是加在正在用的那份 Excel 裡，
紀錄檔又是跟著檔名走的，所以清理這件事一定要程式做，手工清不乾淨。

## 十一、登入即初始化（取代「交還給程式」）

原本第一次用、或任何一格沒被程式管過，都要人明確交接一次；現金還要多回答
一題「Excel 上的餘額含不含今天的淨收付」。20 個帳號的規模下，那個對話框
一次列 11 個帳戶，等於逼人在最不確定的時候做最危險的判斷。

現在改成：**開 Excel → 按登入 → 登入成功的當下，Excel 上的股數、成本、
現金餘額直接被收成程式的起點。**

之所以敢不問，是因為時間點選在登入完成、還沒讀網頁資料之前：

```
登入完成      Excel 上的數字 = 今天買賣之前的狀態  →  直接當基準，沒有猜的空間
讀取網頁資料  今天成交了什麼                      →  往基準上加
寫入          基準 + 今天的淨收付                 →  寫回 B8
```

現金基準取 B8 原值，今天的流水先記 0，之後 `commit()` 用真正的淨收付覆蓋掉它。
所以「B8 含不含今天」這一題在登入的當下根本不存在。

**一天只設一次基準**。今天已經設過（多半也已經寫進 B8 了），再設一次會讓
今天的淨收付被加第二次，而且畫面上不會有任何徵兆 —— 所以 `planner.initialize()`
看到 `baseline_date` 已經是今天就跳過，介面的 `_auto_adopt()` 也照同一條規則。

跳過之後那一格當天就沒有出口了。要重新起算只能由人明講 —— 現金那一條底下的
「今日初始現金餘額　[修改]」，見第十五節。

| 動作               | 誰觸發           | 現金基準怎麼定                    |
|--------------------|------------------|-----------------------------------|
| 登入               | 每次按「登入」   | = Excel 的 B8，今天的流水記 0     |
| 讀取後自動接管     | 自動模式，補網用 | = Excel 的 B8，今天的淨收付加上去 |
| 改今日初始現金餘額 | 人自己按「修改」 | = 人填的數字 − 今天的淨收付       |

## 十二、現金帳本分頁拿掉了

第四節那個分頁（基準、逐日流水、補登、重新校正）在登入即初始化之後
沒有存在的必要了 —— 它的三個功能各自被更簡單的東西取代：

| 原本的功能   | 現在怎麼做                                                       |
|--------------|------------------------------------------------------------------|
| 看基準與流水 | 基準寫在同步分頁上（今日初始現金餘額），流水只剩今天一筆         |
| 重新校正     | 直接改 Excel 的 B8，下次登入以那個數字為準（同一天內見第十五節） |
| 補登漏掉的天 | 不必補。基準每天重設，漏跑的那天不影響今天（見第十五節）         |

換句話說，現金的帳還是照記，只是那變成程式內部的事，不再是一個要人看懂、
要人操作的畫面。介面剩下兩個分頁：同步（這次要改哪幾格）、歷程（誰改了什麼）。

## 十三、同步分頁改成「左邊挑人、右邊看一個人」

20 個交易人、每人十幾格，攤平成一張表是兩百多列。實際跑起來的毛病有三個：

- 捲到一半，畫面上那個 `B8 現金餘額` 不知道是誰的 —— 交易人的名字在群組列上，早就捲出畫面了
- 要知道「這次哪幾個人要處理」，只能整份捲一遍
- 整張表比視窗還寬，最右邊的「說明」永遠被切掉

而真正的工作方式是**依序輪詢**：一次只看一個人，看完換下一個。版面就照那個
方式切。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 開啟EXCEL   ...\持股管理.xls —— 已開在 Excel 裡                             │
│ 登入   帳號 全部 ▾         ☑ 程式自動更新    [ 讀取網頁資料 ]               │
├────────────────────┬────────────────────────────────────────────────────────┤
│ 交易人    3/20 位  │ 交易人G（模擬）　第 7/20 位　現金 553,161　要寫 1 格   │
│ ☐ 只看有差異       ├────────────────────────────────────────────────────────┤
├────────────────────┤ 格子 項目            舊值      網頁      新值    狀態  │
│ 姓名  現金餘額 狀態│ E4  股數(2059 川湖)  1,000     1,000     —     自動    │
│ 交易人A ⋯   ✓      │ F4  成本(2059 川湖)  1,307     1,307     —     自動    │
│ 交易人B ⋯ 要寫 2   │ …（一位就十一列，不必捲、不必展開）                    │
│ ⚠ 交易人E ⋯  ⚠     │ B8  現金餘額       553,161   -28,861  -28,307  自動    │
│ 交易人G ⋯ 要寫 1   │ 今日初始現金餘額 553,161  [修改]                       │
│ 交易人L ⋯   ✓      ├────────────────────────────────────────────────────────┤
│ 點一下換人         │ 提醒：只列這一位的                                     │
└────────────────────┴────────────────────────────────────────────────────────┘
```

| 原本                     | 現在                                             |
|--------------------------|--------------------------------------------------|
| 220 列攤平、用群組分隔   | 左邊 20 列名單，右邊固定只畫一位的十一格         |
| 誰要處理要整份捲一遍     | 名單上直接寫「要寫 N ／ ⚠ ／ ✓」，還有現金餘額   |
| 交易人的名字捲走就沒了   | 右邊標頭固定寫著是誰、第幾位、現金多少、要寫幾格 |
| 找下一個群組             | 點一下名單，或 ↑ ↓ ／ Ctrl+↑ ／ Ctrl+↓           |
| 20 個人的提醒堆在同一框  | 只列選中那位的；別人的事名單上用 ⚠ 標著          |
| 表格比視窗寬，說明被切掉 | 少了「交易人」欄就塞得下，說明是唯一會伸縮的一欄 |

**幾個刻意的決定**

「只看有差異的」不記進紀錄檔 —— 它是「這一輪想少看幾個人」，不是一個設定；
勾著的時候，正在看的那一位一定留在名單上，否則勾下去的瞬間畫面會跳到別人身上。

**右下角那顆「寫入」拿掉了**，「上一位／下一位」兩顆按鈕也是。寫入原本是
人工維護模式下的逃生口，但真的想讓程式寫，把「程式自動更新」勾起來再讀一次
就是了；換人則是名單就在左邊，點一下比按按鈕快 —— 兩者都只是同一件事的
第二個入口。留下來的是 Ctrl+↑ / Ctrl+↓：手放在右邊那張表的時候焦點不在
名單裡，那時候還是要能換人。

換人照**名單上真正顯示的順序**走（`_shown()` 直接問 Treeview），不照
`proposals` 的順序算 —— 開了篩選之後兩者會不一樣，而人是照眼睛看到的在數。
`_step_person` 也不等 `<<TreeviewSelect>>`：那個事件要排進事件佇列才送，
「鍵按了、右邊要立刻換」不該押在佇列什麼時候輪到它上面。

**視窗尺寸**：預設 `wide(1180) × wide(720)`，上限是桌面可用區（螢幕扣掉工作列）
再各留一點邊；擺位置由 `_center()` 算，會多扣掉標題列的高度。

高度**不**跟著帳號數長。原本是照人數算到「整份名單一次看得完」，後來拿掉了 ——
名單本來就有捲軸，滑鼠滾兩下的成本，遠低於「20 個帳號就開一個佔滿整個桌面的視窗」。
要一次看完就自己把視窗拉高，或在 `.env` 設 `UI_HEIGHT`。

外觀有三個設定放在 `.env`，都在 import 時讀一次，改完要重開介面：

| 設定           | 沒設時                   | 有設時             |
|----------------|--------------------------|--------------------|
| `UI_FONT_SIZE` | 12                       | 夾在 8～24         |
| `UI_WIDTH`     | `wide(1180)`，跟著字級走 | 當像素用，下限 640 |
| `UI_HEIGHT`    | `wide(720)`，跟著字級走  | 當像素用，下限 400 |

長寬填的數字就是像素，**不再乘上字級**：使用者量的是螢幕上的視窗，不是某個基準
字級下的寬度，把他填的 1400 放大成 1680 只會讓人以為程式沒讀到設定。三個設定
填了看不懂的東西一律當作沒設 —— 外觀設定不值得為了一個打錯的數字讓介面開不起來。

切到歷程分頁時，交易人的篩選會自動跟著同步 —— 切過去通常就是想看剛才那位
的歷程，不必再選一次人。

上面那排「帳號 全部 ▾」留著：它決定的是**登入／讀取哪幾組帳號**，
跟左邊名單（讀完之後看誰）是兩件事，而且第一次登入之前根本還沒有名單可挑。

## 十四、同一天內要改現金餘額

第十一節「一天只設一次基準」擋掉的是一個真的會算錯的情況，但它同時也把當天
的現金餘額鎖死了：改 B8 只會被判成人工改動然後凍住，一直到隔天才解得開。

有兩種情況會真的踩到：

- **紀錄檔遺失後同一天重開**（誤刪、Excel 改檔名或搬資料夾、換一台電腦）。
  這時 `baseline_date` 是 `None`，看起來就像當天第一次開啟，於是把已經含了
  今日淨收付的 B8 當成基準，待會兒再加一次 —— 畫面上不會有任何徵兆。
- **當天發現餘額不對**，想直接把正確的數字交給程式。

### 問「開盤前」，不問「現在的餘額」

第一版問的是「現在正確的餘額（含今天已成交的部分）」，跳在登入完成的當下。
實測第一次就填錯了：使用者看著 Excel 上的 553,161 填進去，意思是「我手上有
這些現金，請把今天的交易減掉」，程式卻理解成「553,161 已經含過今天的
−28,861,068 了」，於是把基準推成 29,414,229，結論是不用寫。**方向剛好相反，
而且畫面上完全看不出來。**

問題不在標籤寫得不夠清楚，在**問的時機**。登入的當下 `login_only` 還沒查網頁，
程式手上沒有今日淨收付，所以只能請人用文字描述自己填的是哪一種數字 ——
那種要人回想今天做過什麼的問題，答錯又不會有徵兆，本來就不該存在。

現在改成跳在**讀完網頁資料、寫入之前**。淨收付已經在手上，於是：

- 問的是「今天開盤前的現金」。它是那個**不會動**的量 —— 今日淨收付盤中還會再變，
  「現在的餘額」講完下一筆成交就過期了。
- 右邊直接把 `B8 會變成多少` 邊打邊算給你看。該不該按，看那個數字就知道。
- 「含不含今天的成交」這個問題整個消失。

### 什麼時候會問

判斷在**登入時**做（`_cash_reset_names`），對話框在**讀取後**跳（`_ask_cash_reset`）。
不能等讀取時才判：那時 `initialize()` 已經把每個分頁的基準都設成今天，
看起來會全部像「今天開過了」。

| 情況                      | 會問嗎 | 為什麼                                                        |
|---------------------------|--------|---------------------------------------------------------------|
| 今天第一次登入            | 不問   | B8 一定還沒含今天的成交，它就是唯一真相                       |
| 今天第二次以後登入        | 問     | B8 可能已經含了今天的成交，程式看不出來                       |
| 這份 Excel 還沒有紀錄檔   | 問     | `baseline_date` 是 None，光看「第幾次」會誤判成第一次         |
| 淨收付信不過（`blocked`） | 不問   | 拿一個已知是錯的 net 去 calibrate，會把今天的成交永久算進基準 |

第三條不能省。它跟第二條看起來像同一件事，但判斷依據完全不同 —— 少了它，
上面那個「紀錄檔遺失」的情況會安靜地算錯一整天。

### 長什麼樣

一個視窗問完所有分頁，不是一個分頁一個對話框 —— 20 個交易人的規模下，
逐一詢問等於逼人按 20 次「不改」，按到第五次就不會再看內容了。

```
┌─ 重設現金餘額 ─────────────────────────────────────────────────┐
│ 今天已經開啟過，Excel 上的現金餘額可能已經含了今天的成交。     │
│ 要改的分頁請填「今天開盤前的現金」，右邊會算出 B8 會變成多少； │
│ 留空表示維持原樣。                                             │
│                                                                │
│  分頁       程式記得     今日淨收付      開盤前      B8 會變成  │
│  交易人A   1,000,000   -28,861,068  [ 553,161 ] → -28,307,907  │
│  交易人B        (空)        -5,120  [         ] →   維持原樣   │
│  ...（超過 8 列開始捲）                                        │
│                                                                │
│                                  [ 全部維持原樣 ]  [ 確定 ]    │
└────────────────────────────────────────────────────────────────┘
```

對不上的分頁（B8 跟程式記得的數字不一樣、或根本沒有紀錄）排在最前面並標色。
光排序不夠 —— 20 列裡真正要看的通常只有一兩列，不標色還是得一列一列讀過去。

### 算出來的東西

`apply_cash_reset()` 就地改掉現金那一列的提案，`commit()` 再交給既有的
`calibrate()`：

```
B8 提議值 = 開盤前 + 今日淨收付          ← 對話框右邊那一欄
calibrate(balance=B8 提議值, today_included=True)
        → baseline = 開盤前              ← 往回推一天份，剛好回到人填的數字
          applied  = { 今天: 今日淨收付 }
```

`today_included=True` 看起來跟「使用者填的是開盤前」矛盾，其實不是：交給
`calibrate` 的是**算完的 B8**，不是人填的數字。這樣走既有的路，不必為了重設
多開一條分支。之後盤中再成交，`baseline` 不動、`net` 變大，餘額就跟著往上加，
不會停在人填的那個數字。

這是唯一能蓋過「手動」狀態的東西。人已經明講了正確的數字，程式沒有理由
再守著一個它自己也知道過時的值。

## 十五、現金改成「今日初始現金餘額」，每天重新起算

這一節推翻兩件事：第十四節那個「重設現金餘額」對話框（拿掉了），
以及第四節、第十二節留下來的跨日累加（不算了）。

### 一個算式，兩項

```
現金餘額（B8） = 今日初始現金餘額 + 今日淨收付
                 ↑ 今天第一次登入      ↑ 網頁抄來的
                   時 Excel 上的 B8       不會錯
```

右邊那項不會錯，所以餘額不對的時候，錯的一定是左邊那項。既然如此，它就該
一直看得到、一直改得動 —— 現金那一條底下固定寫著這一行，旁邊一顆「修改」。

### 不回頭算舊帳

原本的模型是「基準只設一次，`applied` 把每天的淨收付一路往後疊」，好處是漏跑
的那天看得見、補得回來（第四節）。實際上沒有人會去補：要補得回頭查那天的對帳單，
而更簡單的做法一直都在 —— 今天的 B8 就寫在眼前。

所以改成**每天重新起算**：只要基準日還不是今天，登入就把 B8 收成今天的起點，
不管它昨天是自動還是手動、昨天有沒有跑過。

| 原本                                  | 現在                                     |
|---------------------------------------|------------------------------------------|
| `baseline` 設一次，`applied` 逐日累加 | `baseline` 每天重設，`applied` 只有今天  |
| 漏跑一天要補登，不補就少一段          | 漏跑不影響今天 —— 起點就是今天看到的 B8  |
| 缺哪個交易日要算、要提醒              | 沒有這種提醒了（`missing_dates` 已移除） |

`applied` 這個字典留著：同一天重跑只是覆蓋同一個 key，跑幾次結果都一樣。
舊紀錄檔裡多天的資料不必轉檔，今天第一次登入就會被重設成只剩今天一筆。

### 對話框換成按鈕

第十四節那個對話框由程式判斷「今天可能已經開過了」才跳，一次問完所有分頁。
猜錯的兩個方向都很貴：

- 不該問的時候問 —— 20 個分頁列在同一個視窗，按到第三次就沒人在看內容了
- 該問的時候沒問，或跳的時候填錯 —— 當天再也沒有入口，只能等明天

數字一直在畫面上、按鈕一直按得動，就不必由程式決定什麼時候該問誰。
問法與算法整個沿用（`planner.apply_cash_reset`），只是改成一次一位。

| 情況                         | 顯示                | 「修改」 |
|------------------------------|---------------------|----------|
| 還沒選到人（還沒讀網頁資料） | `—`                 | 灰       |
| 紀錄檔還沒有基準             | `(還沒設定)`        | 灰       |
| 正常                         | `1,234,567`         | 亮       |
| 剛按過修改、還沒落帳         | `1,234,567 → 5,000` | 亮       |
| 淨收付信不過（`blocked`）    | 照常顯示            | 灰＋理由 |

沒有網頁資料就不給改：新的 B8 是「開盤前 ＋ 今日淨收付」，沒有淨收付算不出來，
也就沒有東西可以寫回去。`blocked` 的理由跟第十四節同一條 —— 拿一個已知是錯的
淨收付去 calibrate，會把今天的成交永久算進基準裡。按鈕變灰時理由就寫在旁邊，
灰掉而不說為什麼看起來就像壞了。

### 按下去之後

落實的方式跟著「程式自動更新」走，不另外開第三條路：

| 開關 | 做什麼                                                          |
|------|-----------------------------------------------------------------|
| 勾著 | 直接寫進 Excel 並落帳；算出來剛好等於 B8 時不必寫，但一樣要落帳 |
| 沒勾 | 只把建議值畫成「舊 → 新」，Excel 由人自己改，紀錄檔一個字不動   |

「不必寫也要落帳」是第十四節就有的坑：基準確實被人改掉了，這一筆不記，
下一次讀取會拿沒被修正的基準再算一次，今天的淨收付就被加了第二次
（見 `_commit_round` 的註解）。

### 換來的代價

拿掉對話框之後，有一種情況不再有人主動提醒：**紀錄檔遺失後同一天重開**
（誤刪、Excel 改檔名或搬資料夾、換一台電腦）。那時 `baseline_date` 是 `None`，
看起來就像今天第一次登入，於是已經含了今日淨收付的 B8 被當成起點，待會兒再加
一次。原本第十四節的第三條規則就是為了接住它。

現在接住它的是畫面本身：那個數字就寫在現金餘額底下，跟「今日淨收付」上下並排。
起點被算成含了今天的成交，這一行會明顯偏高 —— 看到不對就按「修改」。
用「一直看得到」換掉「程式挑時機提醒」，是這一節整個的交易。

### 說明放在哪裡

「看到不對就按」要成立，前提是使用者知道什麼算不對。真正會走到那顆按鈕的路只有
一條：**人自己在盤中改過 B8**。他改進去的是「現在正確的餘額」，那個數字已經含了
今天的成交，照抄成開盤前就等於把今天的淨收付算進起點裡，待會兒再加一次。
這件事沒有任何檢查擋得住 —— 兩個數字都是合法的金額，錯的那個要到明天才看得出來，
所以只能用講的。三個位置各講一段，愈靠近出錯的當下講得愈細：

| 位置                 | 說什麼                                                         |
|----------------------|----------------------------------------------------------------|
| 「修改」旁邊那行灰字 | 這個數字＝今天第一次登入時的 B8；那時它已含今天成交才要按      |
| 提醒框最後一行       | 今天別改檔名、別自己改 B8；真改了就用「修改」補開盤前的金額    |
| 對話框（按下去之後） | 開盤前的定義、`B8 − 今日淨收付` 算好擺著附「帶入」、填錯的後果 |

對話框裡那一行「B8 已經含了今天的成交的話，開盤前是 X」是最實際的一項：需要按這顆
按鈕的人，手上有的正好是 B8，缺的正好是那個減法。算好擺著、再給一顆「帶入」，
比請他自己心算一次再賭算得跟程式一樣可靠。

提醒框那一句排在最後一行，因為那個框只有五行高又沒有捲軸：常駐的字排在前面會把
當天真正的警告推出視線；排最後的話，沒事的日子看得到（框是空的），
有事的日子被擠掉的正好是它。

另一個弄壞今天起點的方式是**改 Excel 檔名或搬資料夾**（紀錄檔跟著檔名走，
換了名字就變成「紀錄檔遺失後同一天重開」）。它跟手改 B8 是同一種傷害，
所以講在同一句話裡 —— 分成兩條提醒，讀的人不會知道那是同一件事。

## 十六、一次只更新一位交易人

原本一顆「讀取網頁資料」永遠是全部：19 個帳號逐一登入、逐一查、逐一寫，
跑一輪要好幾分鐘。但盤中真正在看的通常只有一位 —— 剛下完單的那一位。
為了看他一個，得把另外 18 個人重讀一次，而那 18 個人的資料還會被順手寫進 Excel。

### 範圍就是「按下去會動到誰」

上面那個下拉選單從「帳號（全部／第 N 組）」改名成「範圍」，並且跟左邊的名單
接成同一個選擇的兩個入口：

- 名單上點一位 → 範圍換成他，按鈕改名成「更新（王小明）」
- 範圍換一位 → 名單跳到他，右邊也跟著換人

按鈕上的字就是這一節的全部重點：按下去會動到誰，寫在按鈕上，
不必回頭去確認那個下拉選單現在停在哪一列。

| 範圍                | 按鈕字樣                | 按下去做什麼                       |
|---------------------|-------------------------|------------------------------------|
| 全部                | 讀取網頁資料            | 每一組都登入、都查、都寫           |
| 第 3 組（名字已知） | 更新（王小明）          | 只查他、只寫他那一頁               |
| 第 3 組（名字未知） | 讀取網頁資料（第 3 組） | 一樣只做那一組，只是還說不出他是誰 |

名字為什麼會未知：`.env` 裡只有帳密，交易人的名字要登入之後才從網站的
sessionStorage 拿得到（見 `fetch.collect` 的 `sheet_name`）。所以對照表是一邊做
一邊長出來的，模擬帳號例外 —— 它的名字本來就寫在 `.env` 裡，一開機就填得進去。

### 預設仍然是「全部」

左邊那份名單是網頁資料長出來的，沒讀過一輪之前它是空的，也就沒有人可以點。
一天的動線因此還是：開盤前讀一次全部（順便把名單與名字都建起來），
之後整個交易時段都在「點一位 → 更新（他）」。

### 只更新一位，要守住三件事

**一、讀到的是補上去，不是整份換掉。** 名單上其他人手上那份是上一輪的資料，
清掉他們等於整份名單只剩一個人。`records`／`sheet_data`／`read_at` 全部改成合併。

**二、畫面上同時有好幾個時間點的資料。** 所以每一位都記著自己的讀取時間，
右邊標頭寫「讀取於 10:32」。沒有它，半小時前讀的數字跟剛讀的長得一模一樣
—— 這是這個改動最容易讓畫面說謊的地方。

**三、寫入、落帳、接管只能碰這一輪讀到的那幾位。** 介面多了一個 `round_scope`，
`_collect_writes`、`_commit_round`、`_auto_adopt`、寫入後的回填四處都照它。
名單上別人也可能有「要寫」的格子，那是用上一輪的網頁資料算出來的
—— 順手寫出去就是拿舊資料改 Excel，而且沒有人要求過。
現金那顆「修改」也一樣：按的時候把範圍縮到眼前這一位。

失敗原因跟著改成掛在「第幾組」上，不再是每讀一次就整串重來：只更新一位的時候，
別人上一輪沒完成的事並沒有因此解決，那些 ⚠ 要留到那一組自己再讀一次成功為止。

### 換人不重登：把 cookie 換回去

整個瀏覽器只有一組 cookie（`JSESSIONID`），所以同時只帶得動一個人的身分，
後登入的會把前一個頂掉。這常被講成「一次只能登入一個帳號」，但那句話只對一半：

| 哪一邊 | 20 組同時登入 | 為什麼                                                        |
|--------|---------------|---------------------------------------------------------------|
| 瀏覽器 | 做不到        | 一個 context 一組 cookie，`JSESSIONID` 只有一個值             |
| 伺服器 | 本來就是      | 20 個不同身分證＝20 個各自獨立的 session，B 登入不會殺掉 A 的 |

A 被頂掉的意思只是「暫時沒有人帶著他的 cookie 去敲門」，他在伺服器上還活著。
所以換人這件事在程式裡不是「重新登入」，是**換一組 cookie**：

1. 按「登入」時 20 組照樣一次跑完，每一組登入完就把當下整份 cookie 收進 `store["jars"]`
2. 「更新（王小明）」時先把他那份 cookie 換回瀏覽器（`clear_cookies` + `add_cookies`），
   回帳戶頁確認一下，就直接查 —— 不必跑登入流程，連驗證碼都省了
3. 確認不過（那一組在伺服器上逾時了）才真的重登一次

三條路的成本差很多，而盤中最常走的是前兩條：

| 情況                       | 做什麼                 | 成本           |
|----------------------------|------------------------|----------------|
| 剛才就是他（連按同一位）   | 回帳戶頁確認一下       | 最快           |
| 換人、他的 cookie 還有效   | 換回 cookie 再確認一次 | 快，不必驗證碼 |
| 換人、他已經在伺服器上逾時 | 整套登入流程跑一遍     | 慢             |

換 cookie 換不回去的唯一原因是 session 逾時，那時候走的是原本就有的重登，
所以這個機制最壞的結果等於沒有它，不會更糟。

**確認身分那一道不能省。** 分頁自己的 `sessionStorage` 不會因為 cookie 被換掉就失效
——只看它的話，一個早就被頂掉的分頁探起來一樣「還活著」，照它走就會拿到別人的資料
寫進別人的 Excel。所以 `_revisit` 三道一起看：還在帳戶頁、`sessionStorage` 有值、
而且身分跟這一組登入時記下來的帳號代號相同。`collect` 裡原本那道「每一列的
`bhno`／`cseq` 要跟登入身分相符」照樣留著當最後一道。

還有一個門檻在登入本身：瀏覽器裡已經有人登入著的時候，網站不會再給登入表單
（看到 cookie 就把人導去別的頁），`do_login` 的選擇器只會白等到逾時。所以等不到
表單就清掉 cookie 再回登入頁一次 —— 那是網站認人的唯一依據，清掉就等於登出。
憑證不在 cookie 裡（它在 Windows 的憑證存放區與這個 Chrome profile 裡），
不會被這一步弄掉。

**還沒實測。** 這台機器上真帳號只有一組（另外 19 個是不連網的模擬帳號），
「換人」這件事跑不到。要驗的是兩件事：換回去的 cookie 網站認不認、
以及 session 大概多久逾時（逾時之後就會退回重登那條路）。

### 沒有改的東西

- 「程式自動更新」還是那一個開關，只更新一位照樣是讀完就寫
- 判斷、提案、落帳全部還是 `planner`／`ledger` 那一份，介面只決定範圍
- 一次讀全部的行為跟以前一模一樣（範圍留在「全部」就是了）

## 十七、把 Excel 搬進來，Excel 降成存檔

2026/08/19 定的方向，還沒動手。這一節是動手前的規劃。

### 為什麼：工具從三項變回兩項

原本操作一天的交易只碰兩樣東西：網頁跟 Excel。這支程式做成「橋樑」之後變成三樣，
而且多出來的那一樣沒有取代掉任何東西 —— 三項工具的使用頻率是不平均的：

| 工具  | 一天用幾次                                     |
| ----- | ---------------------------------------------- |
| 網頁  | 下單的時候                                     |
| Excel | **整天都在按**（更新股價 → 填比重 → 自動計算） |
| 程式  | 一次（收工同步）                               |

所以現在的問題不是「多了一個工具」，是**多了一個工具，但整天在用的那個沒被吸收**。
把 Excel 上那四個動作搬進程式，剩下的就是「網頁下單」跟「其他全部」，這才是兩項。

順帶會發生一件現在辦不到的事：**「今天該買幾股」跟「今天實際成交了什麼」
會第一次出現在同一個畫面上**。前者現在在 Excel、後者在這支程式，中間隔著人的眼睛。

使用者確認過每天在 Excel 上的動作只有四個：按「更新」抓股價 → 填 5 個預計比重 →
按「自動計算」→ 看下單試算。換股的時候多一個「刪掉舊的、加進新的」。
**沒有在空白格即興算東西、沒有整欄複製貼上、沒有開多分頁對照** ——
這是這個方向成立的前提，因為 Excel 唯一換不回來的東西就是那種即興自由。

### 省下多少：2026/08/19 實測

「真的省得到時間嗎」這個問題量得出來，不必猜。以下在模擬檔上實測
（Excel 隱藏執行，比實際看得到畫面的情況**還快**，所以是現況成本的下限）：

| 動作     | 一個分頁 | 20 個分頁    | 搬進來之後                 |
| -------- | -------- | ------------ | -------------------------- |
| 更新股價 | 2.98 秒  | 約 60 秒     | 1.15 秒（見下）            |
| 自動計算 | 1.65 秒  | 約 33 秒     | 純算術，20 人合計不到 1 秒 |
| 合計等待 |          | **約 93 秒** | **約 2 秒**                |

**關鍵在於那支 Yahoo 端點吃得下多個代號，而巨集完全沒用到。**
`更新股價` 是一檔一個請求、一個分頁跑一輪，20 個分頁就是 100 次請求。
但實測 `symbols=2059,2344,2408,6213,6274,0050` 一次帶六個代號會回六筆，只要 1.15 秒。
而且 19 個模擬交易人**持有完全相同的 5 檔、預計比重也完全相同**（0.2 × 5 等權重），
只有股數、成本、現金不同 —— 也就是說那 100 次請求裡真正不重複的只有 5 個代號。

除了機器的等待，人的操作也從「切 20 次分頁、按 40 次按鈕、讀 20 次結果」
變成「按兩次、看一張 20 人 × 5 檔的表」。

**第二層的好處比省下的秒數更值錢**：現在跑一輪要好幾分鐘，所以一天大概只跑一次；
如果只要半分鐘，盤中想跑就跑，看到價格動了就重算一次。這是行為上的差別，不只是快慢。

**但要誠實看待這件事在整天裡的比例。** 上面省的全部發生在「決策」那一段。
「下單」那一段（20 人 × 最多 5 檔 = 最多 100 筆單要在網頁上打）一秒都沒省，
而它很可能才是整天最花時間的。所以動手之前值得先拿碼表量自己一輪的真實時間，
分成決策／下單／記帳三段記 —— 機器的時間我量得到，人的時間只有使用者量得到。
如果下單那段佔了大半，那下一個該做的其實是「把 20 人的單匯出成一張可以照著打的清單」
（那是這條路順手就能長出來的東西），而不是再優化決策那一段。

### 為什麼不是反過來（Excel 當主控台）

`todo.txt` 裡有一份相反方向的規劃：Excel 上加按鈕（VBA）→ 本機小埠 →
常駐 Python 進程 → COM 寫回 Excel。它一樣收到兩項工具，開發量還小得多。
不走它的理由有四個，前兩個是查了巨集才發現的：

**一、`自動計算` 巨集會反覆寫壞程式負責的那三塊格子，而且整支沒有錯誤處理。**
它的做法是把 Excel 的格子當變數用 —— 迭代過程中反覆把試算股數寫進 `E4:E8`、
重算成本寫進 `F4:F8`、現金寫進 `B8`，讓 Excel 重算公式，再讀 `F14:F18` 的比重
回來看收斂了沒，收斂之後才復原。而 361 行 VBA 裡一個 `On Error` 都沒有
（`自動計算` 尾巴那個 `over:` 是沒人跳的死標籤）。迭代中途炸一次，復原就不會跑，
Excel 上留著看起來完全正常的模擬值 —— 下次同步一比對，`last_written` 對不上，
那幾格判定成「人手改過」轉手動，從此不再更新，畫面上不會說是為什麼。
搬進來之後這支東西變成純函式，問題直接消失。

**二、「人正在編輯儲存格」會擋掉 COM 寫入，而 VBA 沒有 `finally`。**
非同步 XMLHTTP + `DoEvents` 解掉的只是「同步 send 鎖死訊息幫浦」那一半；
`DoEvents` 讓 Excel 恢復回應的同時也讓人能繼續打字，游標停在儲存格編輯模式裡
的時候外面的 COM 寫入會被拒。標準解法是等待期間 `Application.Interactive = False`
把鍵盤擋掉，但 VBA 沒有 `try/finally`，只要那段中途出錯而沒還原，
**Excel 會變成打不了字，只能強制關掉**。

**三、本機小埠沒有身分驗證就等於開了一個「誰都能叫它操作券商帳號」的介面。**
常駐進程握著已登入的瀏覽器與憑證，埠開著的期間本機任何程式（含瀏覽器裡的網頁）
都打得到它。至少要綁 `127.0.0.1`、每次啟動產生隨機 token 寫檔、VBA 讀檔帶在標頭。

**四、那份規劃自己的第四點已經承認工具數是 2.5** —— 第一次接管與 `B8` 修改
程式不能猜，所以開盤前仍要開一次介面。變成「大部分時候兩項、每天開頭三項」。

兩條路的差別歸根究柢在成本的形狀：Excel 當主控台前期便宜，
但把整類併發與生命週期問題永久留在系統裡（Excel 突然卡住、值被還原、
格子莫名轉手動、常駐進程半夜死掉隔天才發現），而且全部發生在 VBA 那一側 ——
沒有 log、沒有堆疊、只有 MsgBox。搬進來則是一次付清，
移植風險可以用「逐格對帳」壓到接近零。

### 那 15 條公式

`i` = 持股列 4~8，`j` = 對應的狀態列 14~18（`j = i + 10`）。
`B5` 是手續費率，`0.003` 是證交稅：

| 名稱       | 位置      | 算法                                                                  |
| ---------- | --------- | --------------------------------------------------------------------- |
| 總成本     | `E{j}`    | `E{i} * F{i} * (1 + B5)`                                              |
| 成本比重   | `F{j}`    | `E{j} / E20`                                                          |
| 市值       | `G{j}`    | 令 `v = E{i}*I{i}*(1+H{i}/10)`，則 `v - floor(v*B5) - floor(v*0.003)` |
| 市值比重   | `H{j}`    | `G{j} / G20`                                                          |
| 損益       | `I{j}`    | `G{j} - E{j} + G{i} * E{i}`（加回現金股利）                           |
| 報酬率     | `J{j}`    | `I{j} / (E{i} * F{i} * (1 + B5))`                                     |
| 現金列     | `E19,G19` | 都等於 `B8`                                                           |
| 合計       | `E20,G20` | `SUM(E14:E19)`、`SUM(G14:G19)`                                        |
| 加買金額   | `N{i}`    | `(M{i} - F{j}) * E20`                                                 |
| 加買股數   | `O{i}`    | `floor(N{i} / (I{i}*(1+B5)))`                                         |
| 總淨值     | `B13`     | `G20 + SUM(G{i} * E{i})`                                              |
| 全部損益   | `B14`     | `B13 - B6`（原始資金）                                                |
| 全部報酬率 | `B15`     | `B14 / B6`                                                            |
| 今年損益   | `B16`     | `B13 - B7`（今年股本）                                                |
| 今年報酬率 | `B17`     | `B16 / B7`                                                            |
| 交割款     | `O{j}`    | 見下（買賣兩段，含最低手續費）                                        |
| 剩餘現金   | `O19`     | `SUM(O14:O18) + B8`                                                   |

交割款 `O{j}`，其中 `m` = 加買股數 `M{j}`、`p` = 股價 `N{j}`，整條外面包 `ROUNDDOWN(…, 0)`：

- `m == 0` → `0`
- `m > 0`（買）→ 手續費 `m*p*B5` 大於 1 就 `-m*p*(1+B5)`，否則 `-m*p - 1`
- `m < 0`（賣）→ 手續費 `-m*p*B5` 大於 20 就 `-m*p*(1-B5-0.003)`，否則 `-m*p*(1-0.003) - 1`

### 自動計算到底在算什麼

一句話：**給定每檔的「預計比重」，反推要買賣幾股，使成交後每檔的「成本比重」
逼近預計比重（誤差 < 0.1%），且現金剩下 `(1 - 預計比重總和) × 總淨值`。**

這是個沒有解析解的問題（買了會改變總成本，總成本又是比重的分母，
再加上手續費、證交稅、無條件捨去到整股），所以巨集用迭代逼近：

1. **檢查輸入** —— 股票全空、有股數無股號、有成本無股號、股價沒填、
   比重總和 > 100%、比重是負數。任何一項就跳 MsgBox 中止。
2. **記下原狀** —— 原始股數、原始成本、原始現金（存 `Formula` 不是 `Value`），
   以及每一檔原本是買還是賣（看 `N` 欄加買金額是不是負的）。
3. **外層迴圈**：跑一次 `Sim_trade` → 把結果填進下單試算 → 復原 →
   用下單試算的結果重新套一次（先算成本再算股數）→ 檢查每檔
   `|成本比重 - 預計比重| ≤ 0.001` 或加買股數為 0，不符就再來一輪。
4. **`Sim_trade` 內層迴圈**：每一檔決定這一輪動幾股 ——
   預計比重為 0 而還有股數就全賣；比重誤差已在 0.1% 內就 0；
   否則照 `O` 欄的加買股數；但「原本是賣、這輪也是賣、而且賠錢」時
   改成一次只賣 1%（`Round(股數 * 0.01, 0)`）。套用之後檢查收斂。
5. **多餘現金處理** —— 現金比預期多，就找比重差距最小（最負）的那檔加 1 股，
   重算成本、扣現金，直到現金不再多。
6. **現金小於 0 處理** —— 反過來找比重差距最大的減 1 股。
7. **預計比重剛好 100% 時的零錢處理** —— 剩餘現金還買得起最便宜那檔，
   就找「股價不超過剩餘現金之中最貴的」加 1 股，直到買不動。
8. **手續費誤差造成剩餘現金 < 0** —— 最便宜那檔減 1 股，直到不為負。

### 移植這支求解器的六個坑

**一、不要照抄「拿格子當變數」的寫法。** 巨集之所以那樣寫是因為 VBA 手上
只有 Excel 的重算引擎可用。搬過來之後狀態是一個 dict，每一輪重算是一次
純函式呼叫 —— 快得多，而且看得到每一輪的中間值。

**二、`twenty_fee_given` 的初始值就是 `True`，可能是 bug。**
外層一開始把每一檔的 `twenty_fee_given(i)` 都設成 `True`，
而 `Sim_trade` 裡的判斷是「手續費不足 20 元時，扣過了就加回 20 元」——
初始值為 `True` 等於第一輪就當作已經扣過，直接 +20。註解說的是「重複扣才加回」，
程式做的不是那件事。**移植時要逐輪比對數值，不能照著註解寫。**

**三、賠錢時「1% 慢慢賣」在小部位會變成不賣。**
`Round(股數 * 0.01, 0)` 在股數少於 50 的時候得 0，那一檔就永遠不動 ——
如果外層的收斂條件還在等它，會不收斂。VBA 版沒有防護。

**四、第 8 步有無限迴圈的可能。** `Do While 剩餘現金 < 0` 一直減最便宜那檔 1 股，
如果那檔股數已經是 0 或負數，減下去不會讓現金變正。移植版要有次數上限與明確的錯誤。

**五、`is_sell` 只在最外層設定一次**，依 `N` 欄的原始加買金額判定，
`Sim_trade` 每一輪都沿用同一份。不要在內層重算，會改變行為。

**六、第 7 步只加下單試算的股數、不碰現金**，靠 `O19` 公式重算出剩餘現金。
純 Python 版每加一股都要把整條鏈重算一次，否則條件永遠成立。

### 兩處看起來像 bug 的地方，動手前要問清楚

**一、交割款公式的賣出分支，門檻是 20 元、補收的卻是 1 元。**
買進那段是「手續費不足 1 元就收 1 元」，前後一致；賣出那段判斷
「手續費大於 20 元才照算」，不足時卻是 `-1`。而 `Sim_trade` 裡的最低手續費
處理用的又是 20 元。三處對不起來，移植前要確認哪一個才是想要的。

**二、模擬檔的 `B5` 手續費率是空的。** 空值在 Excel 裡當 0，
所有手續費計算因此全部歸零，`自動計算` 的「手續費不足 20 元」也永遠成立。
真檔是不是也空的要確認 —— 如果是，那現在算出來的下單試算本來就沒算手續費。

### 寫回 Excel 的方式要改

Excel 不再是操作工具，但要留著，角色降成兩件事：**存檔**（熟悉的格式、
可以印、給別人看、歷史留著）與**備援**（公式跟巨集原封不動，
哪天程式出事，打開 Excel 照舊能用）。

要讓備援成立，寫回的方式就得改：

|          | 現在                   | 之後                                      |
| -------- | ---------------------- | ----------------------------------------- |
| 寫哪些格 | `B8`、`E4:E8`、`F4:F8` | 所有**輸入格**：`B3:B8`、`D4:I8`、`M4:M8` |
| 公式格   | 不碰                   | 不碰                                      |
| 巨集     | 不碰                   | 不碰                                      |
| 時機     | 每次同步完             | 收工時一次                                |

差別在於寫完之後 Excel 是一份**可以獨立運作的完整檔案**，而不是缺了幾格的殘檔。

### 5 檔上限暫時留著

Excel 版面卡死在 5 檔 —— 巨集裡 `stock_limit = 5`，公式也只鋪到第 8 列與第 18 列。
搬進來之後程式這邊沒有這個限制，但只要還要寫回 Excel 就得守著它。
要放寬得連 Excel 版面一起重新產生，那是另一件事，不在這一節。

### 做的順序

分三段不是為了安全，是為了**中途可以改主意**：

**第一段：計算層 + 對帳。** 15 條公式與求解器寫成純 Python，不做介面、不寫 Excel。
另外寫一支對帳腳本：拿真檔每一格的值跟 Python 算的逐格比對。
產出只有一句話 ——「搬對了」或「這幾格對不上」。這一步不做，後面全是沙上蓋樓。
上面那六個坑與兩處疑似 bug，就是在這一段被數字釘死的。

**第二段：介面長出來，Excel 退居存檔。** 可編輯表格、三塊顯示、四顆按鈕，
接上第一段的計算層。這時候整天只要開這支程式。Excel 只在收工時被寫一次。

**第三段：收掉橋接邏輯。** `ledger.py` 那套自動/手動狀態機、接管、現金基準，
是為了「人跟程式同時改同一張表」而存在的；Excel 不再是操作工具之後大部分可以砍。
**這一段要等第二段實際用過一陣子再做**，砍早了會後悔 —— 在那之前 Excel 仍然
隨時可以手改，那套機制還是有意義的。
