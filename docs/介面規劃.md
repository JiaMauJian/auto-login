# 持股同步介面規劃

Excel 版面維持原樣，程式自己記帳，加一個 Tkinter 視窗把過程攤開來看。

---

## 一、為什麼要有介面

現在的 `update_excel.py` 是「一次性覆蓋」：跑一次、印一堆字、寫進去。
它沒有記憶，所以只能靠在 Excel 裡多開三格（B9 前日餘額、B10 今日淨收付、
B11 最後更新日）來記住上次做到哪。這有兩個問題：

- Excel 版面被改了，那三格也可能被誤改，改了程式就停下來罵人。
- 人工改過的數字，程式無法分辨是「你刻意改的」還是「算錯了」，只能一律中止。

介面要解決的是後者：**讓程式記得自己寫過什麼，這樣任何跟記憶不符的數字，
就一定是人改的。** 記憶放在程式旁邊的紀錄檔，Excel 就可以完全保持原本的樣子。

## 二、資料放哪裡

| 檔案                                 | 內容                                            | 誰維護   |
| ------------------------------------ | ----------------------------------------------- | -------- |
| `持股管理-台美股-5家.xls`            | B8 現金餘額、E4:E8 股數、F4:F8 成本，其餘全公式 | 人＋程式 |
| `持股管理-台美股-5家-同步紀錄.json`  | 現金帳本、每格自動/手動狀態（已拿掉，見下）、上次程式寫入的值 | 程式 |
| `持股管理-台美股-5家-同步歷程.jsonl` | 一行一筆異動，只增不改                          | 程式     |

檔名跟著 Excel 的檔名走而不是固定名稱：萬一同資料夾裡出現第二份持股表，
兩者的現金基準混在一起是災難級的錯誤，而且不會有任何徵兆。
**紀錄檔掉了不會壞事**：程式判定「所有格子都不認得」，壞掉的方向是安全的那一邊。

每格自動/手動的概念整個拿掉、`account_code` 那道核對也拿掉了，見第三節開頭
與 CLAUDE.md「改動前必看」。留著只是為了看懂後面幾節「手動」「接管」字眼的

## 三、自動 / 手動怎麼判定（**這一整套機制 2026/08/20 整個拿掉了**）

> 股數／成本／現金後來改成一律覆蓋 Excel，不再逐格判斷自動/手動、不再擋
> 手改、沒有「接管」這個動作了——風險交給人管。細節與原因見 CLAUDE.md
> 「改動前必看」。以下是拿掉之前的原始設計，留著是因為後面幾節（五、十一、
> 十三）的舊版介面圖裡「手動 🔒」「交還給程式」字眼都是從這裡長出來的，
> 拿掉這節反而看不懂那些圖在講什麼。

原本的規則：每一格各自比對 `Excel 現在的值` 跟紀錄檔的 `last_written`，
相等＝自動（程式可覆蓋），不等＝手動（人改過，程式不准碰），紀錄檔沒這格＝
未接管（登入時以 Excel 現值接管）。

手動轉回自動，股數/成本（快照，網頁重抄一次沒有副作用）可以隨時切回；
現金（累加值）不行，因為程式不知道人改的新數字**含不含今天的淨收付**，
猜錯就多扣或少扣一次——所以現金那格設計成一個要多回答一題的「重新校正」
按鈕，不是單純的開關。這個「現金不能直接切回」的判斷後來一路沒變，
只是問法換了兩次（第十四、十五節），最後定案是每天重新起算、不再逐格判斷。

## 四、現金帳本：順便解掉「漏跑一天就永遠不準」（**逐日累加後來拿掉了，見第十五節**）

當初的想法：舊的 B9/B10 模型是「前日餘額 + 今日淨收付」，漏跑一天那天的錢
就永遠不會進帳、之後全錯；改成紀錄檔按日累積 `baseline + sum(applied[日期])`，
同一天重跑覆蓋 `applied[今天]` 即可，且能比對缺哪個交易日、去對帳單補登。

後來發現沒有人真的會去補（要回頭查對帳單），而更簡單的做法一直都在——
今天的 B8 就寫在眼前。第十五節改成每天重新起算，漏跑不影響今天。

## 五、視窗長相（下面的同步分頁、現金帳本分頁都是最初版本，早就改掉了）

> 最初是單一視窗、兩個分頁（同步／歷程），表格用 `ttk.Treeview`，逐格顯示
> 「自動／手動 🔒」狀態，右下角有「交還給程式」「寫入這 N 格」兩顆按鈕。
> 這整張圖跟著第三節那套自動/手動機制一起作廢：狀態欄沒了、兩顆按鈕沒了，
> 同步分頁後來改成左右兩半（左邊挑人、右邊只畫那一位，見第十三節）。

**寫不寫 Excel 由「程式自動更新」一個開關決定**（沿用至今）：勾起來，讀完
網頁資料就直接寫進 Excel、更新紀錄檔；取消勾選，程式一格都不碰，同步分頁
只是對照表。原本每格前面還有勾選框＋全選/全不選，20 帳號上百格的規模下
沒人會逐格看，兩層開關只是多一次誤判機會，全部拿掉。開關記在紀錄檔的
`settings.auto_write`，下次打開沿用——這種「程式會不會動你檔案」的開關
不該每次啟動就跳回自動。

**歷程分頁**

```
交易人  簡嘉懋 ▾    項目  現金餘額 ▾    期間  今天 ▾

08/17 11:30  程式  簡嘉懋 B8   893 → 786    今日淨收付 −107（3 筆成交）
08/17 11:30  程式  簡嘉懋 E5   500 → 600    未實現損益 成交股數
08/17 14:02  人工  簡嘉懋 B8   786 → 900    ← 08/18 09:15 執行時偵測到，已轉手動
08/18 09:16  校正  簡嘉懋 B8   基準改為 900（08/18 起算，今日淨收付尚未計入）

篩出 3 筆／共 943 筆，最新的在最上面。
```

人工那一筆的時間標的是**偵測到的時間**，不是你實際改的時間——程式沒在看，
只能事後從差異推回來，介面上會明講這件事，不要假裝知道。

上面三個選單是必要的：20 個帳號跑幾天就是近千筆，一路捲下去等於找不到。
人要問的問題永遠長成「某個人的某一格，今天怎麼了」，所以就照那句話拆成
交易人、項目、期間三層，都不選時維持原本的全部列出。

項目清單跟著交易人走 —— 選了人就只列那個人有的格子，沒選人才列全部。
清單順序是現金在最前面，其餘照股票分組（同一檔的股數排在成本前面）：
照字串排會讓同一檔股票的兩格隔開幾十列，但人是先想到股票才想到看哪一格。

期間只給「今天」與「近 7 天」兩個級距——再細要多一個日曆元件跟一整套錯誤
處理，換來的是沒人真的會用的功能。「今天」是每次重畫時現算的，不是開程式
那一刻的日期，因為這支程式常開著過夜，跨過午夜還停在昨天會讓剛跑完的那批
整批不見。時間欄壞掉的紀錄只有「全部」看得到，避免憑空生出一筆今天的異動。

**現金帳本分頁（後來整個拿掉了，見第十二節）**

當初的想法：基準、逐日淨收付、應有餘額 vs Excel B8 對不對得上、缺日期補登。
「登入即初始化」（第十一節）之後這個分頁的三個功能都被更簡單的東西取代，
沒有存在的必要了。

## 六、程式怎麼拆

現在都擠在 `update_excel.py`。要接介面就得把「抓資料 / 算 / 寫」拆開，
因為 Tkinter 得在自己的執行緒跑，Playwright 和 Excel COM 不能卡住畫面。

| 檔案              | 職責                                                      |
| ----------------- | --------------------------------------------------------- |
| `login.py`        | 不動。登入、開瀏覽器                                      |
| `recon.py`        | 不動。AJAX 重放                                           |
| `fetch.py`        | 從 `update_excel.py` 抽出 `collect()`，只負責回傳網頁資料 |
| `ledger.py`       | 紀錄檔讀寫、自動/手動判定、現金帳本計算、歷程追加         |
| `excel_io.py`     | COM 開檔、讀 B8/E/F、寫入、備份。只認得這三處             |
| `planner.py`      | 網頁資料 × Excel 現值 × 紀錄檔 → 一張「變更提案」清單     |
| `ui.py`           | Tkinter 視窗，唯一有畫面的檔                              |
| `update_excel.py` | 保留無介面模式，改成呼叫上面那些模組                      |

`planner.py` 產出的每一列長這樣，介面直接照著畫，不用再自己算：

```python
{
  "cells": ["E5", "F5"], "label": "聯發科(2454)",
  "current": (500, 900), "web": (600, 880), "proposed": (600, 880),
  "state": "auto",            # auto / manual / untracked / web_missing / excel_missing
  "checked": True,
  "note": ""
}
```

執行緒切法：按下「讀取網頁資料」→ 背景執行緒跑 Playwright 和 COM 讀取 →
結果丟回主執行緒畫表格。寫入也一樣。畫面全程可以按取消。

## 七、既有的安全機制要留著

- ~~寫入前備份，保留最近 10 份~~ ——這條後來拿掉了（2026/08/24 前後）：使用者
  自己那邊已經有備份機制，程式這層備份只是每次寫入多一趟複製檔案的時間，
  留著沒有實益。
- Excel 已經開著就接上那個實例，直接寫、直接存檔。不留 Ctrl+S 那一步 ——
  紀錄檔在寫入成功後就記成寫過了，人沒按 Ctrl+S 就會讓帳本跟檔案分家，
  畫面上還不會有徵兆。
- 每一列都驗 `bhno`/`cseq`，擋掉多帳號時 session 被頂掉抓到別人資料。
- 網頁沒有的股票**不自動清空**，只提醒。
- 「未實現損益顯示今天有成交，但淨收付是 0」（收盤結帳後查不到）仍然要擋，
  但改成只擋現金那一列，持股照樣可以寫——不必整份中止。

## 八、做的順序

| 階段 | 內容                                                            | 能驗收什麼                   | 狀態 |
| ---- | --------------------------------------------------------------- | ---------------------------- | ---- |
| 一   | 拆模組、`ledger.py` 上線，拿掉 B9/B10/B11，CLI 先跑通新帳本模型 | 命令列試算結果跟現在一致     | 完成 |
| 二   | Tkinter 主畫面：讀取、表格、寫入                                | 不用看命令列就能完成一次同步 | 完成 |
| 三   | 歷程分頁、現金帳本分頁、補登、重新校正                          | 手改一格再跑，看得到它變手動 | 完成 |
| 四   | 併進 `tbb-login.exe`，或另做一支 `持股同步.exe`                 | 目標機器雙擊就能用           | 完成 |

介面在 `ui.py`，執行方式是雙擊 `tbb-login.exe`（不帶參數就是它）或 `python ui.py`。
登入、抓網頁、開 Excel 全在背景執行緒（COM 前要先 `CoInitialize`），
背景只回傳純資料、由主執行緒畫，不在背景碰任何 widget。

打包成單一 exe，靠參數切換（`login.py` 的 `route()`）：

    tbb-login.exe              持股同步介面（不帶參數就是它）
    tbb-login.exe --sim-excel  在 Excel 補上模擬用的分頁（測試用，見 dev_tools/sim_excel.py）

實測到兩個「只有在目標機器上才會現形」的坑，都已修掉：`tkinter` 原本被
`--exclude-module` 排除，留著的話打包成功、一執行 GUI 才會炸；早期用
`.bat` 包一層去帶參數時，`.bat` 內容一度混了中文註解，cmd.exe 靠系統
OEM 編碼解析 .bat（不保證是 UTF-8），實測會把註解片段誤判成指令去執行，
改成純 ASCII 並用完整路徑呼叫 exe（有些機器設定
`NoDefaultCurrentDirectoryInExePath` 後，cmd.exe 不會在目前目錄搜尋
不帶路徑的指令名稱）。

2026/08/20 起：登入、抓網頁、寫 Excel 全部都在 GUI 裡做，原本命令列用的
自動登入（`main()`）與 `--update`（`update_excel.py`）都已經沒人在用，整支
拿掉了——`login.py` 不再有 `main()`，`update_excel.py` 這個檔案也直接刪掉。
因此：

- exe 改打包成 `--windowed`（不跳黑視窗）。
- `route()` 把 GUI 變成不帶參數的預設行為（原本的 `--sync` 拿掉了）。這樣
  雙擊 exe 就直接開 GUI，不再需要 `.bat`/`.vbs` 這層中間檔案去帶參數。
- 代價：`--windowed` 沒有主控台，`route()` 丟出來、還沒被 GUI 自己的
  `messagebox` 接住的例外（例如還沒進到 GUI 就炸掉）看不到任何輸出。
  補上 `login.py` 的 `log_crash()`：把這類例外寫進 exe 旁邊的
  `crash.log`，使用者遇到「雙擊沒反應」時把這個檔案內容貼出來即可。
- `do_login()` 留著：GUI 的登入流程（`fetch.ensure_logged_in`）還是靠它，
  拿掉的只是「單獨開瀏覽器、登入所有帳號、什麼都不抓就等你按 Enter」這個
  獨立的命令列用法。

階段一實際拆出來的檔案：`util.py`（數字與寬度對齊的小工具）、
`excel_io.py`（只認得 B8/D/E/F 的 COM 讀寫）、`ledger.py`（紀錄檔與現金流水）、
`planner.py`（純計算，產出變更提案）、`fetch.py`（登入抓資料）。
`update_excel.py` 只剩命令列介面。介面版之後直接接 `planner` 的提案清單就好。

拿掉 B11 最後更新日還順手消掉一個陷阱：程式不再需要把日期寫進 Excel，
原本 pywin32 把 datetime 當本地時間換算成 COM 日期、少一天導致重複扣款的問題
就不存在了（日期現在只存在紀錄檔的 ISO 字串裡）。

### 第一次啟動要做的事

現在 Excel 的 B8 = 893，而且**你已經手動扣過今天的 −107 了**。
紀錄檔還不存在，所以第一次開介面會跳設定精靈，問三件事：

1. Excel 檔在哪、哪個分頁對哪組帳號（分頁名 = 帳戶名，可自動猜）
2. 現金基準：以目前的 893 為準，基準日填今天
3. 這個 893 含不含今天的 −107？→ 你答「含」，程式就把 `applied["2026-08-17"] = -107`
   記起來，之後今天再跑不會重複扣

持股那邊不用問，第一次執行就以網頁值全部接管。

## 九、還沒決定的事

- **多帳號**：紀錄檔已經用分頁名當 key，20 個分頁不用改結構。
  但介面上是一次跑一組、還是一鍵跑完全部？後者要處理 session 被頂掉的問題

- **補登的來源**：現在只能人工輸入。對帳單查詢頁（`type=2`）能不能回查
  某一天的淨收付還沒偵察，可以的話就能自動補。

## 十、模擬多帳號（測試用）

手上只有一組真帳號，但要跑的是 20 組。介面、Excel 20 個分頁、紀錄檔與現金帳本
在這個規模下順不順，不該等到拿到 20 組帳密才知道，所以補了一套模擬：

真的那一組照原本流程登入，另外 19 個在**同一個瀏覽器**各開一個分頁，
放一頁程式自己畫的假網頁（`page.set_content`，不連任何網站）。假網頁把資料放在
`window.__SIM__`，`fetch.py` 對假帳號改成呼叫它而不是打 `MainController`，
回傳的形狀跟真 API 一模一樣，所以 planner / ledger / excel_io / ui 都不知道有假帳號這件事。

| 檔案                     | 職責                                                |
| ------------------------ | --------------------------------------------------- |
| `dev_tools/simulate.py`  | 假帳號清單、隨機資料、假網頁 HTML、開分頁與讀回資料 |
| `dev_tools/sim_excel.py` | 在 Excel 補上／移除模擬分頁（交易人A～S）           |
| `.env`                   | `SIMULATE_ACCOUNTS=19`，沒設就等於整套模擬不存在    |

開起來的順序：

1. `python dev_tools/sim_excel.py --write` —— 複製 19 個分頁（範本就是真分頁，公式全部保留）
2. `.env` 設 `SIMULATE_ACCOUNTS=19`
3. `python update_excel.py --adopt --today=pending --write` —— 一次接管 20 個分頁
   （介面上一格一格按是 200 格，不現實）
4. `python ui.py` —— 登入、讀取（自動更新開著就會直接寫），跟平常一樣操作

隨機值的種子是（帳號名 + 日期），所以同一天重讀網頁資料數字不變 ——
剛好可以驗證「同一天重跑不會重複扣現金」。要換數字就按假網頁上的「重新隨機」。
股數、成交均價、市價、當日成交在頁面上都是輸入格，改完立刻生效，
可以自己擺出特定情境（某檔股數改成 0 = 網頁庫存沒這檔）。

**測不到的**：20 個分頁裡只有 1 個真的在跟網站講話，所以「多帳號共用 JSESSIONID
會互踢」這個真正的風險模擬不出來，那只有真的 20 組帳號才驗得出來。
`fetch.py` 那道「每一列的 bhno/cseq 要等於這個分頁登入的身分」的檢查照樣會跑
（假資料的 bhno 也照真 API 的規則帶開頭那個 1），所以檢查本身有被測到。

**收乾淨**：`python dev_tools/sim_excel.py --remove --write` 會刪掉模擬分頁、
從 `同步紀錄.json` 移除對應分頁、把 `同步歷程.jsonl` 裡的模擬紀錄濾掉
（動手前 Excel 與歷程都會先備份）。模擬分頁是加在正在用的那份 Excel 裡，
紀錄檔又是跟著檔名走的，所以清理這件事一定要程式做，手工清不乾淨。

## 十一、登入即初始化（取代「交還給程式」）

原本第一次用、或任何一格沒被程式管過，都要人明確交接一次；現金還要多回答
一題「Excel 上的餘額含不含今天的淨收付」。20 個帳號的規模下，那個對話框
一次列 11 個帳戶，等於逼人在最不確定的時候做最危險的判斷。

現在改成：**開 Excel → 按登入 → 登入成功的當下，Excel 上的股數、成本、
現金餘額直接被收成程式的起點。**

之所以敢不問，是因為時間點選在登入完成、還沒讀網頁資料之前：

```
登入完成      Excel 上的數字 = 今天買賣之前的狀態  →  直接當基準，沒有猜的空間
讀取網頁資料  今天成交了什麼                      →  往基準上加
寫入          基準 + 今天的淨收付                 →  寫回 B8
```

現金基準取 B8 原值，今天的流水先記 0，之後 `commit()` 用真正的淨收付覆蓋掉它。
所以「B8 含不含今天」這一題在登入的當下根本不存在。

**一天只設一次基準**。今天已經設過（多半也已經寫進 B8 了），再設一次會讓
今天的淨收付被加第二次，而且畫面上不會有任何徵兆 —— 所以 `planner.initialize()`
看到 `baseline_date` 已經是今天就跳過，介面的 `_auto_adopt()` 也照同一條規則。

跳過之後那一格當天就沒有出口了。要重新起算只能由人明講 —— 現金那一條底下的
「今日初始現金餘額　[修改]」，見第十五節。

| 動作               | 誰觸發           | 現金基準怎麼定                    |
| ------------------ | ---------------- | --------------------------------- |
| 登入               | 每次按「登入」   | = Excel 的 B8，今天的流水記 0     |
| 讀取後自動接管     | 自動模式，補網用 | = Excel 的 B8，今天的淨收付加上去 |
| 改今日初始現金餘額 | 人自己按「修改」 | = 人填的數字 − 今天的淨收付       |

## 十二、現金帳本分頁拿掉了

第四節那個分頁（基準、逐日流水、補登、重新校正）在登入即初始化之後
沒有存在的必要了 —— 它的三個功能各自被更簡單的東西取代：

| 原本的功能   | 現在怎麼做                                                       |
| ------------ | ---------------------------------------------------------------- |
| 看基準與流水 | 基準寫在同步分頁上（今日初始現金餘額），流水只剩今天一筆         |
| 重新校正     | 直接改 Excel 的 B8，下次登入以那個數字為準（同一天內見第十五節） |
| 補登漏掉的天 | 不必補。基準每天重設，漏跑的那天不影響今天（見第十五節）         |

換句話說，現金的帳還是照記，只是那變成程式內部的事，不再是一個要人看懂、
要人操作的畫面。介面剩下兩個分頁：同步（這次要改哪幾格）、歷程（誰改了什麼）。

## 十三、同步分頁改成「左邊挑人、右邊看一個人」

20 個交易人、每人十幾格，攤平成一張表是兩百多列。實際跑起來的毛病有三個：

- 捲到一半，畫面上那個 `B8 現金餘額` 不知道是誰的 —— 交易人的名字在群組列上，早就捲出畫面了
- 要知道「這次哪幾個人要處理」，只能整份捲一遍
- 整張表比視窗還寬，最右邊的「說明」永遠被切掉

而真正的工作方式是**依序輪詢**：一次只看一個人，看完換下一個。版面就照那個
方式切。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 開啟EXCEL   ...\持股管理.xls —— 已開在 Excel 裡                             │
│ 登入   帳號 全部 ▾         ☑ 程式自動更新    [ 讀取網頁資料 ]               │
├────────────────────┬────────────────────────────────────────────────────────┤
│ 交易人    3/20 位  │ 交易人G（模擬）　第 7/20 位　現金 553,161　要寫 1 格   │
│ ☐ 只看有差異       ├────────────────────────────────────────────────────────┤
├────────────────────┤ 格子 項目            舊值      網頁      新值    狀態  │
│ 姓名  現金餘額 狀態│ E4  股數(2059 川湖)  1,000     1,000     —     自動    │
│ 交易人A ⋯   ✓      │ F4  成本(2059 川湖)  1,307     1,307     —     自動    │
│ 交易人B ⋯ 要寫 2   │ …（一位就十一列，不必捲、不必展開）                    │
│ ⚠ 交易人E ⋯  ⚠     │ B8  現金餘額       553,161   -28,861  -28,307  自動    │
│ 交易人G ⋯ 要寫 1   │ 今日初始現金餘額 553,161  [修改]                       │
│ 交易人L ⋯   ✓      ├────────────────────────────────────────────────────────┤
│ 點一下換人         │ 提醒：只列這一位的                                     │
└────────────────────┴────────────────────────────────────────────────────────┘
```

| 原本                     | 現在                                             |
| ------------------------ | ------------------------------------------------ |
| 220 列攤平、用群組分隔   | 左邊 20 列名單，右邊固定只畫一位的十一格         |
| 誰要處理要整份捲一遍     | 名單上直接寫「要寫 N ／ ⚠ ／ ✓」，還有現金餘額   |
| 交易人的名字捲走就沒了   | 右邊訊息框第一行固定寫著是誰、資料幾點讀的       |
| 找下一個群組             | 點一下名單，或 ↑ ↓ ／ Ctrl+↑ ／ Ctrl+↓           |
| 20 個人的提醒堆在同一框  | 只列選中那位的；別人的事名單上用 ⚠ 標著          |
| 表格比視窗寬，說明被切掉 | 少了「交易人」欄就塞得下，說明是唯一會伸縮的一欄 |

**幾個刻意的決定**

**右下角那顆「寫入」拿掉了**，「上一位／下一位」兩顆按鈕也是。寫入原本是
人工維護模式下的逃生口，但真的想讓程式寫，把「程式自動更新」勾起來再讀一次
就是了；換人則是名單就在左邊，點一下比按按鈕快 —— 兩者都只是同一件事的
第二個入口。留下來的是 Ctrl+↑ / Ctrl+↓：手放在右邊那張表的時候焦點不在
名單裡，那時候還是要能換人。

換人照**名單上真正顯示的順序**走（`_shown()` 直接問 Treeview），不照
`proposals` 的順序算 —— 開了篩選之後兩者會不一樣，而人是照眼睛看到的在數。
`_step_person` 也不等 `<<TreeviewSelect>>`：那個事件要排進事件佇列才送，
「鍵按了、右邊要立刻換」不該押在佇列什麼時候輪到它上面。

**視窗尺寸**：預設 `wide(1180) × wide(720)`，上限是桌面可用區（螢幕扣掉工作列）
再各留一點邊；擺位置由 `_center()` 算，會多扣掉標題列的高度。

高度**不**跟著帳號數長。原本是照人數算到「整份名單一次看得完」，後來拿掉了 ——
名單本來就有捲軸，滑鼠滾兩下的成本，遠低於「20 個帳號就開一個佔滿整個桌面的視窗」。
要一次看完就自己把視窗拉高，或在 `.env` 設 `UI_HEIGHT`。

外觀有三個設定放在 `.env`，都在 import 時讀一次，改完要重開介面：

| 設定           | 沒設時                   | 有設時             |
| -------------- | ------------------------ | ------------------ |
| `UI_FONT_SIZE` | 12                       | 夾在 8～24         |
| `UI_WIDTH`     | `wide(1180)`，跟著字級走 | 當像素用，下限 640 |
| `UI_HEIGHT`    | `wide(720)`，跟著字級走  | 當像素用，下限 400 |

長寬填的數字就是像素，**不再乘上字級**：使用者量的是螢幕上的視窗，不是某個基準
字級下的寬度，把他填的 1400 放大成 1680 只會讓人以為程式沒讀到設定。三個設定
填了看不懂的東西一律當作沒設 —— 外觀設定不值得為了一個打錯的數字讓介面開不起來。

切到歷程分頁時，交易人的篩選會自動跟著同步 —— 切過去通常就是想看剛才那位
的歷程，不必再選一次人。

上面那排「帳號 全部 ▾」留著：它決定的是**登入／讀取哪幾組帳號**，
跟左邊名單（讀完之後看誰）是兩件事，而且第一次登入之前根本還沒有名單可挑。

## 十四、同一天內要改現金餘額（**這裡的彈窗機制後來拿掉了，見第十五節**；下面「算出來的東西」那條公式仍在用）

第十一節「一天只設一次基準」會把當天的現金餘額鎖死：改 B8 只會被判成人工
改動然後凍住，到隔天才解得開。有兩種情況真的會踩到——紀錄檔遺失後同一天
重開（誤刪、改檔名、換機器，`baseline_date` 變 `None` 看起來像今天第一次
開），或當天發現餘額不對想直接校正。

**問「開盤前」，不問「現在的餘額」**——這是踩過的坑：第一版問「現在正確的
餘額（含今天已成交的部分）」，使用者看著 Excel 上的 553,161 填進去，意思是
「我手上有這些現金」，程式卻理解成「553,161 已經含過今天的 −28,861,068
了」，方向剛好相反，而且畫面上完全看不出來。問題出在問的時機：登入當下
還沒查網頁、手上沒有今日淨收付，只能要人用文字描述自己填的是哪種數字——
那種答錯又沒徵兆的問題本來就不該存在。改成跳在**讀完網頁資料之後**，問
「開盤前」這個不會動的量（今日淨收付盤中還會變，「現在餘額」講完下一筆
成交就過期），右邊即時算出 B8 會變成多少，「含不含今天成交」這問題就消失了。

判斷「該不該問」的邏輯（今天第一次登入不問／第二次以後問／紀錄檔遺失也要
問，因為看「第幾次」會誤判成第一次／淨收付信不過時不問，避免把錯的淨收付
永久算進基準）連同一次問完所有分頁的彈窗，整個被第十五節的常駐按鈕取代。

### 算出來的東西

`apply_cash_reset()` 就地改掉現金那一列的提案，`commit()` 再交給既有的
`calibrate()`：

```
B8 提議值 = 開盤前 + 今日淨收付          ← 對話框右邊那一欄
calibrate(balance=B8 提議值, today_included=True)
        → baseline = 開盤前              ← 往回推一天份，剛好回到人填的數字
          applied  = { 今天: 今日淨收付 }
```

`today_included=True` 看起來跟「使用者填的是開盤前」矛盾，其實不是：交給
`calibrate` 的是**算完的 B8**，不是人填的數字。這樣走既有的路，不必為了重設
多開一條分支。之後盤中再成交，`baseline` 不動、`net` 變大，餘額就跟著往上加，
不會停在人填的那個數字。

這是唯一能蓋過「手動」狀態的東西。人已經明講了正確的數字，程式沒有理由
再守著一個它自己也知道過時的值。

## 十五、現金改成「今日初始現金餘額」，每天重新起算

這一節推翻兩件事：第十四節那個「重設現金餘額」對話框（拿掉了），
以及第四節、第十二節留下來的跨日累加（不算了）。

### 一個算式，兩項

```
現金餘額（B8） = 今日初始現金餘額 + 今日淨收付
                 ↑ 今天第一次登入      ↑ 網頁抄來的
                   時 Excel 上的 B8       不會錯
```

右邊那項不會錯，所以餘額不對的時候，錯的一定是左邊那項。既然如此，它就該
一直看得到、一直改得動 —— 現金那一條底下固定寫著這一行，旁邊一顆「修改」。

### 不回頭算舊帳

原本的模型是「基準只設一次，`applied` 把每天的淨收付一路往後疊」，好處是漏跑
的那天看得見、補得回來（第四節）。實際上沒有人會去補：要補得回頭查那天的對帳單，
而更簡單的做法一直都在 —— 今天的 B8 就寫在眼前。

所以改成**每天重新起算**：只要基準日還不是今天，登入就把 B8 收成今天的起點，
不管它昨天是自動還是手動、昨天有沒有跑過。

| 原本                                  | 現在                                     |
| ------------------------------------- | ---------------------------------------- |
| `baseline` 設一次，`applied` 逐日累加 | `baseline` 每天重設，`applied` 只有今天  |
| 漏跑一天要補登，不補就少一段          | 漏跑不影響今天 —— 起點就是今天看到的 B8  |
| 缺哪個交易日要算、要提醒              | 沒有這種提醒了（`missing_dates` 已移除） |

`applied` 這個字典留著：同一天重跑只是覆蓋同一個 key，跑幾次結果都一樣。
舊紀錄檔裡多天的資料不必轉檔，今天第一次登入就會被重設成只剩今天一筆。

### 對話框換成按鈕

第十四節那個對話框由程式判斷「今天可能已經開過了」才跳，一次問完所有分頁。
猜錯的兩個方向都很貴：

- 不該問的時候問 —— 20 個分頁列在同一個視窗，按到第三次就沒人在看內容了
- 該問的時候沒問，或跳的時候填錯 —— 當天再也沒有入口，只能等明天

數字一直在畫面上、按鈕一直按得動，就不必由程式決定什麼時候該問誰。
問法與算法整個沿用（`planner.apply_cash_reset`），只是改成一次一位。

| 情況                         | 顯示                | 「修改」 |
| ---------------------------- | ------------------- | -------- |
| 還沒選到人（還沒讀網頁資料） | `—`                 | 灰       |
| 紀錄檔還沒有基準             | `(還沒設定)`        | 灰       |
| 正常                         | `1,234,567`         | 亮       |
| 剛按過修改、還沒落帳         | `1,234,567 → 5,000` | 亮       |
| 淨收付信不過（`blocked`）    | 照常顯示            | 灰＋理由 |

沒有網頁資料就不給改：新的 B8 是「開盤前 ＋ 今日淨收付」，沒有淨收付算不出來，
也就沒有東西可以寫回去。`blocked` 的理由跟第十四節同一條 —— 拿一個已知是錯的
淨收付去 calibrate，會把今天的成交永久算進基準裡。按鈕變灰時理由就寫在旁邊，
灰掉而不說為什麼看起來就像壞了。

### 按下去之後

落實的方式跟著「程式自動更新」走，不另外開第三條路：

| 開關 | 做什麼                                                          |
| ---- | --------------------------------------------------------------- |
| 勾著 | 直接寫進 Excel 並落帳；算出來剛好等於 B8 時不必寫，但一樣要落帳 |
| 沒勾 | 只把建議值畫成「舊 → 新」，Excel 由人自己改，紀錄檔一個字不動   |

「不必寫也要落帳」是第十四節就有的坑：基準確實被人改掉了，這一筆不記，
下一次讀取會拿沒被修正的基準再算一次，今天的淨收付就被加了第二次
（見 `_commit_round` 的註解）。

### 換來的代價

拿掉對話框之後，有一種情況不再有人主動提醒：**紀錄檔遺失後同一天重開**
（誤刪、Excel 改檔名或搬資料夾、換一台電腦）。那時 `baseline_date` 是 `None`，
看起來就像今天第一次登入，於是已經含了今日淨收付的 B8 被當成起點，待會兒再加
一次。原本第十四節的第三條規則就是為了接住它。

現在接住它的是畫面本身：那個數字就寫在現金餘額底下，跟「今日淨收付」上下並排。
起點被算成含了今天的成交，這一行會明顯偏高 —— 看到不對就按「修改」。
用「一直看得到」換掉「程式挑時機提醒」，是這一節整個的交易。

### 說明放在哪裡

「看到不對就按」要成立，前提是使用者知道什麼算不對。真正會走到那顆按鈕的路只有
一條：**人自己在盤中改過 B8**。他改進去的是「現在正確的餘額」，那個數字已經含了
今天的成交，照抄成開盤前就等於把今天的淨收付算進起點裡，待會兒再加一次。
這件事沒有任何檢查擋得住 —— 兩個數字都是合法的金額，錯的那個要到明天才看得出來，
所以只能用講的。三個位置各講一段，愈靠近出錯的當下講得愈細：

| 位置                 | 說什麼                                                         |
| -------------------- | -------------------------------------------------------------- |
| 「修改」旁邊那行灰字 | 這個數字＝今天第一次登入時的EXCEL現金餘額B8                    |
| 提醒框最後一行       | 今天別改檔名、別自己改 B8；真改了就用「修改」補開盤前的金額    |
| 對話框（按下去之後） | 開盤前的定義、`B8 − 今日淨收付` 算好擺著附「帶入」、填錯的後果 |

對話框裡那一行「B8 已經含了今天的成交的話，開盤前是 X」是最實際的一項：需要按這顆
按鈕的人，手上有的正好是 B8，缺的正好是那個減法。算好擺著、再給一顆「帶入」，
比請他自己心算一次再賭算得跟程式一樣可靠。

提醒框那一句排在最後一行，因為那個框只有五行高又沒有捲軸：常駐的字排在前面會把
當天真正的警告推出視線；排最後的話，沒事的日子看得到（框是空的），
有事的日子被擠掉的正好是它。

另一個弄壞今天起點的方式是**改 Excel 檔名或搬資料夾**（紀錄檔跟著檔名走，
換了名字就變成「紀錄檔遺失後同一天重開」）。它跟手改 B8 是同一種傷害，
所以講在同一句話裡 —— 分成兩條提醒，讀的人不會知道那是同一件事。

## 十六、一次只更新一位交易人

原本一顆「讀取網頁資料」永遠是全部：19 個帳號逐一登入、逐一查、逐一寫，
跑一輪要好幾分鐘。但盤中真正在看的通常只有一位 —— 剛下完單的那一位。
為了看他一個，得把另外 18 個人重讀一次，而那 18 個人的資料還會被順手寫進 Excel。

### 範圍就是「按下去會動到誰」

上面那個下拉選單從「帳號（全部／第 N 組）」改名成「範圍」，並且跟左邊的名單
接成同一個選擇的兩個入口：

- 名單上點一位 → 範圍換成他，按鈕改名成「更新（王小明）」
- 範圍換一位 → 名單跳到他，右邊也跟著換人

按鈕上的字就是這一節的全部重點：按下去會動到誰，寫在按鈕上，
不必回頭去確認那個下拉選單現在停在哪一列。

| 範圍                | 按鈕字樣                | 按下去做什麼                       |
| ------------------- | ----------------------- | ---------------------------------- |
| 全部                | 讀取網頁資料            | 每一組都登入、都查、都寫           |
| 第 3 組（名字已知） | 更新（王小明）          | 只查他、只寫他那一頁               |
| 第 3 組（名字未知） | 讀取網頁資料（第 3 組） | 一樣只做那一組，只是還說不出他是誰 |

名字為什麼會未知：`.env` 裡只有帳密，交易人的名字要登入之後才從網站的
sessionStorage 拿得到（見 `fetch.collect` 的 `sheet_name`）。所以對照表是一邊做
一邊長出來的，模擬帳號例外 —— 它的名字本來就寫在 `.env` 裡，一開機就填得進去。

### 預設仍然是「全部」

左邊那份名單是網頁資料長出來的，沒讀過一輪之前它是空的，也就沒有人可以點。
一天的動線因此還是：開盤前讀一次全部（順便把名單與名字都建起來），
之後整個交易時段都在「點一位 → 更新（他）」。

### 只更新一位，要守住三件事

**一、讀到的是補上去，不是整份換掉。** 名單上其他人手上那份是上一輪的資料，
清掉他們等於整份名單只剩一個人。`records`／`sheet_data`／`read_at` 全部改成合併。

**二、畫面上同時有好幾個時間點的資料。** 所以每一位都記著自己的讀取時間，
右邊寫著「簡嘉懋　讀取於 10:32:07」。沒有它，半小時前讀的數字跟剛讀的長得一模一樣
—— 這是這個改動最容易讓畫面說謊的地方。這一句原本是表格上方一行獨立的粗體標頭，
2026/08/21 使用者要求收進底下的訊息框當第一行（見 `ui_sync._head_line`）：右半邊
由上到下本來有標頭、兩張表、訊息框四塊，而標頭跟訊息框講的是同一種話 ——
這份資料是誰的、什麼時候來的、有什麼要注意。以後只要有讀取動作，那一句就固定
擺在訊息框第一行。

**2026/08/22 這件事整個拿掉**（見 `docs/同步分頁訊息框改版.md`）：訊息框改成
讀歷程檔重排之後，每一行本來就帶著自己的時間戳，第一行再講一次「誰、幾點讀的」
變成重複資訊，使用者要求拿掉。`_head_line`、`self.read_at` 整組刪掉，「半小時前
讀的數字跟剛讀的長得一模一樣」這個風險目前沒有畫面信號提醒，只是不影響
`round_scope` 那條寫入範圍的硬規則——資料新舊不分不會讓程式寫錯地方，只是人自己
不容易一眼看出來。

**三、寫入、落帳、接管只能碰這一輪讀到的那幾位。** 介面多了一個 `round_scope`，
`_collect_writes`、`_commit_round`、`_auto_adopt`、寫入後的回填四處都照它。
名單上別人也可能有「要寫」的格子，那是用上一輪的網頁資料算出來的
—— 順手寫出去就是拿舊資料改 Excel，而且沒有人要求過。
現金那顆「修改」也一樣：按的時候把範圍縮到眼前這一位。

失敗原因跟著改成掛在「第幾組」上，不再是每讀一次就整串重來：只更新一位的時候，
別人上一輪沒完成的事並沒有因此解決，那些 ⚠ 要留到那一組自己再讀一次成功為止。

### 換人不重登：把 cookie 換回去

整個瀏覽器只有一組 cookie（`JSESSIONID`），所以同時只帶得動一個人的身分，
後登入的會把前一個頂掉。這常被講成「一次只能登入一個帳號」，但那句話只對一半：

| 哪一邊 | 20 組同時登入 | 為什麼                                                        |
| ------ | ------------- | ------------------------------------------------------------- |
| 瀏覽器 | 做不到        | 一個 context 一組 cookie，`JSESSIONID` 只有一個值             |
| 伺服器 | 本來就是      | 20 個不同身分證＝20 個各自獨立的 session，B 登入不會殺掉 A 的 |

A 被頂掉的意思只是「暫時沒有人帶著他的 cookie 去敲門」，他在伺服器上還活著。
所以換人這件事在程式裡不是「重新登入」，是**換一組 cookie**：

1. 按「登入」時 20 組照樣一次跑完，每一組登入完就把當下整份 cookie 收進 `store["jars"]`
2. 「更新（王小明）」時先把他那份 cookie 換回瀏覽器（`clear_cookies` + `add_cookies`），
   回帳戶頁確認一下，就直接查 —— 不必跑登入流程，連驗證碼都省了
3. 確認不過（那一組在伺服器上逾時了）才真的重登一次

三條路的成本差很多，而盤中最常走的是前兩條：

| 情況                       | 做什麼                 | 成本           |
| -------------------------- | ---------------------- | -------------- |
| 剛才就是他（連按同一位）   | 回帳戶頁確認一下       | 最快           |
| 換人、他的 cookie 還有效   | 換回 cookie 再確認一次 | 快，不必驗證碼 |
| 換人、他已經在伺服器上逾時 | 整套登入流程跑一遍     | 慢             |

換 cookie 換不回去的唯一原因是 session 逾時，那時候走的是原本就有的重登，
所以這個機制最壞的結果等於沒有它，不會更糟。

**確認身分那一道不能省。** 分頁自己的 `sessionStorage` 不會因為 cookie 被換掉就失效
——只看它的話，一個早就被頂掉的分頁探起來一樣「還活著」，照它走就會拿到別人的資料
寫進別人的 Excel。所以 `_revisit` 三道一起看：還在帳戶頁、`sessionStorage` 有值、
而且身分跟這一組登入時記下來的帳號代號相同。`collect` 裡原本那道「每一列的
`bhno`／`cseq` 要跟登入身分相符」照樣留著當最後一道。

還有一個門檻在登入本身：瀏覽器裡已經有人登入著的時候，網站不會再給登入表單
（看到 cookie 就把人導去別的頁），`do_login` 的選擇器只會白等到逾時。所以等不到
表單就清掉 cookie 再回登入頁一次 —— 那是網站認人的唯一依據，清掉就等於登出。
憑證不在 cookie 裡（它在 Windows 的憑證存放區與這個 Chrome profile 裡），
不會被這一步弄掉。

**還沒實測。** 這台機器上真帳號只有一組（另外 19 個是不連網的模擬帳號），
「換人」這件事跑不到。要驗的是兩件事：換回去的 cookie 網站認不認、
以及 session 大概多久逾時（逾時之後就會退回重登那條路）。

#### 順序：一組登入完就立刻抓完他的資料

上面那個機制有一個很容易寫錯的前提 —— **抓資料的時候，瀏覽器帶著的必須正好是
那一組的 cookie**。所以 `collect()` 是「登入 → 抓完 → 換下一組」，
不是「20 組全部登入完，再回頭一組一組抓」。後者查到的會是最後那一組的資料：
前面 19 組的分頁看起來都還活著（`sessionStorage` 是分頁自己的，不會因為 cookie
被換掉就變），但 cookie 只有一組，伺服器只認 cookie。

2026/08/21 修掉的就是這個：`collect()` 當時是先 `ensure_logged_in()` 把全部登入完
才進迴圈查。只有一組真帳號的時候完全看不出來（前面沒有別人可以頂掉他），
20 組上線的第一天就會每次讀取都壞。用假瀏覽器＋假伺服器（cookie 是誰的就回誰的
資料）測過四種情境：第一次讀取、第二次讀取（不重登，走換 cookie）、只更新某一位、
先按「登入」再按「讀取」—— 修之前第 1 組拿到第 2 組的資料，修之後四種都各拿各的。

`ensure_logged_in()` 留著給「登入」按鈕用（它只登入、不抓資料，全部登完剛好），
docstring 裡寫明了要抓資料不能用它。借空白分頁那件事也順手收緊：
只借「第一個而且還沒有人認領」的分頁（`spare_page()`），否則第二組會把第一組
正在用的分頁導去登入頁。

### 沒有改的東西

- 「程式自動更新」還是那一個開關，只更新一位照樣是讀完就寫
- 判斷、提案、落帳全部還是 `planner`／`ledger` 那一份，介面只決定範圍
- 一次讀全部的行為跟以前一模一樣（範圍留在「全部」就是了）
