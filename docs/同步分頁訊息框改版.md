# 同步分頁改版：拿掉現金／股票兩張表，併進訊息框

2026/08/22 討論定案，同一天實作完成。這份文件保留當初的完整規格，獨立讀也看得懂，
不必回頭翻對話記錄；「還沒做的部分」那一節現在是實作紀錄，不是待辦。


## 動機

使用者原本的問題：「我真的需要現金表格和股票表格嗎？我需要的只是網頁抓到了
什麼、它又把 Excel 變更了什麼，顯示在訊息框就好，對吧？」

現況（`ui_sync.py`、`ui_layout.py`）：右半邊是兩張 Treeview 並排——左邊
`self.cash_tree`（現金餘額／今日初始現金餘額／現金算法三列），右邊 `self.tree`
（一檔股票一列，股數／成本兩欄），底下才是 `self.warn_box` 訊息框放提醒與
現金算式說明。這兩張表大半列平常都是「跟網頁一致，沒事」，真正要看的一兩格
被淹沒在裡面；而且訊息框裡本來就已經在講「這個數字怎麼來的」，跟表格內容
有重複。

結論：兩張表整個拿掉，內容併進訊息框；現金算法、今日初始現金餘額因為是
「今天的固定基準／設定」而不是「這一輪的結果」，改成常駐顯示在別處，不進
訊息框的捲動文字。


## 要拿掉什麼、留什麼

| 項目 | 現況 | 改版後 |
| --- | --- | --- |
| `self.tree`（股票明細表） | Treeview，一檔一列，股數／成本兩欄 | 整個拿掉 |
| `self.cash_tree`（現金表） | Treeview，現金餘額／今日初始現金餘額／現金算法三列 | 整個拿掉 |
| 現金算法 | 現金表裡一列，可點切換（`_on_cash_click`） | 搬到右上方，變成常駐的一顆小控制項／可點文字，不進訊息框 |
| 今日初始現金餘額 | 現金表裡一列 | 跟現金算法一起常駐顯示 |
| 「修改今日初始現金餘額」按鈕 | 貼在現金表正下方 | 維持獨立按鈕，一樣放在常駐區塊 |
| 現金餘額本身（現在的數字） | 現金表第一列 | 併入訊息框，當作「這一輪改了什麼」的一部分 |
| 股票股數／成本 | 表格一列列列出（含沒變的） | 併入訊息框，**只列這一輪真的有變化的檔** |

**不列未變化項目的取捨**：股票這邊只列有寫入的，沒異動的完全不提。取捨過的
風險是「沒辦法一眼確認今天真的抓到全部檔的網頁資料」——這個由 warnings
（例如「網頁庫存已無此檔」）跟左邊名單的整體狀態旗標補，不在這次改版的
訊息框裡另外加一行「讀到 N 檔」之類的小結（討論過，最後沒有採用這個提案，
維持單純）。


## 資料來源：直接借用歷程檔，不要自己另外管狀態

關鍵決定：訊息框不要自己維護一份「這一輪的暫存結果」再自己想辦法保留、清除。
專案裡已經有現成的東西完全符合需求——**歷程檔**（`ledger.py` 裡的
`-同步歷程.jsonl`，`planner.commit()` 每次真的寫入 Excel 就會 append 一筆
事件：`at`／`sheet`／`cell`／`label`／`by`／`old`／`new`／`note`，「歷程」
分頁 `ui_history.py` 就是拿這份檔案篩選著看的）。

做法：訊息框內容 = 這份歷程資料，篩選成「`sheet == 目前選中的交易人`
且 `at` 是今天」（沿用 `ui_history.within()` 那套邏輯），重新排版成一行一句話。

好處：
- 不用自己想一套「換人／重開程式資料要不要保留」的狀態機——資料本來就在磁碟上，
  按 `sheet` 分好了，換人只是換篩選條件
- 跟「歷程」分頁看到的是同一份真相，不會兩邊對不起來
- `self.history_rows` 已經在 `refresh_history()`（每次 commit 完都會呼叫，
  見 `ui_background.py`）裡整份讀進記憶體了，換人重畫訊息框只是在記憶體裡
  篩一次，不必碰硬碟

**沒被寫入、因此不在歷程裡的東西**：現金被擋住不寫的那幾句提示（例如「B8 是
空的，請先填一個現金餘額」）、股票「網頁庫存已無此檔」的提醒。這些維持現在
的 `warnings` 機制，排在今日歷程清單之後，跟「今天已經發生過的事」分開。


## 訊息框最終格式規格

### 標籤與行文

```
19:54:23 [餘額更新] 初始餘額累加 = 893 - 238 = 655
19:54:23 [餘額更新] 銀行餘額推算 = 893 - 238 + 0 = 655
19:54:20 [股票更新] 2059 川湖　股數 2,000　成本 10.8
```

- 標籤統一叫「更新」：`[餘額更新]`、`[股票更新]`（不是「異動」）
- **都不留「舊 → 新」**：這是一份會往下疊的今日歷程，想知道以前是多少，看
  上面／更早的那一行就有了，不必在同一行重複兩個數字
- 股票只列這一輪真的有寫入的欄位：股數／成本同一輪都改了就兩個一起列在
  同一行；只改了一個，那行就只寫那一個（合併規則見下面）
- **現金一律列出完整算式**（2026/08/22 訂正：原本規劃只有轉負那一次才印算式，
  平常只顯示算出來的數字；使用者確認後改成不管有沒有轉負都要看得到算法），
  格式是「{算法名稱} = {算式} = {結果}」，兩種算法都是這個形狀：
    - 初始餘額累加：`今日初始現金餘額 + 今日淨收付` 那組數字 → `893 - 238 = 655`
    - 銀行餘額推算：`銀行餘額 + 淨收付(T+0) + 淨收付(T+1) …` 那組數字 →
      `893 - 238 + 0 = 655`
  這段數字就是既有的 `item["note"]`（`planner._bank_note`／`_formula_note`
  算好的）去掉前面那串標籤文字（`銀行餘額 + 淨收付(T+0) + …`），換算法名稱
  打頭——標籤名稱在這裡是重複資訊（算法名稱已經講了這是哪一種算法），數字
  才是這一行真正要看的東西。

### 現金是負的：只有顏色是例外

算式本身不管正負都印（見上面）。**結果是負的那一行整行標紅**：

```
19:54:23 [餘額更新] 銀行餘額推算 = -893 + 238 + 0 = -655      ← 整行標紅
```

**2026/08/22 再訂正**：紅字判斷原本是「這一輪把餘額從正轉負」（`old >= 0
and new < 0`），結果連續好幾筆都是負的時候，除了轉負那一筆，後面每一筆
「老早就負的」都沒有紅字——使用者實測發現這樣看起來像沒事。改成只看
`new < 0`，跟名單上現金負的名字變紅字同一個規則：看「現在是不是負的」，
不看「是不是這一輪才變負的」。`[今日初始餘額]` 那個標籤也是同一個規則。

### 「今日初始餘額」是另一個標籤，不是 [餘額更新]

2026/08/22 使用者訂正：現金的歷程事件裡有兩種 `by == "adopt"`——今天第一次
登入把 B8 收成今日起點（`planner.initialize`）、「修改今日初始現金餘額」算出來
剛好等於 Excel 上的數字所以沒有格子要寫（`planner.apply_cash_reset`）。這兩種
都不是套公式算出來的餘額異動，Excel 那一格根本沒被寫過。原本套用 `[餘額更新]`
跟一句沒帶數字的說明（例如「今日初始現金餘額（今天第一次登入時的 B8）」），
語意不明：讀起來像有什麼被更新了，卻看不到任何數字。

改用專屬標籤，直接印當時的數字：

```
16:16:41 [今日初始餘額] 893
```

負的話一樣整行標紅（跟 `[餘額更新]` 用同一個 `neg` tag），但這裡沒有「轉負」
的概念——今天一開始就是負的也算，不必等「這一輪由正轉負」。

`by == "program"`（真的寫了 Excel）才會出現在 `[餘額更新]` 底下：多數時候是
`_cash_formula` 算出來的算式，但「修改今日初始現金餘額」如果真的寫了格子，
note 是 `apply_cash_reset` 自己的散文說明，不是「標籤 = 算式 = 結果」的形狀，
一樣原樣印出（`_cash_formula` 抓不到算法名稱時的備援）。

### 現金結果沒變就不重複印，常駐狀態列補一項「現金餘額」

2026/08/22 使用者發現：現金每次讀取都無條件覆蓋 B8（見
`docs/現金餘額兩種算法.md`「B8 無條件覆蓋」），連續按好幾次「讀取」而金額
沒變的時候，訊息框會出現一長串一模一樣的 `[餘額更新]` 洗版——同一個結果連
續出現不只一次沒有任何資訊量。

做法（`ui_sync._dedupe_cash_rows`）：現金那幾筆事件按時間先後比對，結果
（`new`）跟上一筆顯示過的一樣就整筆丟掉，不進訊息框；只有「今天第一筆」、
「數字真的變了」（含由正轉負、由負轉正這種變化）才會留下來顯示。這隻動
訊息框要不要重複顯示，**不**動 Excel 寫入或歷程檔——B8 照樣每次覆蓋、
「歷程」分頁照樣一筆不漏，只有這裡的訊息框看不到連續重複的那幾筆。

拿掉重複顯示之後有個副作用：訊息框可能連續好幾輪都沒有新的一行（因為結果
沒變），這時候想知道「現在的現金餘額到底是多少」，不能只看訊息框最後一行
——那一行可能是很久以前印的。所以常駐狀態列多一項「現金餘額」（見
`ui_sync._fill_status`），不管這一輪訊息框有沒有印新的一行都固定顯示目前
算出來的數字：訊息框只回答「發生了什麼事」，狀態列固定回答「現在是多少」，
兩件事分開。負的一樣紅字，跟名單上現金負的名字變紅字同一個規矩。

### 「這一輪跟網頁一致、不用更新」怎麼講：最後定案是常駐狀態列的小提示

這一小節的做法換了三次，以下只留最終結論＋簡短的演變理由，細節不用回頭
翻對話記錄。

**最終做法（2026/08/22 定案）**：右上角常駐狀態列（`method_label`／
`opening_label`／`balance_label` 那一排）多一個 `quiet_label`，讀成功
（或改完今日初始現金餘額）之後原地顯示：

```
✓ 與網頁一致（19:16:42）
```

- 時間來自 `self.round_at[name]`（`ui_background._on_fetched`、
  `ui_sync.edit_opening` 各自更新一次，同一輪大家蓋同一個時間即可）。
- `ui_sync._fill_status` 判斷要不要顯示：這一位被擋住（現金還沒設基準）
  或有提醒（例如「網頁庫存已無此檔」）在跑的時候不顯示——那時候不算
  「一致」，提醒本身已經在講了，這裡不能講反話。
- 顏色用 `self.colors.success`（綠），呼應打勾符號的既有語意。
- 每次讀取／修改今日初始現金餘額都是**原地覆蓋**，不是疊加——跟訊息框
  「按幾次疊幾行」的歷程時間序刻意不一樣，因為這句話「多數輪次都成立」，
  疊起來反而是雜訊，只有「現在」這一份值得看。

**為什麼不是一句話（演變過程）**：

1. 一開始想放在底下的一行式狀態列（`ui_background._problem_note` 那條），
   但那裡塞不下「股數、成本跟網頁一致，不需要寫入；現金金額不變（但仍會
   照例更新公式）」這麼長的句子，改放進訊息框，當作「這一輪」的說明
   （灰字、永遠排最前面）。
2. 使用者發現這樣看起來像釘死在第一行，要求改成掛時間戳、跟其他逐筆歷程
   一樣排序——結果連續按好幾次「讀取」都沒事的時候，只看得到最後一次
   （單一值被每一輪覆蓋）。
3. 再改成用一份會累加的清單，按幾次「讀取」就留幾行、混進訊息框的時間序
   裡——這時才發現真正的問題：多數讀取本來就是「沒事」，累加下去訊息框
   反而被這句話洗版，真正的異動（`[餘額更新]`／`[股票更新]`）被埋在一堆
   長得幾乎一樣的 `[說明]` 裡面。
4. 結論：這句話的本質是「現在的狀態」，不是「這一輪發生的事」，跟
   `balance_label`（現金餘額）同一類，不該待在訊息框那個逐筆歷程的時間序
   裡——搬到常駐狀態列、原地更新，才是它真正該待的地方。

文字也順手簡化：不再分「股票一致」「現金不變」兩句話各自判斷、用「；」
合併，改成單一句「與網頁一致」，不逐項細講是哪個部分沒變——這點細節
2026/08/22 使用者認可可以放棄，換取狀態列夠簡短。

### 框的標題掛名字，字級加大

2026/08/22 使用者要求：訊息框拿掉「讀取於」那行之後，換人換得快的時候容易
看著一段文字卻認不出是誰的。沒有走「加回第一行」這條路——第一行會被捲軸
捲走，換人時不一定看得到——改成 `ui_layout.LabelFrame` 的標題動態掛名字
（「交易人A　訊息」），貼在框邊、不隨內容捲動，換人立刻看得到（見
`ui_sync._fill_right`）。字級也從 `HINT_SIZE`（欄位說明那種次要文字）加大
兩級：兩張表拿掉之後這裡是唯一逐行讀的內容，該是主要閱讀區級別，不是次要
提示的級別。

### 排列規則

- **同一輪內**：現金固定排最前面，股票照 Excel 列的順序排在後面——不管歷程檔裡
  實際寫入的先後（`planner.plan()` 是股票先、現金最後才 append，`commit()`
  照這個順序記歷程，所以歷程檔裡的原始順序是股票在前；訊息框畫的時候要自己
  重排，不是直接照歷程檔順序印）
- **整體**：新的在最上面，跟「歷程」分頁同一個慣例（`ui_history._fill_history`
  裡 `reversed(shown)` 那個做法）

### 股數／成本合併規則

歷程檔裡股數、成本是兩筆分開的事件（一格一筆）。合併成一行的判斷依據：
**同一檔股票的名稱（從 `label` 拆出來，例如「股數（2059 川湖）」取「2059 川湖」）
+ 同一個 `at` 時間戳**——同一輪寫入的話兩筆事件的 `at` 會完全一樣，這個規則
抓得到。


## 常駐顯示區（不進訊息框）

現金算法、今日初始現金餘額、「修改今日初始現金餘額」按鈕，搬到右上方變成一個
小狀態列，常駐顯示，不管這一輪有沒有異動都在。現金算法維持可點切換
（`.env` 的 `CASH_METHOD_TOGGLE` 照舊管得到要不要開放點擊）。

`quiet_label`（「✓ 與網頁一致」小提示，見上面「這一輪跟網頁一致、不用更新」
那節）2026/08/22 加進同一排，也是原地更新、不進訊息框。


## 提醒（警告／整組失敗）改成時間序，不再堆在固定位置（2026/08/22）

**背景**：股票提醒（`self.warnings`）、整組帳號失敗（`self.problems`）原本
都排在訊息框最後面。使用者實測發現：帳號測久了，訊息框累積很多行今天的
歷程，提醒被擠出這個小框（`warn_box`，大概只顯示 4~5 行）的可視範圍，要
往下捲很多次才看得到——等於沒提醒。

**最終做法**：兩者都改成跟其他行同一種「時間 [標籤] 內容」形狀，混進同一個
時間序裡照時間排序（見 `ui_sync._format_today_events`），不加特殊顏色：

```
09:00:00 [警告] 第 5 列「0050 元大台灣50」在網頁庫存中已不存在
09:00:00 [警告] 網頁有 006208 富邦台50（200 股）但 Excel 沒有這一列
20:35:08 [異常] 登入失敗
```

同一輪內（同一個 `at`）排序：異常 > 警告 > 現金 > 股票。

**股票警告**（`_warning_line`）：
- 文字縮短，拿掉「股數與成本維持原樣，請確認是否忘記刪除這一列」「不會
  自動新增，請自行決定放在哪一列」這兩句說明性尾巴——跟其他行一樣簡短
  （改過的檔案：`planner.py` 的 `plan()`）。
- 「同一檔股票在網頁上佔了好幾列，已用股數加權平均合併成本」這則提醒
  **整個拿掉**：使用者確認同一天分批用現股買賣同一檔，網頁上券商已經先
  平均好只剩一列；會佔多列的其他交易別（融資等）目前的交易方式不會發生，
  所以這個情境根本不會觸發。合併股數/成本的計算邏輯本身還留著（防真的
  資料不對時算錯持股），只是拿掉那句用不到的提醒；`merge_holdings()` 回傳
  值也從 `(merged, notes)` 簡化成只回 `merged`，`record["trades"]`／
  `TRADE_NAMES` 這些只服務那句提醒的東西跟著一起刪掉。
- 時間戳來源是 `self.round_at[name]`（跟右上角「✓ 與網頁一致」小提示同一個
  來源，讀資料那一刻定住），因為 `self.warnings[name]` 本身不帶時間。
- 現金被擋住的那幾句（`planner._cash` append 的 `[現金] ...`）**還在討論
  中**，暫時維持原樣排在最後面，不進這個時間序。

**整組帳號失敗**（`_error_line`）：
- 使用者要求不要放進系統狀態列（`self.status`，那顆一行式的東西塞不下、
  也會被下一句話蓋掉），也不要 20 個人共用同一份——改成**按交易人分流**：
  `self.problem_of[order]` 從單純字串換成 `{"text":..., "at":...}`，
  `_refresh_problems()` 攤平出的 `self.problems` 每一項多帶一個 `order`；
  `ui_sync._fill_notes` 用 `self.trader_of.get(order)` 反查這一組對應到
  的交易人，等於這個人只把屬於自己那幾組的失敗原因併進自己的訊息框。
  文字不再自帶「第 N 組：」前綴——人是誰已經在框的標題上了，前綴是重複
  資訊。
- 極少數「連是誰都查不出來」的情況（`trader_of` 也沒有這個 order，通常是
  這組帳號從來沒有成功登入過）沒有任何交易人的分頁掛得上，退回舊做法：
  不管選中誰都顯示，前綴補回「第 N 組：」自報身分。
- 失敗原因**不套「今天」的篩選**：跟股票警告不一樣，這是要留到「這一組
  自己再讀一次成功為止」的持續狀態（見 `_refresh_problems` 原本就有的
  設計），不是今天才發生、過午夜就該消失的一次性事件——時間戳照樣掛
  `problem_of[order]["at"]`，只是舊的一樣會顯示，只會因為時間比較舊而
  排到後面去，不會被濾掉。
- `now`（這一輪的時間戳）要在 `ui_background._on_fetched` 判斷失敗原因的
  迴圈之前先算好，原本是判斷完才算。


## 其他決定

- **訊息框要加捲軸**：現在的 `warn_box`（`tk.Text`）固定高度、沒有捲軸，裝不下
  的內容會被無聲吃掉。內容量變多之後這個風險不能再賭，一定要加捲軸。
- **視覺上色**：原本表格用列的底色／前景色做提示（負的紅字、要寫的綠底），
  改成 `tk.Text` 的 tag 上色，機制換了但視覺信號要留著（至少負的紅字這條，
  見上面「現金轉負」那節）。
