# 成交確認規格

**狀態：規格，還沒實作。** 定案落地之後把結論併進 `docs/介面規劃.md`（建議編號 9.11），
這一份留著當「為什麼這樣設計」的出處，跟 `docs/更新分頁訊息框改版.md` 同一種定位。

來源：2026/09/05 使用者要求——**買賣股票、出清股票、全持股交易只要送出過委託，都要用
查詢結果確認成交與否，三個作業的判斷方式要一致**，不是只在出清那邊特例處理。

**2026/09/05 追加、推翻原本「查兩支」的設計**：一開始規劃另開 `queryDealOrder`
（`order_deal_recon.py` 已驗過，唯讀偵察保留），但對照台企銀網頁「委託查詢」頁自己的
`fakeJSON()` 判讀邏輯（`errcode`／`orgqty`／`matqty`／`act` 決定顯示哪一句）發現：
**`queryOrder` 一支自己就查得到「成交多少」**，`order_recon.describe_outcome` 早就是那段
邏輯的部分移植。決定**不顯示均價／收付金額**（那兩個數字才是原本非要 `queryDealOrder`
不可的唯一理由）之後，第二支查詢整個沒有存在的必要——`order_deal.py`、`order_deal_recon.py`
接線都收掉，改成在 `order_query.py` 內部多一支純函式。以下內容已經照這個決定改寫；
`order_deal_recon.py` 當偵察腳本留著，不刪，只是不進正式路徑（同 `fastquote.py` 的定位）。

## 一、現在的答案有三份，沒有一份是直接問券商的

| 作業              | 現在怎麼判斷「成交了沒」                                 | 問題                                            |
| ----------------- | -------------------------------------------------------- | ----------------------------------------------- |
| 買賣股票（ROD）   | 完全沒有判斷                                             | 送出去就結束，成交與否只能自己去網站看          |
| 出清・整張（IOC） | 下一輪完整同步之後比對持股股數（9.9）                    | 只有勾多輪才有；單輪跑完什麼都不知道            |
| 出清・零股（ROD） | 等 6 秒查 `queryOrder`，看還有沒有 `open` 的單就撤（9.8） | 那是「還掛不掛在外面」，不是「成交多少」        |
| 假帳號            | `simulate_orders.fill_order` 當場回報的 `matched_qty`     | 只有假帳號有，真帳號的 payload 裡沒有這個鍵     |

`ui_order_exec._order_exec_init_state` 那段註解已經寫明了這個缺口：「真帳號目前沒有這條路
可以確定『當場沒有成交』……要另外走 `queryDealOrder` 才查得到，還沒做」。這份規格就是把那句
話補上，順便讓「沒有進展就停」那道保險對真帳號也講得出道理。

## 二、不動的東西（先講清楚，免得順手改掉）

- **對帳只讀，不寫。** 不寫 Excel、不落帳、不改 `self.order_holdings`。持股怎麼變是完整同步
  那條路的責任（9.9），用成交量去推持股等於在同步之外開第二條寫入路徑，那正是 9.9 花了兩天
  才收乾淨的東西。
- **不碰「掛單分頁只列還掛在外面的」那個決定**（2026/09/02 使用者定的）。
- **不碰收斂訊息與底部進度條**（9.10 已經定案的那幾句一個字都不改）。
- **不讀 `queryOrder.avg_price`**：它是 `queryDealOrder.avg_price` 的 **100 倍**（2026/09/04
  五筆真實委託書號全部驗過，跟 `queryBankBalance` 的 `Amount` ÷100 同一種地雷）。目前全專案
  沒有人讀它，維持不讀，並在 `order_query.normalize` 旁邊補一句警告。
- **`branchId` 不加 `'1'` 前綴、鍵名是 `cust_id`**，跟 `queryOrder` 同一套規則（跟 `query610`
  ／`queryBankBalance` 相反）。錯了不會報錯，只是查不到東西。

## 三、A：`order_query.classify()`（不開第二支查詢）

原規格這裡是一整支新模組 `order_deal.py`（呼叫 `queryDealOrder`、`merge()` 兩支查詢的結果、
外加「這支 CMD 沒有 `bhno`/`cseq`，要跟 `queryOrder` 借身分核對」的整套借用規則）。收掉的
理由見文件開頭：**判讀成交與否只需要 `queryOrder` 自己的欄位**，`order_query.normalize()`
已經攤開 `matched`／`qty`／`left`／`open`／`ordstatus`，`raw` 裡還有 `errcode`。不必再開一次
登入分頁、不必對第二支回應做身分核對、不必寫 `merge()` 去比對兩份資料是不是講同一張委託。

新增的是 `order_query.py` 裡一支純函式：

```python
def classify(order_rows, wanted):
    """wanted: [{"ordno", "code", "side", "unit", "lots"}, ...]，這一輪這一位送出去的那幾筆。
    回傳 {ordno: {"outcome": ..., "matched": ..., "sent": ...}}，純函式、不碰 Playwright。
    """
```

`order_rows` 就是 `query_orders()` 回傳的那份（呼叫時已經做過身分核對，丟例外就整批不能
用）；一個 `ordno` 一列比對 `wanted`，判斷邏輯照第五節的七種結論表，用的全是 `normalize()`
現有欄位（`matched`、`qty`、`open`、`ordstatus`、`raw["errcode"]`），不需要第二份資料。

`order_query.py` 仍然新增 `class SessionMismatch(RuntimeError)`——這條跟要不要查
`queryDealOrder` 無關：`query_orders()` 本來就會核對身分，只是現在核對失敗丟的是普通
`RuntimeError`，對帳那一段要分辨「查詢失敗（記錄、繼續下一位）」跟「身分不符（整批停）」，
所以還是要把後者獨立成子類別（現有 `except RuntimeError` 全部照舊不受影響）。

## 四、B：委託書號從哪來（兩條路都拿得到）

`偵察資料\委託確認視窗\orderConfirmRWD.html:767` 寫死：
`$('#result'+row).text('委託成功,委託書編號: '+ordno)`。

| 模式               | 書號從哪拿                                                               |
| ------------------ | ------------------------------------------------------------------------ |
| 自動送出（真帳號） | `order_fill.confirm_order()` 回的 `message` 就含著書號，已經在 payload 裡 |
| 自動送出（假帳號） | 假網頁的 `委託成功, 委託書編號: ` ＋ 書號（**逗號後多一個空白**）          |
| 半自動（人按確認） | 背景輪詢視窗關了沒的時候，順手讀一次 `#result0`（見下）                   |
| 人按了「取消」     | `#result0` 是空的 → 沒有書號 → 那一列的結論是「未送出」                 |

要做的三件事：

- **`order_fill.parse_ordno(message) -> str`**：正規式 `委託書編號[:：]\s*([A-Za-z0-9]+)`，
  抓不到回空字串。真假兩條路共用同一支（假網頁多一個空白，正規式本來就吃得下）——
  **一套判讀只能有一份**。
- **`order_fill.read_confirm_result(page) -> str`**：讀確認視窗 iframe 裡 `#result0` 的文字，
  讀不到（視窗還沒開、已經關了、frame 不在）一律回空字串，不丟例外。
- **`ui_order_exec._order_dialog_closed(page)` 改成 `_order_dialog_state(page) -> (closed, text)`**：
  每一輪輪詢先讀一次文字（讀到非空就記著、蓋掉舊的），再判斷視窗關了沒；視窗不見了就把記到的
  最後一份交出去。`_browser_worker` 那邊多存一個 `order_watch_text`，回話改成
  `("order_dialog_closed", {"message": text})`。

  **這是唯一動到「依序執行」熱路的一段**，只多一個唯讀動作，不新增任何 click／goto——那條路上
  「換 cookie 前一定要等視窗真的關掉」的規矩一個字都不能動（見 `ui_order_exec.py` 開頭那段）。

`_on_order_filled`／`_on_order_dialog_closed` 把書號存進 `self.order_exec_ordno[(sheet, code)]`，
**自動送出那條路以 `auto_result["message"]` 為準**（那是程式自己按的，最可靠），半自動才用
輪詢讀到的那一份。

> 一輪之內 `(sheet, code)` 必定唯一（三支 `plan_*` 都是「帳戶 × 股票」交叉，一列一筆），
> 跟 `self.order_preview_iid` 用同一組鍵，所以對得回畫面上那一列。哪天同一輪同一檔會出現
> 兩列（例如整張＋零股混在同一批），這個鍵要跟著加上單位。

## 五、C：新的一段「輪後對帳」

### 位置

```
一輪的委託全部送完
  → ［零股才有］等 6 秒 → 撤掉還掛著的（現況，不動）
  → ★ 對帳：一個帳戶一則指令，查一次 `queryOrder` 比對成交            ← 新增
  → ［勾多輪才有］完整同步 → 重讀 Excel → 下一輪
```

**三個作業都跑，不分單輪多輪**（單輪跑完什麼都不知道，正是使用者要補的洞）。
接在撤單**後面**：零股那批單撤掉之後，「成交多少」才是最終答案；撤之前查會漏掉那零點幾秒
之間撮到的量。

**不逐筆對帳**（每送一筆就查一次）：一筆委託要多一趟查詢，20 位 × 10 檔就是 200 趟；
而且 ROD 剛掛上去查一定是 0，查了也沒有意義。

**成本**：一個帳戶約 1 支查詢（換 cookie ＋ 一個頁面 ＋ `queryOrder` 這一支 AJAX，跟掛單
分頁現在查一次的量體一樣，比照記憶「每組帳號登入/讀取的實測秒數」的讀取 2.1 秒量級），
一輪查一次，比原本規劃兩支查詢再省一半。這一輪一筆委託都沒送出去的帳戶**直接跳過、不查**
（沒有書號就沒有東西要對）。

### 指令與 job

`ui_background._browser_worker` 新增一個分支 `order_deal_check`，形狀照 `order_odd_cancel` 抄
（**不收進 `simple_jobs`**：那張表的錯誤 payload 沒有 `sheet`，這裡失敗時一定要說得出是哪一位）：

```python
("order_deal_check", (order_number, account, sheet, wanted))
#   wanted = [{"ordno", "code", "side", "unit", "lots"}, ...]  這一輪這一位送出去的那幾筆
```

```python
def _order_deal_check_job(self, context, store, order_number, account, sheet, wanted):
    page, session, problems = fetch_mod.ensure_logged_in(...)      # 同其他 job
    query_o = simulate_orders.query_orders if account.get("fake") else order_query.query_orders
    order_rows = query_o(page, session, sheet)    # ← 身分核對在這裡，會丟 SessionMismatch
    return {"fills": order_query.classify(order_rows, wanted)}
```

`order_query.classify()` 是純函式（好測、不碰 Playwright），一個 `ordno` 一列結論：

| `outcome`  | 條件                                          | 意思                                       |
| ---------- | --------------------------------------------- | ------------------------------------------ |
| `full`     | `matched >= 送出量`                           | 全部成交                                   |
| `part`     | `0 < matched < 送出量`                        | 部分成交                                   |
| `open`     | `matched == 0` 且委託那一列 `open` 為真       | 還掛在外面，今天還可能成交                 |
| `reserved` | 委託那一列 `ordstatus == '1'`                 | 預約單，今天不會成交（收盤後送的會是這種） |
| `failed`   | 委託那一列 `errcode != '00000000'`            | 委託被拒／IOC 未能成交                     |
| `none`     | `matched == 0`、不 `open`、`errcode` 正常     | 已結案、一股都沒成交（IOC 沒吃到／已撤）   |
| `unknown`  | 查詢結果裡找不到這個 `ordno`                  | 無法確認，**不要猜**                       |

判斷順序照上表由上往下（先看成交量，再看委託狀態）。`送出量` 換算成股：整張 `lots × 1000`、
零股 `lots`（跟 `_order_sent_qty` 同一套換算）。

### 失敗怎麼辦

| 情況                   | 行為                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| `SessionMismatch`      | **整批停下來** ＋ `show_error`：剛剛那幾筆委託可能是用別人的 cookie 送的，這是最嚴重的一種  |
| 其他查詢失敗／登入失敗 | 記進 `problems`，**繼續查下一個帳戶**，跑完 `show_warning` 一次；**不擋下一輪**              |
| 使用者按「停止」       | 不派下一則就是停了（跟撤單同一個做法，不必另外發明跨執行緒旗標）                            |

「不擋下一輪」的理由跟撤單失敗那條一樣（`_odd_cancel_finished`）：對帳只是把事情看清楚，
它跟「下一輪該不該跑」是兩件事——而下一輪開始前那次完整同步會把真實持股讀回來，該修正的
都會被修正。

`stop_order_execution` 要多認一種「queue 是空的但整批還在跑」的狀態（現在有四種，這是第五種），
狀態文字見第八節。

## 六、D：畫面——執行預覽多一欄「成交」

**這是「成交訊息要不要整合進執行預覽」那一題的答案：整合進去，不另開分頁、不另開視窗。**

理由：執行預覽本來就是「一列一筆委託」的表，成交結果天生屬於那一列；掛單分頁刻意只列
「還掛在外面的」（2026/09/02 定案），成交完的單在那裡看不到；而訊息框是一次性的，
20 位 × 10 檔的結果塞不進一句話。

### 欄位位置

```
順序 帳戶 買賣 股票 張數 價格 │ 持股 出清進度 成交 │ 備註
                              └ 為什麼是這樣 ＋ 結果 ┘
```

放在**「出清進度」右邊、「備註」左邊**：出清進度與成交都是「跑起來才有值」的結果欄，
擺在一起；備註留在最後，因為它最寬、內容最多變。買賣股票／全持股交易看不到出清進度
（`displaycolumns` 切掉），但**成交這一欄三個作業都看得到**——那正是「三個作業一致」的意思。

改動點跟 9.10 完全一樣的三處，不要只改一邊：`ui_layout` 的 `columns` 與 `titles`、
`ui_order._render_order_preview` 的 values tuple、`displaycolumns` 那一段。
欄寬用 `col_width` 量可列舉的候選字串（照 9.10 量出清進度的做法），不要寫死。

### 一格顯示什麼

| 時間點／結論     | 顯示            | 說明                                       |
| ---------------- | --------------- | ------------------------------------------ |
| 還沒開始／被略過 | （空白）        | 跟現在的行為一致                           |
| 已送出、還沒對帳 | `送出中`        | `index < order_exec_pos` 那幾筆            |
| `full`           | `2/2 張`        | 零股是 `327/327 股`                        |
| `part`           | `1/2 張`        |                                            |
| `open`           | `0/2 張 掛著`   | 今天還可能成交，不是失敗                   |
| `reserved`       | `預約單`        | 收盤後送出的，今天不會成交                 |
| `failed`         | `委託失敗`      | 原因太長塞不下，寫進備註欄或狀態列         |
| `none`           | `0/2 張 未成交` | IOC 沒吃到、或掛到被撤掉                   |
| `unknown`        | `無法確認`      | 查不到這個書號                             |
| 沒有書號         | `未送出`        | 人按了取消，或視窗被自己關掉               |

單位跟著那一列的 `unit` 走（張／股），不是跟著整批模式——理由同 `_order_fill_job` 裡算 `odd`
那一行的說明。

### 出清進度改用「確認成交」推進（9.10 的一小段修訂）

9.10 現在寫「百分比只算已經確認出清的部分，絕對不含已送出——**真帳號拿不到成交量**」。
括號裡那個前提正是這份規格要拿掉的東西，所以規則跟著升級（**精神不變：不把「送出」當「成交」**）：

```
done = max(base_qty - now_qty, 這一批累計確認成交的股數)
```

- `now_qty` 還是來自 `self.order_holdings`（同步寫回來的），仍然是最終權威；
- 累計確認成交只補「同步還沒跑、但成交已經確認」那一段空窗；
- 兩者取 max，同步跑完之後兩邊會收斂到同一個數字，不會重複計算；
- `▒`（已送出）的意思跟著變精確：**送出去、但還沒對帳**。對帳完那一段就會變成 `█` 或消失。

新狀態放三份，不要塞進 `order_holdings`（那份是持股，動它就是在同步之外偷改持股）：

```python
self.order_exec_fills   = {}   # (sheet, code) -> 這一輪的對帳結論；每輪重組 queue 時清空
self.order_exec_matched = {}   # (sheet, code) -> 這一批累計確認成交股數；start 時清空、停止不清
self.order_exec_ordno   = {}   # (sheet, code) -> 這一輪的委託書號
```

刷新照 9.10 那條路：`_refresh_order_progress_cells` 一起更新「成交」那一格（單格 `set`，
不重畫整張表），仍然掛在 `_update_order_exec_ui` **最前面**、所有 early return 之前。

## 七、E：「沒有進展就停」那道保險改用對帳結果

現在的例外只對假帳號生效（`order_exec_round_all_fake` ＋ `all_zero_fill`，靠
`simulate_orders.fill_order` 當場回報的 `matched_qty`）。有了對帳，真帳號也講得出同一句話：

- `all_zero_fill` 改成由**對帳結果**餵：這一輪每一筆的 `outcome` 都是 `none`／`failed`／`open`
  （＝一股都沒成交）才算數。
- 只要有任何一筆是 `unknown`、或這一位的對帳整個失敗，就當作**不能確認** → 保險照舊生效
  （保守的那一邊，跟現在 `matched_qty is None` 打成 `False` 是同一個態度）。
- `order_exec_round_all_fake` 可以收掉了：例外的理由從「這是假帳號」變成「對帳確認了零成交」，
  假帳號自然也走同一條路（假網頁的 `queryOrders()` 一樣吐得出 `matqty`）。
  **收掉的時候要在 `_order_exec_init_state` 留一句話說明它為什麼消失**，不然下次看到
  9.9 或「假帳號下單模擬」那篇記憶，會以為是漏掉的。

連帶：真帳號多輪出清一直沒成交時，現在會在第 2 輪被保險擋下來（症狀跟真的出事一樣）；
改完之後會照 `ORDER_MULTI_ROUND_CAP` 跑滿再停——**這是對的**（追價本來就可能好幾輪吃不到），
但要在 9.9 補一句，免得看起來像保險失效。

## 九、F：假帳號那條路

- 假帳號不用另外接線：`simulate_orders.query_orders()` 本來就吐得出 `matqty`（假網頁的
  ROD 成交在 `resolvePending()` 那一刻就定案了），`order_query.classify()` 對真假帳號是
  同一支函式，不用像原本規劃那樣為假帳號多寫一支 `query_deals()`。
- `simulate_orders.fill_order` 現在把 `place()` 回的 `ordno` 丟掉了——**不必補**：真假兩條路
  都改用 `order_fill.parse_ordno(message)` 從訊息文字解析，少一條真帳號沒有的捷徑。
- 假網頁「異常注入」那一區加一顆（可選，但很便宜）：**「委託查詢查不到這一筆」**，讓
  `unknown` 那條路測得到——它是唯一會讓保險維持生效的分支，沒有注入就只能靠想像。

## 十、不做的事

- **不逐筆對帳**（每送一筆查一次）：一輪一次就夠，理由見第五節。
- **不用成交量去推持股、不寫 Excel、不落帳**：那是完整同步的責任（9.9）。
- **不叫 `queryDealOrder`、不建 `order_deal.py`**（2026/09/05 推翻原規劃）：`queryOrder`
  自己的 `errcode`／`orgqty`／`matqty`／`ordstatus`／`celable` 就夠判斷成交與否，
  `order_deal_recon.py` 當偵察腳本留著，不進正式路徑。
- **不顯示均價／收付金額**：那兩個數字才是原本非要 `queryDealOrder` 不可的唯一理由，
  沒有這個需求就沒有第二支查詢的必要。
- **不讀 `queryOrder.avg_price`**：100 倍地雷，就算哪天真的要顯示均價，也不能從這支 CMD 讀。
- **不做「等到成交才進下一輪」的等待迴圈**：ROD 可能整天掛著，等於掛在那裡不動。
- **不做對帳開關**：少一個開關就少一個「上次忘了勾」的坑。真的實測太慢再回來加。
- **不改掛單分頁**：它的定位是「還剩什麼可以取消」，不是對帳面。

## 十一、落地順序（每一步都跑得起來）

1. `order_query.classify()` ＋ `order_query.SessionMismatch` ＋
   `order_fill.parse_ordno`／`read_confirm_result`（純函式／純模組，還沒接畫面）。
2. 委託書號蒐集：`_order_dialog_state` 改回傳兩個值、payload 帶 message、
   `order_exec_ordno` 存起來。**這一步先不做任何查詢**，先確認兩種模式都真的拿得到書號
   （狀態列暫時把書號印出來驗一次就好）。
3. 輪後對帳那一段（指令、job、`classify`、失敗處理、停止）。
   假帳號先跑：多輪出清整段離線測到收斂，看得到 `full`／`part`／`none` 三種結論
   （`simulate_orders.query_orders()` 現成就有 `matqty`，不用額外接線）。
4. 畫面：「成交」欄、出清進度改用確認成交、保險改用對帳結果。
5. 真帳號小單位實測（一檔零股，盤中），驗收條件：
   - 自動送出：書號解析得到、成交欄顯示 `n/n 股`；
   - 半自動按確認：同上；
   - 半自動按取消：成交欄是 `未送出`，而且不會被算進進度；
   - 零股掛了沒撮到被撤掉：`0/n 股 未成交`，撤單那一段的結論一個字不變。
6. 定案內容併進 `docs/介面規劃.md` 9.11，這份文件標成「已落地」。
